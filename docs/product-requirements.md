# ForgeLoop 首版产品需求：快速启动

日期：2026-10-12，Asia/Shanghai。状态：范围已冻结；**主体已实现**（domain/records/adapter/graph/cli、受控归并与 CD 的 S1–S3、需求研发线入口 I01），**真实验收尚未完成**（A01/G01 真实小任务、G02 完整需求到部署、A05 备份未执行）。实现与验证状态见[状态记录](status.md)，不写在本文件。

首版目标：**用 CLI 完成一个真实小任务，从批准方案到可验收代码交付。** 需求审查见[审查表](requirements-review.md)，后置功能见[待实现列表](pending-requirements.md)，完整旧目标见[历史快照](history/full-product-scope-2026-10-12.md)。

**所有者需求澄清（2026-10-15）**：ForgeLoop 应具备修改 ForgeLoop 项目并交付可验收代码的能力，实现自我迭代。取消“服务端强制拒绝所有绕过 ForgeLoop 的写入”和“只有 ForgeLoop 才能提交”的要求；该要求已撤销，不进入待实现列表。所有者、DSH 及其他开发工具仍可在项目授权、提交时段和质量约定内修改、提交与推送。

## 1. 用户与范围

一名所有者、一个主要执行节点、一次执行一个小任务。项目由用户手动创建并同步 GitHub，配置文件可以登记首期两个项目；任务绑定一个项目，禁止跨项目任务。先验证 ForgeLoop，不分析其他项目业务。

首版输入仅为文本正文或 UTF-8 文本文件。链接作为原始输入保存，需要的资料由用户提供文本或已在仓库中的文件。大需求人工拆成小任务；不建设任务树、依赖调度或自动工程化平台。

采用 LangGraph 编排和 PI 执行，保留 Python Adapter、受限容器与独立工作副本。与另一个项目统一底座意味着复用同一框架与接入方向，不要求首版先发布跨项目共享包。

用户等待不计入实际执行时间。新的失败授权不清零历史、不自动延长耗尽的工时；超时后先决定延长或拆分。

## 3. 两次本地批准

第一次同时确认目标、边界、验收标准、技术方案与正式测试命令；范围和方案分别保存，但不要求两个独立往返。第二次确认实际小场景及交付证据。

正式批准绑定任务身份和方案版本，重复或旧版本决定不能重复执行。配置保存为本次快照，运行中不热更新；更改用于下一次已批准执行。

首版不建设邮件审批、Web 身份或分布式签名服务。本地 CLI 的批准与追加决定须明确记录，不由模型猜测。未来细分审批与配置修订见 B20。

## 4. 编码、审查、测试与失败

执行顺序为实现及自验证 → 独立审查 → 程序正式测试 → 人工验收。阻断问题和测试失败回到修复；可维护性建议记录，不主动扩大范围。

开发和审查使用独立会话。测试结果来自程序运行的实际命令；首版不增加专门测试 Agent 或自动用例生成平台，用户根据明确的小场景验收。

正式测试失败只计一次，即使同轮多个用例失败；转测前实现、自验证、审查失败和普通模型／网络异常不直接消耗失败轮数，但消耗执行时间。用户验收发现明确交付失败，按同一正式候选轮次规则记录，重复反馈不重复加数。

每次授权允许最多三个失败轮次。第一次累计 1–3，追加后为 4–6，再追加为 7–9；保存授权记录、本次消耗和累计失败。当前只有研发计数，版本运维计数在 B06 实现。

结构化结果至少包含任务、结果、改动引用、真实测试依据及未解决事项。格式有效不等于测试成立。未验证、跳过、执行异常均明确报告，不伪装为通过。

## 5. 代码与执行保护

保留 main 主干、取消强制 PR。PI 在独立副本／隔离 worktree 等环境中生成候选改动，不获得实际 main 的直接写权限。验收后的 main 接回、GitHub 同步和部署由用户处理，自动归并在 B04。

执行环境隔离用于约束实现 PI 的权限；仓库准入按已有授权和质量约定执行，允许多种开发工具参与。自我迭代验收不要求专用 GitHub 写入身份、DogFood HMAC 来源签名、来源 Secret 或排他写入时间窗；普通 Git 凭据和已选定的检查流程可继续复用。自我迭代的代码交付能力与自动部署／自动自升级分别验收。

容器只开放任务工作区、必要测试资源和模型访问配置，首版不注入生产凭据。依赖与宿主设置按最小工程方案准备，不让 Agent 自动修改未批准宿主配置。

请求停止与确认停止分别记录；若工具仍运行或副作用不明，标为待核对，保留现场。不宣称已实现安全点暂停与无损续跑。进程重启可查询记录，不能自动重放中断动作；恢复控制见 B08、B12。

## 6. 复用与记录

复用 PI 原生工具、会话和自动上下文压缩。保留压缩事件与可取得旧会话；不自研压缩器，也不把全部压缩专项测试作为首次交付前置条件。

每次执行保存原始意图、配置、批准、PI 会话／可取得事件、stderr、测试命令与实际日志、diff、审查及交付报告。大输出截断或文件无法取得时如实标记，不承诺隐藏模型思维或未暴露原始请求。

使用一个本地持久化存储和文件目录；暂不建独立数据库服务、队列、档案检索平台或费用管理服务。Token／费用只保存可取得数据，未知不填零；无模型费用硬上限。模型服务用现有 PI 配置，自动备用切换后置。

## 7. 简单备份

目标仍为本机额外挂载的独立硬盘。首版对完成任务做手动备份和可读取核对，保留来源、任务及备份位置。不可把系统盘同名目录冒充独立硬盘。

逐动作备份确认、关键记录零丢失目标、原始轨迹一小时损失上限及完整故障恢复演练进入 B13；当前不承诺这些保证。没有备份挂载的开发验证明确记录该项未通过，不能声称备份已经完成。

## 8. 首版退出条件与后置项

至少一个真实小需求经过批准、PI 实现、自验证、独立审查、实际正式测试和用户验收，生成可接回 main 的 diff 与完整基本记录。具体计划见[验收计划](first-validation-plan.md)。

邮件、管理页面、附件、自动上线、自升级、复杂暂停恢复、优先级调度、完整版本体系、共享包和更多执行器均不作为首版门槛。下一步按[待实现列表](pending-requirements.md)中的实际痛点逐项选择。邮件入口的需求级交互已按所有者要求实现（见第 10 节），但它仍不是首版退出条件，也不改变本节的批准与验收规则。

## 9. 三条业务线入口（I01 已实现）

除第 2 节的 V0 单任务闭环外，CLI 已把三条业务线接到真实可调用入口（I01，见 [DogFood 执行计划](dogfood-execution-plan.md)）：

| 业务线 | CLI 入口 | 范围 |
| --- | --- | --- |
| 需求研发（A 线） | `requirement submit`／`revise`／`analyze`／`plan`／`approve`／`advance`／`accept`／`status` | 受理原文与追加版本、只读分析与澄清、任务包生成与批准绑定、按依赖推进、需求整体验收 |
| 单任务研发（B 线） | `submit`／`approve`／`grant`／`status`／`stop` | 第 2 节 V0-01–V0-11 单任务闭环及自我迭代 |
| 版本交付（C 线） | `candidate <task_id>`、`merge`、`release`、`deploy`、`rollback` | 候选产物、受控归并、发布与本机部署回滚 |

需求线任务通过 `RequirementTaskRunner` 映射为稳定身份的单任务记录，复用 B 线的实现／独立审查／正式测试／人工验收与 C 线的归并／发布；需求文本一经追加，旧任务包与旧批准失效；全部任务交付后仍需所有者整体验收，单个任务通过不等于需求整体验收。

已知边界：容器隔离未接入（见[架构说明第 5 节](architecture.md)与[状态记录第 6 节](status.md)）；真实模型下完整「需求 → 任务 → 交付 → 部署」链条尚待 G02 验收，**模拟场景与系统测试不能作为完整产品通过的证据**。

## 10. 邮箱交互入口（2026-10-19，B02 需求级部分）

所有者要求邮箱成为与 CLI 同等的交互入口。已实现的 `forgeloop mail interact --once` 复用同一套需求、任务包、批准与执行记录，不另建业务状态：

- 入向：白名单发件人可提交新需求，或回复既有通知执行 `status`／`revise`／`analyze`／`plan`／`approve <任务包版本>`／`advance`／`accept`／`help`；未识别命令的回复按需求修订内容追加。
- 出向：每封命令邮件回信结果与当前状态；回信保留 `In-Reply-To`／`References` 线程，后续回复可据此关联需求。
- 约束：批准绑定最新任务包与需求版本；**2026-10-21 所有者决定支持自然语言批准，一步到位**——封闭短语（批准／同意／可以／没问题／lgtm 等，可带版本）由确定性规则识别，无版本时绑定最新任务包，歧义、过期、多目标一律不执行；模型不直接写批准，批准来源记为 `email-natural-language:<Message-ID>`。验收自然语言同样一步执行。重复邮件按入向 Message-ID 幂等；发送失败只重发同一封回信；进程中断的现场标记不确定、不盲目重放。
- 常驻方式：**并入 `serve`**（`--mail`，默认 60 秒轮询）；回复任意通知邮件即延续同一需求线程，不再依赖单独 cron 单次入口。
- 真实邮箱验证（2026-10-19，QQ 邮箱）：受理新需求、`status` 查询与所有者从个人地址回复 `help` 均真实收发成功；暴露两点部署要求——白名单必须登记全部实际发件地址；部分邮箱会重写出向 `Message-ID`，线程关联因此依赖主题中的 `req-…`（详见[状态记录](status.md)）。
- 未实现：任务级验收／追加授权命令、主动进度与成果通知、DKIM/SPF 等来源密码学校验（当前为发件地址白名单）；这些仍留在[待实现列表](pending-requirements.md) B02。

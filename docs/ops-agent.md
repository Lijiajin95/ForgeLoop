# 运维 Agent（首版实现）

编写日期：2026-10-29。本文描述当前 TypeScript 实现如何落实[产品方案 §8.3](product.md#83-运维职责与简化要求)的首版运维边界，
并明确哪些判断由程序强制、哪些仍待验证。对象是否已交付以[状态记录](status.md)为准，不以本文存在为完成证据。

## 1. 范围

首版只处理 **DogFood 实际需要的运行状态**：已登记资源的状态检查、失败事件、只读诊断、
少量预先登记的恢复动作、恢复复核，以及未恢复时的关联修复需求。

不做：通用运维平台、任意 Shell 执行、自动扩容／迁移、多账户／SSH／远程主机、告警平台接入、
自动发布、对未知系统的接管。

资源、检查与动作都来自插件配置中的 `ops` 目录；目录在装载时校验，非法配置直接失败。
正常巡检通过不产生事件，也不进入人工介入统计的分母。

## 2. 角色分工

| 角色 | 能做什么 | 不能做什么 |
| --- | --- | --- |
| 运维 Agent（模型，`role: ops`） | 读取程序提供的检查输出与登记目录，输出业务影响、事实、推断、一个已登记动作建议 | 没有工具；不能执行检查或动作、不能改文件、不能批准、不能验收、不能编造动作或参数 |
| 主控（`runtime/ops.ts`） | 运行检查与动作、校验参数、判定恢复、写记录与证据、生成修复需求 | 不能凭模型自述认定恢复；不能执行目录外命令；不能在结果未知时自动重放 |
| 恢复检查（登记 argv） | 处置后复核服务是否恢复 | 退出码 0 之外不构成通过；超时不算通过 |
| 需求流程 | 承接关联修复需求，按既有分析、任务包、批准、验证与验收推进 | 创建修复需求不等于已修复，也不等于事件已恢复 |
| 所有者 | 批准／拒绝非自动处置、核对未知结果、关闭事件、要求生成修复需求 | 页面按钮不能伪造自动授权；等待超时不是批准 |

## 3. 事件生命周期

```text
检查失败
  └─ 归并到同一签名的处理中事件，或新开 open
       └─ 运维 Agent 诊断 ── 无动作/参数非法/要求人工 → awaiting_decision
       │                    └─ 目录自动授权 → diagnosed → 主控执行 → recovering
       │                                                        ├─ 恢复检查通过 → recovered
       │                                                        ├─ 检查未通过   → unresolved
       │                                                        └─ 超时/宿主中断 → unknown（需核对）
       └─ 所有者决定：批准 → 执行；拒绝 → unresolved
```

- **签名**：`资源/检查/退出码/首条输出摘要`。同一故障的重复告警归并为一个事件，观测次数保留；
  输出首行变化视为不同签名。终态事件不吸收新告警，复发会新开事件。
- **未知**：动作超时或宿主中断时动作记录标为 `unknown`，事件同时标为结果未知；不自动重放。
  所有者核对现场后才能转为未解决或关闭。
- **一次处置**：首版每个事件最多执行一次登记动作；失败后不自动尝试第二种动作，避免失败循环。
- **恢复与永久修复分离**：`recovered` 只表示恢复检查通过；`fix_required` 的诊断会生成关联需求，
  其修复、验证与验收仍走正常需求流程。

## 4. 配置

```yaml
ops:
  enabled: true
  intervalSeconds: 300          # 巡检周期，最小 30 秒
  resources:
    - id: web
      kind: app                 # app | database | cache | queue | host | other
      label: 天工页面
  checks:
    - id: web-health
      resourceId: web
      command: ["node", "-e", "fetch('http://127.0.0.1:3080/').then(r=>process.exit(r.ok?0:1)).catch(()=>process.exit(1))"]
      timeoutSeconds: 20
      severity: major            # critical | major | minor
  actions:
    - id: restart-web
      resourceId: web
      command: ["node", "scripts/restart-web.mjs", "{mode}"]
      params:
        - name: mode
          values: [graceful, force]   # 只允许枚举值；模型不能提交目录外的值
      timeoutSeconds: 60
      auto: true                 # 目录预先授权自动执行；false 时必须所有者批准
      verifyCheckId: web-health  # 恢复复核；省略时要求资源只有一个检查
```

约束（装载期强制，见 `src/domain/ops.ts` 与 `src/config.ts`）：

- 资源、检查、动作身份唯一；检查与动作必须引用已登记资源。
- 检查与动作只接受 argv 数组，不接受 Shell 字符串；超时为正数。
- 动作命令中的 `{参数}` 必须对应已声明参数；参数只能取 `values` 中的值；声明的参数必须在命令中使用。
- 恢复检查必须属于同一资源；`enabled: true` 时至少登记一个检查。
- 未启用的目录同样做静态校验，非法值不会在运行期被静默忽略。

## 5. 授权与执行

自动处置必须同时满足：目录标记 `auto: true`、动作属于事件资源、动作就是诊断提出的动作、
参数通过目录校验、诊断未要求人工决定。任一条件不成立都停在 `awaiting_decision`，由所有者决定。

- 模型不能把未登记动作变成自动执行；运行时在执行前重新做一次授权判定。
- 动作执行前先写 `running` 意图记录（动作身份、参数、授权来源），再启动子进程；退出后才写结果。
- 授权来源可回查：自动处置为 `ops-action:auto:<动作>`，人工决定为
  `owner:<所有者>:<入口来源>`。
- 页面/模型工具没有执行动作的入口；所有者批准只改变决定记录，实际执行由协调器完成。

## 6. 记录与证据

| 表 | 内容 |
| --- | --- |
| `ops_events` | 事件身份、签名、严重度、状态、影响、诊断、决定、人工介入、结果未知、修复需求 |
| `ops_observations` | 按序追加的检查、诊断、授权、动作、恢复复核、决定、关闭观测 |
| `ops_action_attempts` | 处置意图与结果：动作身份、参数、授权来源、退出码、证据路径、未知标记 |

证据目录：`<recordsRoot>/projects/<project>/ops/<事件>/`
保存 `check-<n>.log`、`diagnosis-<n>.json(l)`、`action-<n>.log`、`recovery-<n>.log`。
检查输出原样保存（最多截断 256 KiB，超出时保留截断标记），当前未做敏感信息脱敏；
材料保留策略仍是待决项。

## 7. 入口

- 模型工具 `forgeloop_ops`：只读事件、诊断、处置记录与统计；可传 `event_id`。
- 认证 Web 端点（与天工工作台同一路由 `/api/forgeloop/board`）：
  `ops`、`ops-detail`、`ops-decide`、`ops-confirm-unknown`、`ops-close`、`ops-request-fix`。
  读端点只取记录；写端点使用本机 owner，模型工具不能调用。
- 天工工作台新增“运维”视图：事件列表、严重度/状态、影响、诊断事实与推断、处置记录、证据路径，
  以及批准、拒绝、核对未知、关闭、生成修复需求。页面不另存业务状态。
- 协调器在持有单消费者锁时按 `pollSeconds` 唤醒巡检；宿主启动时把上次未收口的动作标为 unknown。

## 8. 统计口径

`opsStats` 按产品 §12.2 计算：独立事件数为分母；诊断后发生批准/拒绝、核对未知、关闭或
外部接管的事件计为人工介入；正常巡检不产生事件。同时报告已恢复、未解决、未知、待决定、
关联修复需求数与平均恢复时长。当前只有总量，不提供观察窗口、样本充分性或 M2 达标判定。

## 9. 首版限制（如实保留）

- 不抢占正在执行的研发任务；只按严重度排序处理运维事件。“严重故障优先”尚无进程级抢占。
- 每个事件最多一次处置；没有自动的第二种动作、自动重试或失败循环归并之外的策略。
- 恢复检查只看退出码与超时，不检查业务指标；检查本身是否只读由登记配置保证，运行时无法证明。
- 动作在宿主账户与项目目录下执行，没有 OS/容器隔离；拥有插件配置的人可以登记任意命令。
- 结果未知需要人工核对；当前没有自动读取外部状态收口的适配器。
- 修复需求进入正常需求流程，不自动批准；恢复与修复分别收口。
- 未接入告警平台、日志平台、邮件/IM；检查输出是唯一自动证据来源。
- 真实 DogFood 的线上事件尚未跑通；本批验证均为仓库行为测试与本地命令，见状态记录。

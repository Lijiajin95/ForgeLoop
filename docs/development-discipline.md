# ForgeLoop 研发纪律

复刻自 EvidHist 研发纪律，适配 ForgeLoop 的 CLI 自动研发工具定位。适用于人工与 AI 辅助开发：以当前用户需求、已确认方案和可核查的完成证据约束实现，保持个人工具的简单性、改动范围与关键行为可靠性。可靠性门槛与检查入口见[工程可靠性方案](engineering-reliability.md)。

## 纪律一：简单优先，抵抗过度设计

先写最简单、显而易见正确的版本。新增框架、策略、配置层或抽象，都需要说明它解决了什么当前问题，以及维护成本为何值得。

- 先满足当前需求，使用能够直接表达行为的实现。
- 写完自问：能否减少不必要的逻辑？这层抽象是否值得？
- 三行重复代码，好过一个过早的抽象；重复确实形成稳定模式或维护负担后再考虑提取。
- 只为当前需求写，不为臆想中的未来需求过度设计。首版范围以[首版需求](product-requirements.md)为准，不因可靠性骨架的存在提前建设插件注册、多执行器或共享包。

审阅时检查一次性操作是否被包装成通用框架，小段逻辑是否引入了缺乏实际用途的策略体系，以及新增扩展点是否真的有当前使用者（保留执行器 Seam 不等于实现插件体系）。能用清楚的函数和数据结构解决的问题，应保持这种直接表达。

“更少行”指减少不必要的逻辑和结构。必要的注释、错误处理、边界校验与可读步骤应保留；不通过压缩语句或拆出大量琐碎函数迎合行数门槛。结构度量及例外政策见[工程可靠性方案](engineering-reliability.md#4-结构门槛统计口径与例外)。

## 纪律二：范围纪律，只碰该碰的

开发方案必须列出准许修改和新增的文件，以及每个改动的目的。开发 AI 必须且只能修改方案列出的文件，人工开发遵循同样的范围约束。这与 ForgeLoop 自身对 PI 的[执行边界](architecture.md#5-容器与-main)是同一条原则：授权范围内工作，范围外不碰。

实现中发现范围外的命名、组织、性能或其他问题，采用**“发现但不碰”**机制：记录问题与位置，说明潜在影响和建议，保留给后续任务处理。不要顺手修改相邻代码、执行全仓格式修复或混入无关重构。

确需扩大范围才能完成需求时，应先说明原因并将变更提交到方案评审，依据更新后已确认的方案继续。不能由开发 AI 自行扩大文件清单来代替范围确认。

变更摘要固定保留以下内容：

| 项目 | 应记录的内容 |
| --- | --- |
| 计划范围 | 准许修改/新增的文件和对应目的 |
| 实际改动 | 实际文件、行为变化及与方案的对应关系 |
| 验证结果 | 已运行的检查、结果和未完成项 |
| 发现但不碰 | 范围外问题的位置、影响和建议；没有发现时注明“无” |

收尾时核对计划文件清单与实际改动，识别范围外修改。保留用户及其他 Agent 的既有工作，不能为清理自己的任务而回退、覆盖或删除无关改动。

## 纪律三：关键路径先写测试，再实现

核心业务逻辑中新增的判断分支、关键计算、状态流转和幂等逻辑，必须按以下顺序推进：

1. 根据需求写一个会失败的行为测试，使用明确且独立的预期结果。
2. 运行测试，确认失败指向目标行为或尚未实现的公共接口。
3. 编写最小实现，使该测试通过。
4. 补齐必要边界和反例，再在测试保护下改善结构。

ForgeLoop 的典型关键路径：失败轮次计数与累计不清零、追加授权额度边界（1–3 / 4–6 / 7–9）、批准绑定任务身份与方案版本（旧版本决定不能重复执行）、时间限额与用户等待不计入执行时间、请求停止与确认停止的区分、中断标记与禁止盲目重放、任务与记录的回查。测试通过公共接口观察结果，避免断言私有方法调用过程或复制实现逻辑计算预期值。

不是所有改动都需要先写测试。文档、格式和低风险简单改动按影响选择验证方式；核心行为不能因实现短、编译通过或类型检查通过而省略测试先行。缺依赖、环境权限或测试配置错误属于环境/工程问题，不能当作目标行为的失败证据。

这条纪律的目的，是把验收标准固化成可运行的测试。编译、静态类型和结构校验只能提供各自范围内的证据，单元及流程测试用于检查行为。测试通过表示所覆盖场景满足其预期；预期本身、材料依据和未覆盖情况仍需审阅。ForgeLoop 的“真实测试不能只读 Agent 声称通过”（V0-05）与这条纪律同源。

错误样例加入回归用例，记录测试的初始失败与实现后的通过结果。覆盖率、属性测试、变异测试、真实集成和 CLI 端到端测试按风险补充，不能以单一数字代替正确性判断。详细方法见[工程可靠性方案](engineering-reliability.md#3-分层测试策略)。

## 审查与交付时怎样落实

审阅者核对三个问题：实现是否以最简单的方式满足当前需求；实际修改是否全部属于已确认范围；关键行为是否具有先失败、后通过的测试证据。

交付说明记录用户可观察的行为变化、实际文件、验证结果和“发现但不碰”。必要抽象说明当前用途，未运行检查说明原因，范围变更说明方案依据。提交时间、消息要求遵循[贡献规范](../CONTRIBUTING.md)。

## 用户提供的实践背景

用户提供的材料报告（来自 EvidHist 的实践陈述）：注入“简单优先”约束后，架构过度复杂类审查问题的出现频次下降约一半；约 49 条需求（约 17%）在自动开发阶段经历了超过一轮代码审查与修复，并描述了“编译通过但单测失败”较早暴露逻辑问题的情况。

这些数字来自用户提供的实践陈述，材料未附样本明细、统计窗口及完整比较口径。本文保留其作为纪律的实践背景，**不将其记为 ForgeLoop 的测量结果或预期收益保证**。ForgeLoop 后续若统计效果，应记录需求分母、问题分类、执行版本、审阅与修复轮次，以及运行证据。

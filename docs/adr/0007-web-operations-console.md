# ADR 0007：Web 作为操作管理界面（前台 `web` / 常驻 `serve`）

- 状态：已接受（2026-10-22，所有者决定）
- 取代：`docs/resident-service-plan.md` 的 D1 中「`forgeloop web` 只读」部分
- 相关：[架构说明](../architecture.md)、[产品需求 §11](../product-requirements.md)、[常驻服务与页面操作入口方案](../history/resident-service-plan.md)

## 背景

仓库已有两种浏览器入口：`forgeloop web`（前台、只读状态页）与 `forgeloop serve`（常驻、页面写入口 + 会话面板）。所有者明确：**Web 不再是只读界面，定位改为操作管理界面**；需要从 Web 会话界面进行对话，并对需求做增删改查。

## 决定

1. **Web 是一套操作管理界面，不是只读展示层。** 默认落在会话；提供按项目建会话与对话、需求提交/查看/修订/取消/分析/规划/批准/推进/验收/停止，以及项目档案维护。
2. **`forgeloop web` 是前台控制台**：监听回环、Ctrl+C 停止、**不自动接续**；只执行人工点下的显式请求。
3. **`forgeloop serve` 是同一套页面与写入口的常驻版本**：另承担 worker 心跳、`auto_advance`、邮箱轮询与受控热升级。两者共用一个 HTTP 处理器、面板与三道闸门，避免两套业务状态。
4. **一个进程服务一个已登记项目**（`--project`；缺省取唯一项目，多项目不指定即拒绝）。前台与常驻同口径。
5. **需求「删除」= 取消（软删除）**：终态 `cancelled`，身份、版本、批准、交付与现场原样保留，可回查；不做权威记录物理删除。
6. **修订 = 追加版本**：历史原文不覆盖；版本行记录 `revised_by` / `source` 审计归属。
7. **分析/规划与推进同属受理型操作**：先持久化到项目库 `service_requests`（`action` 区分），返回 202，由下一次心跳消费；同需求同动作幂等、不同动作拒绝。重启后请求仍可见。
8. **执行档案合并**：worker 可执行项目 = 手写 `config/service.toml` 项目 + 页面维护的 `config/projects.toml` 项目；同名冲突拒绝。页面创建的项目因此可被 Web 直接分析、规划和推进。

## 后果

- `forgeloop web` 成为破坏性变更：不再是无项目可运行的只读页；需要已登记项目，并默认落在会话。
- `web` 与 `serve` 的生命周期分工不变：自动接续、邮箱、热升级仍只在 `serve`；`web` 固定 `auto_advance=false`。
- 写入口仍只在本机回环开放，使用一次性页面令牌、同源校验与请求体上限；**没有**登录、多用户或远程访问。
- 归并/发布/部署仍不在 Web 提供；交付类动作继续走 CLI。
- 记录层只增加 `service_requests.action` 与 `requirement_versions.revised_by`/`source` 两组列，不新建业务状态表。

## 被否备选

- **只升级 `serve` 的页面，`web` 保持只读**：不能满足「Web 不再是只读界面」的明确要求，且两个入口的定位继续分裂。
- **把 `web` 改成常驻**：生命周期与 `serve` 重叠，自动接续/邮箱/升级会让前台交互进程承担后台职责；D1 的原判断仍成立。
- **物理删除需求**：会破坏批准、交付与审计链；取消已能表达「不再推进」。
- **让分析/规划同步阻塞 HTTP**：模型调用分钟级，请求会超时；沿用推进的持久受理与心跳执行。

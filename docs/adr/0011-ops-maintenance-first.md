# ADR 0011：运维模块维护优先，研发转向核心交付闭环

- 状态：已接受（2026-11-06，所有者决定）
- 依据：[统一方案 §8.3](../product.md#83-运维职责与简化要求)、[§11.3](../product.md#113-m1-通过目标所有者设定2026-11-05)、[§14.2](../product.md#142-尚需具体化的实施与验收事项)
- 接续：[ADR 0010](0010-remove-command-surface-legacy-compat-and-commit-policy.md)；实际状态与证据见[状态记录 §178](../status.md#178-运维模块进入维护阶段所有者决定2026-11-06)

## 背景

ForgeLoop 当前主要是个人使用的 DSH 插件和一个尚未上线的网站。没有稳定运行、持续产生真实反馈的
线上目标，日常运维事件与人为核对量都不足以支撑继续扩建运维能力。

已有实现覆盖本地安装与升级核对、运行身份查询、登记巡检、只读日志、事件与证据记录，以及已有
授权范围内的恢复与复核。M1-3 的真实事件到修复仍为“部分达成”：临时恢复与诊断已有证据，
永久修复的部署、原事件复核通过与事件关闭仍待验证（状态 §160、§174、§176）。继续投入外部监控
平台、运维 Agent 增强或通用运维平台，会先增加维护面而不是解决当前交付闭环。

此前的工具选型讨论（Gatus、Prometheus、goss 等）没有形成接入决定，也没有安装或配置任何外部工具；
这些讨论只保留为将来评估的参考。

## 决定

1. **运维模块进入维护阶段**。保留现有能力，包括本地安装与升级核对、运行身份查询、登记巡检、
   只读日志、事件和证据记录，以及已有授权范围内的恢复与复核。维护优先处理直接阻塞实际使用或
   现有交付的问题。
2. **暂缓外部工具与平台扩展**。暂缓接入 Prometheus、Grafana、OpenTelemetry、SigNoz、
   Alertmanager 等外部工具；暂缓增强运维 Agent、扩展通用运维平台和主动开展运维闭环复跑。
3. **研发优先核心交付闭环**。当前优先用 ForgeLoop 自己的真实需求跑顺
   “需求 → 实现 → 验证 → 可安装交付”，通过持续使用发现问题。网站的功能规划由其所属项目单独维护。
4. **恢复投入条件**。出现稳定使用的运行目标、反复出现的同类故障，或重复且费时的人工核对时，
   由所有者选定一个具体场景，再评估恢复哪项运维研发。评估应写清目标、已有证据、当前痛点与
   可观察的验收结果。

## 影响

- M1 的验收条件、整体判定方式和既有授权边界不变；M1-3 仍为“部分达成”，不因本决定改写为通过，
  也不补造永久修复或事件关闭证据。
- 运维相关工程只做维护性修复；不新增外部监控/日志/告警平台接入，不扩大动作目录，不改变
  自动授权、停止或恢复判据。
- 现有记录、证据和已开始的复跑按实际状态保留；此前的“重跑运维闭环、M1-5 真实崩机、M1-6 复算”
  等后续排期调整，不再作为当前优先级。
- 研发资源集中到真实需求的分析、准入、研发、验证、提交、候选构建与可安装交付；上线核对和
  部署接口继续按既有规则使用，不因维护决定删除或放宽。
- 本次只改文档，不涉及代码、配置、版本、安装或生产部署。

## 恢复投入的评估条件

满足下列任一情况时，由所有者选定一个具体场景，再评估恢复对应运维研发：

1. 出现稳定使用的运行目标（持续运行、有真实使用反馈）。
2. 反复出现同一类故障，已有事件记录显示需要系统化处置。
3. 出现重复且费时的人工核对，已经影响交付节奏。

评估至少写清：目标、已有证据、当前痛点、可观察的验收结果。未满足前，不启动新的运维平台接入、
Agent 增强或主动闭环复跑。

# 提交时间限制改为可选的本机策略：仓库只发布模板

## 背景

提交时间限制此前与仓库绑定：`config/commit-policy.toml` 随版本分发，pre-commit／commit-msg 与 CI 的 `commit-policy` 作业都读它。这套模型在 2026-10-13 暴露了两个结构性问题（[工程可靠性方案](../engineering-reliability.md)第 22、23 节）：

- **规则随仓库分发，等于把一台机器的作息强加给每个克隆与每次 CI 运行**，而这些机器不在同一时区、也没有同一批授权。
- **本地检查与 CI 审计读同一份仓库内配置**。当这份配置被临时放宽来表达"授权"时（第 22 节的 S1–S3 批次），两个检查层都失去发现能力——放宽本身不会被任何一层看见；授权范围因此没有边界，只能靠人工记录兜底。

第 23 节加的授权窄口（09:00–09:55、10:00 硬上限）修补了授权的边界，但没有改变"仓库内配置既是规则又是例外载体"这个根因。

## 决策

1. **仓库只发布模板** `config/commit-policy.template.toml`；**实际生效的配置不入库**，只从本机按固定优先级二选一读取：`.cache/forgeloop/commit-policy.toml`（仓库内缓存，已被 `.gitignore` 忽略）优先，其次 `~/.config/forgeloop/commit-policy.toml`（用户级）。两份不合并。
2. **没有生效配置即不执行提交时间禁止**：判定记为 `policy_absent`，输出显式标注 `NOT enforced`，退出码 0。这是所有者明确选择的"可选强制"，不是"检查通过"。
3. **异常一律失败关闭**：配置存在而损坏、年历目录缺失、或旧路径 `commit-policy.local.toml` 未迁移 → 拒绝并说明原因，不静默放行。
4. **消息头 Conventional Commits 校验与配置无关，始终生效**：它是消息规范，不是时间规则。
5. **删除"仓库默认 + 本地覆盖"的键级合并、覆盖键白名单与生效来源枚举**：单一来源下没有可合并的对象，保留它们只会制造"看起来还有一层兜底"的错觉。
6. **授权硬上限（终点 ≤ 10:00）与"授权窗口必须落在某段禁止窗口内"留在领域层**，任何本机配置都改不掉。

## 后果

- 本机（所有者 macOS 机器）已安装 `.cache/forgeloop/commit-policy.toml`，规则值与授权登记从原仓库配置原样迁移，本机行为不变。
- **未安装配置的机器（包括未注入配置的 CI）上，提交时间规则未落实**：这必须如实标记，不能声称规则已生效。需要服务端强制时，须在 CI 步骤中另行注入配置——**当前未实现**，属缺口。
- 生效配置位于被忽略的缓存目录，**没有版本历史**：该文件丢失即静默失去强制（现在至少会打印 `policy_absent`／NOT enforced，而不是无声通过）。
- 第 22 节的事故模式（放宽仓库内配置以表达授权）在结构上不再存在：仓库里没有可放宽的规则文件；本机改动只影响本机，且不会改变 CI 对历史提交的判定依据。
- 代价：跨机器的一致强制需要额外机制（CI 注入或服务端准入），本次未实现；机器级配置的正确性只能靠 `--validate-config` 与审计输出核对。

## 备选方案

- **保留仓库默认配置，只把授权变成配置项**：仍然把一台机器的作息分发给所有克隆，第 22 节的放宽失败模式依旧存在。否决。
- **仓库配置只读 + 授权走独立签名清单**：引入签名与密钥管理，收益与本项目当前规模不匹配；且未解决"规则随仓库分发"本身。否决。
- **把时间检查改为服务端必需状态检查**：方向正确但需要 CI 能拿到配置（注入或托管），本次范围内未实现，作为缺口记录而非声称已完成。

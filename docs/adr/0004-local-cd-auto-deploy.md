# ADR 0004：本机托管与自动部署（CD）

- **状态**：**已接受**（所有者 2026-10-18 三项决定，见下），**尚未实现**；实现前不得把本文当作已生效规则
- **背景**：所有者要求支持 CD 与自动部署，并明确**部署目标就是本机**。当前实现已经具备受控部署器：`forgeloop release` 产出 wheel 与发布回执（含产物 `sha256`），`forgeloop deploy` 把产物装进版本目录并**原子激活**（幂等 noop、记录上一版本），`forgeloop rollback` 可回到上一版本，规则集中在 `domain/deploy.py`。缺的是**触发**（谁在什么时候决定装新版）与**闭环**（健康检查、回执、失败回滚），以及主机侧的一次性接入。
- **与"受限环境"的关系**：目标在本机时不需要跨机传输，也不需要 Agent 接触生产凭据；受限的只是**写工作区外路径**（systemd unit、部署前缀）——这属于一次性 bootstrap，由所有者执行或显式放行。

## 决定的语义（提案）

**CD = 已授权发布 + 本机自动安装 + 健康检查 + 回执 + 失败自动回滚**，串在既有常驻服务里：

1. `release` 产出并登记发布（产物身份 + 回执），这是**人类决定**的产物（沿用既有就绪判定）。
2. 常驻 worker 增加一个**受控部署环节**：每拍只读筛选「存在已授权发布 且 本机激活版本落后」→ 满足时执行既有 `forgeloop deploy`（规则、幂等、原子激活全部复用，不另写一套）→ 健康检查 → 写回执 → **失败自动 `rollback` 到上一版本**。
3. 开关 **`auto_deploy` 默认 `false`**（与 `auto_advance` 同口径）：关闭时 worker **只报告**"有新版本待部署"，页面/CLI 可人工部署；打开时才自动装。开启是一次**所有者决定**（记录 by/reason/时间）。

## 硬性前提（机器强制，fail-closed，无 `--force`）

1. 目标产物必须**已发布且通过既有就绪判定**（`check_release_readiness`／`check_deploy_readiness`），未验收、未发布、材料漂移一律拒绝。
2. 产物 `sha256` 必须与发布回执一致（同一产物身份，不接受"重新构建一份"）。
3. 部署动作与常驻服务**同机同前缀**：`deploy` 的 prefix 必须等于常驻服务当前运行版本的 prefix（否则拒绝，避免"部署了但跑的还是旧的"）。
4. 同一时刻只允许一个部署动作（复用既有互斥；与任务执行串行）。
5. 健康检查不通过 → **自动回滚**并把失败原因与两次版本号写入记录；回滚失败则停在明确状态并要求人工介入（不得留下半激活前缀）。
6. `auto_deploy` 关闭时不得安装任何产物（只读报告）。

## 主机侧一次性 bootstrap（所有者执行，或在放行后由 Agent 执行）

1. 部署前缀：`~/.local/share/forgeloop`（`releases/<version>` + `current` 符号链接）。
2. 首次部署：`forgeloop deploy --artifact <wheel> --prefix ~/.local/share/forgeloop`。
3. 常驻服务 unit：`~/.config/systemd/user/forgeloop.service`，`ExecStart` 指向 `<prefix>/current/bin/forgeloop serve`（`systemctl --user enable --now forgeloop`）。
4. 需要自动部署时：在 `service.toml` 里 `auto_deploy = true` 并登记决定。
5. 验收按 [常驻服务与邮件入口的真实场景验收方案](../history/resident-service-acceptance.md) 的 A/B 组执行；本 ADR 的验收另加 C 组（见下）。

## 验收条件（实现时）

- **拒绝侧（逐条）**：未发布产物；未验收/材料漂移；`sha256` 不符；prefix 与运行版本不一致；已有部署在运行；`auto_deploy=false` 时尝试安装。
- **放行侧**：开启 `auto_deploy` 后，本机自动装上新版本并原子激活；`/api/service` 显示新版本号与部署回执；**健康检查失败时自动回滚**且记录两次版本；重复部署同一版本为 noop。
- **真机 C 组**：① 本机自动部署一次成功并可见回执；② 故意投放一个健康检查必然失败的产物 → 自动回滚且服务仍可用；③ 关闭 `auto_deploy` → 只报告不安装。
- **契约与文档**：CLI 契约（如新增输出字段）、`docs/architecture.md`（worker 职责与部署链路）、`docs/deployment.md`（主机接入章节）同批更新；`make check` 通过。

## 边界（不做）

- **不做跨机部署**：本 ADR 只覆盖本机；远端目标沿用 git pull 模型另议（见 ADR 0005 若需要）。
- **不自动发布**：`release` 仍是人类决定；`auto_deploy` 只影响"已授权发布是否自动安装"。
- **不动生产凭据**：本机部署不需要新凭据。
- **不做灰度/多实例**：单机单实例，版本目录 + 原子激活已能保证"要么新版、要么旧版"。

## 所有者决定（2026-10-18，冻结语义）

1. **发布前需确认**：**安装任何新版本之前都必须有一次人工确认**，不做无人确认的自动安装。因此原设想的
   `auto_deploy = true` 全自动口径**作废**——改为**每版本一次性部署批准**：批准记录谁、何时、理由、目标版本与
   产物 `sha256`；未获批准的版本，常驻 worker **只报告不安装**。批准与 `release`（产出并登记发布）分开，
   两者都不能被绕过。
2. **保留健康检查**：安装后必须健康检查；不通过 → **自动回滚**并记录两次版本号，回滚失败停在明确状态
   （不得留下半激活前缀）。
3. **需要邮件通知**：部署结果（成功 / 自动回滚 / 失败）必须发邮件通知，复用既有 best-effort 回执通道
   （发送失败只记录，不影响部署事实与回滚结论）。

### 由决定 1 修正后的链路

`release`（人类决定，产出 wheel + 回执 + 产物 sha256）→ 常驻 worker **只读检测**「有已发布但未安装的版本」→
页面/邮件提示"待确认部署"→ **人工确认**（落库批准）→ 执行既有 `deploy`（规则、幂等、原子激活复用）→ 健康检查 →
写回执 + **邮件通知** → 失败则自动 `rollback` + 邮件通知。

即：**自动化的是"检测、执行、验证、回执、回滚"，不是"决定"**。

### 健康检查判据（决定 2 的落地）

`<prefix>/current/bin/forgeloop serve --once --json` 退出码 0 且输出可解析为 JSON；可选再加 `GET /api/service`。
不通过即视为部署失败并立即回滚。

### 邮件通知（决定 3 的落地）

复用邮件线 best-effort 回执：成功/回滚/失败各一封（版本号、产物 sha256、健康检查结论、回滚目标版本）；
发送失败只记 `mail_deliveries` 状态。收件人取邮件配置的 `recipient`。

## 实现方案（下一轮直接执行）

| 文件 | 改动 |
| --- | --- |
| `records/store.py` | 部署批准记录（版本、产物 sha256、批准人、来源、时间、理由），与既有批准同库；校验版本与产物身份 |
| `domain/deploy.py` | 判据补一条：**未获部署批准一律拒绝**（与既有规则并列，不放松任何一条） |
| `cli/deploy.py` | `deploy approve`（须 `--by`/`--reason`）；`deploy` 校验批准并写回执；输出新增批准与邮件通知字段 |
| `graph/worker.py` | 只读检测"待部署版本"入状态（页面与 `/api/service` 可见）；**不自动安装**；领取已批准版本后执行（互斥、与任务执行串行） |
| `cli/web.py`、`frontend/` | 页面新增"待确认部署"段与"确认部署"入口（沿用令牌/同源/体量三道闸门） |
| 邮件 | 部署结果通知（复用发送通道与 best-effort 语义） |
| 契约与文档 | CLI 契约重新导出；`docs/architecture.md`（worker 职责、部署链路、批准表）；`docs/deployment.md` 主机接入；`docs/status.md` 实测记录 |

**测试矩阵**：拒绝侧——未发布、未批准、批准版本与产物不符、sha 不符、prefix 与运行版本不一致、并发部署、批准过期；
放行侧——批准后安装并原子激活、健康检查通过、回执可见、重复部署 noop、**健康检查失败自动回滚**、回滚失败停在明确状态、
部署结果邮件已发（本地假服务器）、邮件发送失败不影响部署结论。

**真机 C 组**：① 人工确认后本机部署成功且回执可见、收到通知邮件；② 健康检查必失败的产物 → 自动回滚、服务仍可用、收到回滚邮件；③ 未确认的版本**不得安装**。

# ADR 0003：按新基线刷新同一任务（受控操作）

- **状态**：**已接受**（所有者 2026-10-18）。其中「任务↔commit 累积关联」部分**已实现并验证**（见下节）；「按新基线刷新」操作**尚未实现**，且经关联模型澄清后，其适用范围收窄为 B 类（基线 commit 已不可解析／工作副本丢失）。
- **背景**：邮件任务 `mail-ports` 在基线 `e22945a` 上完成并通过验收前的全部自动环节，停在验收门。此后主干前进（本批次提交后为 `d6a7bed`），交付基线不再等于主干 → `forgeloop merge` 按漂移规则**拒绝**落地；手工合并可行但属于"在旧基线上验过的交付落到新代码"，验收口径不成立。
- **问题**：所有者 2026-10-18 选择"刷新任务"路线，但**当前实现没有该入口**。实测：`requirement retry --task … --node dev --baseline d6a7bed` 被确定性校验拒绝——"当前 awaiting_acceptance，只有 interrupted 或存在 halted_reason 的任务可人工续跑""检查点没有 halted_reason，无需指定重入节点 dev"。该拒绝是**设计如此**（缺陷 #24 加固的纪律：点名重入只用于检查点自身无法归因的陈旧中断）。

## 决定的语义（提案）

新增一个**受控**操作：`requirement refresh`。

- **同一任务身份、同一任务包版本、新基线**：任务 `task_id` 与 `plan_version` 不变，只把该任务的**批准基线**从旧提交换成新提交；批准本身（所有人、时间、任务包版本）不被改写。
- **重跑该任务的业务节点**：`dev → review → test`，由机制按正常链条执行；产生的新候选 diff **对新基线计算**，因此落地时漂移判定成立。
- **旧现场封存而非删除**：旧工作副本改名为 `workspace.baseline-<旧提交>`、旧候选另存 `candidate.baseline-<旧提交>.diff`，与新现场并存可回查。
- **必须留下的人工决定**：谁、何时、理由、旧基线、新基线、目标任务与任务包版本，一条落库记录；缺任一项一律拒绝。

## 前置条件（机器强制，fail-closed，不提供 `--force`）

1. 任务存在且属于该需求；`plan_version` 与当前有效批准一致（批准过期即拒绝，不得借刷新绕过重新批准）。
2. 任务处于**决策边界**：`awaiting_acceptance`（已产出候选与测试证据并停在人工门）或 `delivered` 之前的中断态；`interrupted` 且无法归因的情形仍归既有 `retry`，不走本操作。
3. **无未核对动作、无残留槽位**：与 R4 启动核对、执行器 B03 判定同一口径（复用同一判定函数，避免第二套标准）。
4. 检查点身份可信（任务／任务包版本匹配、未损坏）。
5. 新基线必须是该项目仓库里的真实提交，且**不等于**当前记录基线（无变化即拒绝，避免空转产生假记录）。
6. 项目无正在运行的推进（同需求互斥、同项目交付串行的判定复用既有实现）。
7. 需求未被停止、未处于终态。

## 不做（边界）

- **不放行验收**：刷新不产生任何批准记录，验收仍需人工 `approve --stage acceptance`。
- **不清失败累计、不改工时与授权额度**：刷新不是失败修复，不重置任何计数。
- **不改任务包版本、不新增需求版本**：那是 `requirement revise` 的职责（见备选方案）。
- **不自动落地**：刷新只让交付重新成立，归并仍走 `merge` 的既有判定。

## 验收条件（实现时的判定口径）

- 单元／属性：前置条件**逐条**给出拒绝测试（缺理由、批准过期、有未核对动作、残留槽位、基线相同、任务不存在、检查点损坏），以及放行测试；无 `--force` 可绕过。
- 系统：对一个停在验收门的任务执行刷新 → 记录中出现人工决定（含新旧基线）、旧现场以 `baseline-<旧提交>` 保留、新工作副本记录的新基线等于入参、候选 diff 对新基线计算；随后 `merge` 的漂移判定通过。
- 契约与文档：CLI 契约快照、`docs/architecture.md`（CLI 命令组与记录模块两行）与架构契约同批更新；`docs/status.md` 记录实测结果与未验证项。

## 备选方案

| 方案 | 何时更合适 | 代价 |
| --- | --- | --- |
| **重新规划**（`requirement revise` → 新任务包 → 所有者重新批准 → `advance`） | 需求本身要改，或希望刷新后的任务身份／版本可追溯到一次新的批准 | 需要所有者重新批准任务包；任务身份与版本变化；旧任务包作废 |
| **手工合并**（已验配方：解 `docs/architecture.md` 一处 + 重新导出契约） | 只想尽快拿到该交付，并接受"旧基线验收 + 在新树上补验"的口径 | 交付记录中的基线仍是旧提交；归并需要人工解冲突 |

## 所有者决定（2026-10-18，冻结语义）

1. **刷新需要人工批准**：刷新是一个必须由人工发起并批准的动作，不是系统自动行为；决定记录必须含谁、何时、理由、目标任务与任务包版本、新旧基线。
2. **禁止刷新已交付的任务**：已交付（delivered 及之后）的任务不得刷新——后续改动走新需求。刷新只允许停在决策边界（未交付）的任务。
3. **旧基线／commit 丢失时的校准**：记录基线已不可解析时，任务必须**重新分析是否已经完成**，并在**新基线上做实现校准**；旧基线的记录保留，**校准的原因与过程同样保留**（作为刷新决定的一部分落库）。
4. **刷新不计入失败轮次**：刷新不是失败修复，不改失败累计、授权额度与工时。
5. **旧现场归档冷备份**：刷新前把旧工作副本整体归档到冷备份位置（不参与后续执行），归档路径写入决定记录；旧候选另存 `candidate.baseline-<旧提交>.diff` 一并保留。

### 由决定 1 与 3 派生的两条硬性要求

- **人工批准是入口前提**：命令必须在**没有任何 `--force`／环境变量开关**可绕过的情况下，要求非空 `--by` 与 `--reason`，并把批准写入 `requirement_refresh_decisions`；缺少任一项一律拒绝且零副作用（与 `retry` 的决定记录同口径）。
- **丢失基线的显式声明**：记录基线在项目仓库中不可解析时，命令必须要求操作者显式声明（例如 `--baseline-lost`），并在记录中写 `old_baseline_lost=true` 与校准说明；未声明即拒绝——不能让"基线丢了"变成静默放行。

## 任务与 commit 的关联模型（所有者 2026-10-18 澄清，推翻原先的 A1 框架）

**待验收的任务不存在"基线漂移"问题。** 任务已实现、停在验收门时，只看它与代码挂钩了没有：

| 情形 | 事实 | 正确做法 |
| --- | --- | --- |
| **代码尚未 commit** | 任务**不与任何 commit 挂钩** | 继续等验收；验收通过后再把代码 commit（此刻才建立关联） |
| **代码已经 commit** | 任务与那个 commit 挂钩 | 验收通过 → **任务↔commit 关联落库**；验收不通过需继续改 → 该任务**可关联多个 commit**，关联关系不因此断裂 |

即：任务与 commit 是**一对多的累积关系**，不是"任务绑死在一个基线上"。原先设想的 A1（"停在验收门 + 主干前进 → 刷新"）**不成立**：验收门前的任务本就该继续等待验收，主干前进不是刷新理由。

### 与现有实现的硬冲突（必须先改规则，才谈刷新）

- 现状**没有**任务↔commit 关联记录：`acceptance_bindings.baseline_commit` 存的是工作副本的**起点**提交（不是任务产出的提交），`releases.merge_commit` 只在发布时出现。
- `domain/merge.py::check_merge_readiness` 要求 **`main HEAD == 交付基线`**，否则拒绝归并。这条规则把任务绑死在单一 commit 上，与累积关联模型**直接冲突**——它正是把"代码已 commit、任务待验收／待改进"误判成漂移的原因。

### 已实现（2026-10-18，所有者批准「认可，批准继续」后落地）

- `records.sqlite` 新增 `task_commits(task_id, commit_sha, relation, source, recorded_by, recorded_at)`，`relation ∈ {implementation, acceptance, merge}`，**只追加不覆盖**、同任务+同提交+同关系幂等；提交号必须 7-64 位十六进制，关系非法即 `ValueError`（fail-closed）。
- `approve --stage acceptance` 通过时落库：任务工作副本里批准基线..HEAD 的产出提交记为 `implementation`，项目仓库当前 HEAD 记为 `acceptance`（取不到就如实跳过，不编造提交号）。
- `merge` 成功后把归并提交记为 `merge`；判定改为「验收材料未变 + 候选可干净应用」，`check_merge_readiness` 不再接受 `main_head`／`baseline_commit`；适配层以 `git apply --check` 预检，冲突时 fail-closed 提示人工解决并留痕；工作树不干净的提示保持原样。
- 验证：`make check` exit 0（高频 **1631 项**、前端 117 项），新增/改写 11 个文件的测试（关联表 5 项、归并判定 3 项改写、场景层漂移用例改为「主干前进仍可归并 + 关联落库」）。

### 待实现设计（需所有者确认后开工）

1. **关联表**：`task_commits(task_id, commit_sha, relation, source, recorded_by, recorded_at)`，`relation ∈ {implementation, acceptance, merge}`；一个任务多行、按时间累积，**只追加不覆盖**。
2. **验收时落库**：`approve --stage acceptance` 通过时记录当时项目 HEAD 与任务产出的提交（代码已在主干上时同时记 `acceptance` 关系），形成"这次验收对应哪些提交"的可回查事实。
3. **需改进时累积**：验收不通过 → 继续改 → 新提交继续以 `implementation` 追加到**同一任务身份**，关联不断裂，不需要新任务、也不需要刷新。
4. **归并规则改判**：把"`main HEAD == 交付基线`"换成与模型一致的安全判定——**验收材料身份未变**（候选 diff／测试证据／审查结论的校验值与 `acceptance_bindings` 一致）且候选能干净应用（冲突经人工解决并留痕）；归并产生的提交以 `merge` 关系追加落库。**不放松的**：未验收交付、材料身份漂移、候选为空一律继续拒绝。

## 何时需要刷新（触发分析）

刷新的唯一职责是**修一条维度：代码基线**。判定一句话：**任务的批准基线已经不等于它将来要落地的主干，而任务本身的内容与批准都还有效、必须继续走完。**

需要刷新（且只有这些）：

| # | 场景 | 为什么必须刷新 |
| --- | --- | --- |
| A1 | 任务在 dev/review/test 之间中断，恢复时主干已前进 | 续跑只会在旧基线上继续产出，最终仍要面对同一次漂移；先刷新可省一次白跑 |
| B1 | 记录基线 commit 在仓库中不可解析（rebase／force-push／仓库迁移／浅克隆） | 候选 diff 与材料身份都无法计算 → 按决定 3「重新分析是否完成 + 在新基线校准」，并显式声明 `--baseline-lost` |
| B2 | 工作副本丢失或被清理，记录与候选仍在 | 现场不可续跑，只能在新基线上重建现场 |
| B3 | 项目仓库重建／历史被压缩，旧提交整体消失 | 同 B1 |

**不需要刷新（各有其正确出口）**：

| 场景 | 正确出口 |
| --- | --- |
| 需求内容要改 | `requirement revise` → 重新 plan → 所有者批准（**批准维度失效，刷新不得绕过**） |
| 批准过期或任务包版本变化 | 重新批准／既有 `retry` 的陈旧中断通路 |
| 有未核对动作、残留槽位、副作用不明 | 先人工核对（`actions clear`／`slot clear`），**不得用刷新掩盖** |
| 任务已交付 | 禁止刷新（决定 2）；改动走新需求 |
| 代码没变、只是想重跑一遍 | 新旧基线相同即拒绝（空转只会产生假记录） |
| 需求已停止或处于终态 | 不刷新，等人工恢复决定 |
| 只是想重置失败累计／授权额度 | 刷新不改任何计数（决定 4），也不是重置手段 |

**决策顺序（先问三个问题）**：① 这个任务还要不要？（不要 → 停止／取消）② 变的是**代码**还是**任务内容**？（任务内容 → 重新规划）③ 现场干净吗？（有未核对动作／槽位 → 先核对）。三问都过、且主干确实变了，才是刷新。

**开放问题（需所有者决定）**：上面的关联模型替换了归并的漂移判定，属于硬规则调整——是否按第 4 条改判（以「验收材料身份未变 + 候选可干净应用」取代「main HEAD == 交付基线」），以及 `relation` 取值是否就定为 `implementation／acceptance／merge` 三种。

## 实现方案（下一轮直接执行）

**技术关键（已勘察，必须解决否则刷新无效）**：停在验收门的检查点 `next_nodes=('gate_acceptance',)` 且无 `halted_reason`，执行器会一直在人工门等待（`_keeps_waiting`）。因此刷新不能只复用 `retry` 的"清除 halted_reason"通路，必须由
`read_authorized_checkpoint` 在处理**刷新决定**时合成一个绑定当前检查点身份与任务包版本的重入状态：`resumed_from_halt=True`、`halted_node='dev'`、`next_nodes=('dev',)`；决定与现场不匹配（检查点身份／任务包版本／任务不符）时一律不合成，保持 fail-closed。改动集中在 `records/checkpoints.py` 的读侧，配 `graph/requirements.py` 的重入判定测试。

**文件与函数**

| 文件 | 改动 |
| --- | --- |
| `src/forgeloop/records/checkpoints.py` | 新表 `requirement_refresh_decisions`（SCHEMA + `_migrate` 补建）；`RefreshDecision` 数据类；`validate_refresh(...)`（七条前置条件 + 人工批准 + 已交付禁止 + 丢失基线声明 + 新旧基线不同 + 无未核对动作／无残留槽位／检查点可信／无运行中推进／需求非停止终态）；`authorize_refresh(...)`（先校验、后归档、再记录，失败零副作用）；`refresh_decision(...)` 读侧；`read_authorized_checkpoint` 叠加刷新决定的合成重入状态 |
| `src/forgeloop/adapter/git_workspace.py` | `archive_workspace(workspace, *, tag) -> Path`：把旧副本整体移入 `archive/workspace-<旧提交>-<UTC 时间戳>`（冷备份，不参与执行），返回路径供记录 |
| `src/forgeloop/cli/requirements.py` | `cmd_requirement_refresh`：解析 → 计划/批准校验 → 任务选择 → `validate_refresh` → `archive_workspace` → `prepare_workspace(source, 新基线, workspace)` → 记录决定 → `executor.advance()`；拒绝路径与 `retry` 同样的可操作原因输出 |
| `src/forgeloop/cli/main.py` | 解析器 `requirement refresh`（`--task --baseline --by --reason --baseline-lost --pi-command --project-path --pi-timeout-seconds --records-root`） |
| 契约与文档 | `contracts/cli-contract.json` 重新导出；`docs/architecture.md` 的 CLI 命令组与记录模块两行同步；`docs/status.md` 记录实测 |

**测试矩阵（两侧行为，缺一不可）**

- 拒绝侧（逐条）：已交付任务；缺 `--by`／`--reason`；批准过期或任务包版本不符；有未核对动作；有残留槽位；检查点不可信；新旧基线相同；基线已丢失但未声明；需求已停止／终态。
- 放行侧：停在验收门的任务刷新成功 → 决定记录含新旧基线与归档路径；旧副本出现在 `archive/`；新副本记录的基线等于入参；候选 diff 对新基线计算；**失败轮次计数不变**（决定 4）；随后 `merge` 的漂移判定通过。
- 属性／变异：`validate_refresh` 与本模块既有判定同一口径（等价变异逐条登记）；前端不涉及。

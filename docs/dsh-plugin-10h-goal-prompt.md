## 目标形态与范围

目标运行结构为：**DSH 原生交互 → TypeScript 实现的 ForgeLoop Host 插件、领域逻辑与持久工作服务 → 项目业务记录及 DSH Agent 执行 → 实际验证与交付结果。**

用户运行这个首版时只需启动 DSH 宿主，不需要另外启动 `forgeloop serve`、`forgeloop-launcher`、另一套 HTTP 服务或独立守护进程。调用 Git、构建、测试等外部工具时可以使用受控子进程，生命周期、停止与异常由宿主管理；不得借此启动旧 Python 核心。

**语言切换是硬性验收项：领域逻辑、持久化、业务编排、插件接入、测试、数据迁移、构建辅助和质量／契约检查中的自有可执行逻辑统一使用 TypeScript。发布 JavaScript 由 TypeScript 构建生成。不得通过 Python 子进程、RPC、HTTP、嵌入式解释器或旧 CLI 执行业务，也不得以过渡实现名义保留混合语言产品。**

沿用适合的 SQLite 数据结构与业务不变量，通过兼容 DSH 所用 Node 环境的 TypeScript 存储实现访问。业务编排用清楚的 TypeScript 模块与 DSH 扩展能力实现；无需逐行翻译旧代码，也不默认引入 LangGraph.js 或重建通用 Agent Runtime。

先形成现有能力处置表：必须迁移的核心行为、交给 DSH 的通用能力、明确退役的旧入口。核心规则的完整性依据原有行为测试与实际业务核对，不能为了赶时限将失败累计、版本绑定、停止、材料身份等必需规则归为“首版后置”。

历史代码、在途修改和旧记录先做可核对快照，按协作规则处理归属。交付时新产品的活动源码、包、启动路径、构建和验证工具链不再依赖 Python；旧实现只留在 Git 历史或明确隔离的历史快照中，不参与新产品执行。旧数据通过 TypeScript 编写的兼容读取或显式迁移保持可回查，迁移先在副本上验证且保留原件。

首版使用 DSH 原生命令、模型工具与通用结果展示。需要的批准交互应明确显示对象、版本和决定效果。只有原生能力确实无法承载必要业务时才增加最小交互扩展；不自建聊天壳、不嵌入旧网页、不做主题和布局优化。

本次实施范围是 TypeScript 工程与插件安装装载、核心业务语义重实现、必要业务 Interface、DSH 宿主内调度／恢复、历史数据兼容、本地候选打包升级、测试与质量工具链迁移，以及契约和文档同步。先给出逐批具体文件清单和用途，再在范围内实施；范围外问题记录为“发现但不碰”。

## 持久工作必须具备的行为

1. 输入先持久受理，再返回稳定请求身份；区分“已受理”“运行中”“等待决定”“完成”“失败／结果未知”。插件不维护第二份与核心冲突的任务账。
2. 由确定性代码核对项目、方案版本、授权、停止状态和执行互斥后领取工作。重复消息、重复唤醒和重连不会重复消耗授权或启动同一动作。
3. 事件驱动调度，必要时用定时扫描补偿；没有待执行工作时不靠持续调用模型保持“活跃”。需要分析、实现或审查时才唤醒相应 Agent。
4. 关闭浏览器后，只要 DSH 宿主仍在运行，已受理工作继续推进。宿主停止期间不执行，重启后待执行请求可找回；此前运行结果不明确的动作先核对，不能盲目重放 Git、部署或其他外部副作用。
5. 插件禁用／卸载和宿主退出时停止新领取，处理在途子进程并保留可核对状态。再次加载不会创建第二个同时消费同一项目的执行者。
6. 业务记录保存实际输出与证据，再通过 DSH 会话或事件主动展示结果。会话消息投递、模型声称完成和工具退出码都不能单独代表验收通过。
7. 人的决定来自可信交互来源，并绑定用户实际看到的需求／方案／材料版本。模型不能通过 `by=owner` 或 `approved=true` 自证批准；现有额度、失败累计、停止与验收规则继续在真实入口强制执行。

4. 产出包含实际 TypeScript 改动的 V1 候选包，关联输入、计划、修改、检查、验收和产物摘要。安装包包含正确构建的 JavaScript 与必要资源，不携带或启动 Python 核心；不能实际运行工作区源码却声称验证了安装包。

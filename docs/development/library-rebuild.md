# 需求库一键重建设计

状态为**需求已明确，待实施**（2026-11-16）。产品范围见[产品方案 §8.1](../product/product.md)。
实施遵循 [AGENTS](../../AGENTS.md) 的工作树与行为测试约定。当前实现和验收进展分别见[架构说明](architecture.md)
和[状态记录](../verification/status.md)。

## 1. 产品流程

用户在已绑定项目的天工「产品」页点击一次「重建需求库」。系统自动发现可用材料和业务主题，在同一轮中完成
取证、提炼、审查已有条目与发布。主题、来源及内部批次由系统决定。运行期间可查看进度或取消，生成结果
无需填写场景、再次确认扫描或逐条确认参考条目。

自动生成的规则以现有 `draft` 状态供产品 Agent 参考，页面展示其重建来源。后续需求如遇到影响范围、验收或数据
的缺口，仍按现有流程提出澄清。只有来自可信所有者决定的 `confirmed` 条目参与对应主题的澄清闸门。
既有确认结论与新证据冲突时，保留事实和差异，按既有业务决定流程处理。
[条目状态与澄清闸门](../../packages/forgeloop/src/domain/library.ts) · [领域术语](../../CONTEXT.md)

## 2. 首版取证范围与顺序

先发现项目文档、历史资料和验收用例，再用可取得的 Git 记录补齐相关规则的演进证据。

| 来源 | 取证内容 |
| --- | --- |
| 项目文档与历史资料 | 产品说明、用户手册、变更或决定记录、已归档的工单与验收材料。提取业务目标、角色、规则、例外及适用版本。 |
| 已有验收用例 | 提取前置条件、业务操作、期望结果和异常分支。实际执行的版本与结果应引用已有运行记录。 |
| 可用 Git 证据 | 固定本次提交基线，从变更路径、相关提交与历史版本补足规则演进和适用范围。 |
| 现有需求库 | 固定每条条目的身份、状态、完整文件摘要及引用内容。所有已有条目都纳入本次核对。 |

- 跨来源按可核对的时间**从最近到最远**处理。文档与归档材料优先采用载明的决定、发布或修订时间，Git 使用提交时间。
  可归属到已知版本的用例采用相应的证据时间。时间无法确定的材料标记为未知，排在有时间的证据之后。
  同一时间的记录使用稳定的来源和位置顺序。
- 时间只决定处理优先级。对照历史意图、实现行为、验收结果和真实决定来判断规则是否仍适用。日期更新或来源数量
  增加时，依据实际内容及范围判断是否有变化。
- 每项证据记录项目归属、来源类型、版本或内容摘要，以及原始章节、工单编号、用例或提交和路径。
  模型引用须对应本次已采集的证据。既有条目和过去的重建结果用于对照，同源材料重复出现时合并引用。
- Git 是可选来源。无 Git 时继续使用本项目的其他材料。结果显示实际覆盖的来源和时间范围，并列出缺失、跳过、
  失败及因预算未处理的部分。缺少可用证据时返回相应结果和原因，已有库继续可用。

## 3. 按产品需求说明产出

按用户可理解的业务规则归并条目。一条描述一个可独立复核的规则或目标。正文采用产品需求说明的表达，
包括适用的**业务目标、用户或角色、触发与前提、预期行为、业务规则、例外边界和可观察验收条件**。
形成不了确定结论的事项记录为待澄清，说明它影响的业务范围。目标和取舍应有文档或真实决定依据。

例如「已发货订单的取消」围绕谁发起取消、哪些状态允许、拒绝后用户看到什么，以及是否影响订单和退款。
接口、表名、源码位置和测试名称放在证据引用中。验收描述用户能看到或核对的结果。

沿用需求库 Markdown 格式的 `id`、`topics`、`summary`、`status` 和来源字段。
稳定主题对应具体业务规则及其适用范围。同一条规则的措辞调整或引用变更沿用原身份。
本轮完整候选、引用和待澄清事项可在产品页查看。
[条目格式](../product/library/README.md)

## 4. 审查已有库与处理冲突

以运行开始时的需求库快照为基线。按条目身份、主题及实际适用范围比对新旧规则，核对主体、
触发条件、结果、例外和验收表现。同主题不同适用范围应分别记录其边界。

| 审查结果 | 本次处理 |
| --- | --- |
| 业务规则一致 | 原条目的文件、身份、状态和内容原样保留。新证据及本轮核对结果追加到报告。 |
| 发现有证据的新规则 | 校验来源、条目格式和整库容量后，以 `draft` 写入供后续分析参考。 |
| 已有重建草稿确有业务变化，且证据能说明更替 | 核实它由本功能生成，并与上次发布记录的完整文件摘要一致后更新。保留原版本、新证据和变更理由。 |
| 新证据与人工条目、已确认规则或人工修改冲突 | 保留原条目及人工记录，展示双方内容、适用范围、证据和待处理事项。旧规则的正式替代以之后可回查的所有者决定为依据。 |
| 无法判定是否等价、证据不足或取证未覆盖 | 保留原内容和待核对原因。 |

人工决定、编辑和冲突处置按其原始来源保存。重跑时已发布文件与记录摘要不一致的条目按人工改动保护。
同一输入重跑保持条目身份幂等。每轮仅发布本轮核对通过的差异，并记录保留项、更新项与冲突项。

## 5. 一次运行与安全发布

1. 从可信入口校验操作者权限和项目归属。服务端根据已绑定项目解析路径，登记运行身份、材料范围和已有库快照。
   同项目同一时间只运行一轮重建，重复点击返回当前运行的进度。
2. 按时间优先级在后台自动分批取证与提炼。复用项目配置的产品 Agent，调用只提供有界证据和输出格式，
   使用 `tools: 'none'`。运行时核对模型引用的证据、项目范围与目标文件。
3. 审查整库并形成一份发布清单。清单包含变更前后摘要、证据、冲突及预计落库条目。发布前复查当前文件和引用
   是否仍对应快照，并调用现有条目解析和整库校验。整库按当前 64 条限制校验，超出容量的候选仍可从报告查看。
4. 项目内串行发布通过校验的差异，再刷新现有索引及结果。批次完成以实际文件与索引核对为准。

完整候选、证据目录、人工与冲突记录、覆盖报告和发布回执保存在项目记录目录
`<recordsRoot>/projects/<project>/library-rebuild/<runId>/`。可自动发布的草稿落在项目的
`docs/product/library/`，继续采用现有[扫描](../../packages/forgeloop/src/runtime/library-docs.ts)
与 SQLite 索引。写入来源绑定项目、运行和候选身份。

预算耗尽或部分证据不可用时，按实际范围报告部分完成，并保留未覆盖的原条目。运行失败或发布前取消，保留
上一次可用库和本轮记录。取消状态以任务实际停止为准。发布中断时，恢复先按回执核对磁盘和索引，再执行安全
续作或恢复。恢复操作只处理仍与本轮写入摘要一致的文件，发现人工修改则保留现场并记冲突。

## 6. 入口及隔离

沿用天工认证看板，服务端从当前会话解析项目。启动动作接收项目会话身份，返回运行 ID。结果页用运行 ID 查看
进度、实际覆盖、草稿、保留项及冲突，并支持取消。写入权限须来自可信入口，本轮授权限于本项目的重建和参考条目发布。

取证限定在该项目允许的文件和记录范围。子目录项目的 Git 证据限制到该项目路径，Git 操作只读，
验收证据来自已有材料。运行时在生成证据摘要之前过滤凭据及超出项目授权范围的内容，模型工具与项目路径检查
共同保护写入边界。所有者的确认按现有澄清与业务决定规则记录，并核验相应的可信来源。

## 7. 首版实施与验收

首版交付一次点击即可完成取证、业务规则提炼、已有库审查、发布参考条目和查看报告的闭环。
候选范围由本版产品交互和业务证据限定，复用现有条目状态、扫描索引和澄清闸门。后续按实际缺口评审通用代码
和数据结构提取、在线工单接入、输入快照复用和漂移提醒。

| --- | --- |
| `packages/forgeloop/src/domain/library-rebuild.ts` | 证据身份、已有条目核对结果与发布校验。 |
| `packages/forgeloop/src/runtime/library-extract.ts`、`packages/forgeloop/src/runtime/library-rebuild.ts` | 项目内取证与排序、单轮调度、结果记录和发布恢复。 |
| `packages/forgeloop/src/runtime/service.ts`、`packages/forgeloop/src/runtime/prompts.ts`、`packages/forgeloop/src/runtime/library-docs.ts`、`packages/forgeloop/src/runtime/library-writeback.ts` | 装配产品 Agent，复用扫描与索引，并协调当前库的读取和人工写入。 |
| `packages/forgeloop/src/index.ts`、`packages/forgeloop/src/runtime/board-route.ts`、`packages/forgeloop/src/tools.ts`、`packages/forgeloop/client.js` | 认证启动、项目范围、受控写入与产品页进度和结果。 |

验收使用两个已绑定的真实项目，一个有 Git 和既有需求库，一个无 Git 但有文档和验收材料。各点击一次，
核对完整链路和实际覆盖。另用可控证据验证取证顺序、无日期处理、同规则原样保留、有差异及人工改动时记录冲突、
模型或发布失败后的恢复、重复点击和跨项目拒绝。下一条真实需求须能引用重建草稿，同时仍可提出有依据的澄清。
实施遵循行为测试先行，运行 `make check`、契约和文档链接检查，并核对真实 DSH 宿主的产品页入口。

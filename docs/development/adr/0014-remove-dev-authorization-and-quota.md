# ADR 0014：研发侧去授权与去额度，非人工阻塞自动重试

- 状态：已接受（2026-11-24，所有者要求“取消授权/额度限制；非必要人工介入的场景支持自动重试”，并确认保留系统准入与部署授权、自动重试需上限与退避、配置项保留但不再阻断）
- 依据：[产品方案 §5.2.1](../../product/product.md#521-研发阶段的人工评审与准出2026-11-23所有者已确认待实施)、[产品方案 §7](../../product/product.md#7-配置默认值失败计数与暂停)、[状态记录 §283](../../verification/status.md#283-研发侧去授权与去额度自动重试2026-11-24)、[ADR 0013](0013-verification-baseline-from-analysis.md)

## 背景

研发推进此前仍有两个人工前置：非准入需求必须由所有者批准任务包；失败轮次、工时、任务尝试与验证次数用尽后，需求停在 `blocked`，必须由所有者追加授权或延长工时才能继续。实际运行中这些额度默认已是不限（`-1`），显式配置时才阻断，但仍让看板要求“批准 / 追加授权 / 延长工时”动作，与“普通任务按有效需求、授权和确定性检查自动推进”的目标不一致。同时，环境异常、测试命令失败、宿主中断等非业务阻塞会一直等待人工点击。

## 决定

1. **额度不再阻断**：`remainingFailureRounds` 恒为不限；工时守卫、任务尝试上限与验证尝试上限不再拦截，只保留记录与展示。`failureRoundsPerGrant`、`maxTaskAttempts`、`maxVerificationAttempts` 配置项继续解析，但正数也不阻断。`retryDecision` 不再以额度或工时措辞拒绝重试。
2. **研发侧授权前置移除**：准入需求无需任务包批准即可推进；看板不再提供 `approve`、`grant-rounds`、`extend-budget` 动作。实现前评审改为只记录，不再阻断任务包生成或触发重新规划。系统准入仍是唯一必需的研发门禁；部署、上线、验收、运维处置与业务例外仍需所有者独立授权。旧端点保留为兼容记录（`approve` 仍写入 `owner-approval`），供历史调用与审计，但不作为推进前置。
3. **自动重试**：协调器每轮扫描 `blocked` 需求，当最近一次失败轮次属于实现修复类阶段（规划、实现审查、正式测试、验证、业务验收、宿主中断），且无主动停止、无在途请求、阻塞原因不属于人工判断类（需求争议、澄清、承诺冲突、部署授权、取消）时，自动排入 `advance`。每需求最多 20 次，退避 30 秒起、指数增长、上限 30 分钟；手动请求重置连续计数。分析失败的自动重试上限同步为 20。
4. **单次推进边界**：同一推进请求内自动修复最多 3 轮，同一修复动作最多 20 次 Agent 回合；达到上限后收口为 `blocked`，交由自动重试继续。该边界防止模型无进展时无限循环，不属于需要人工追加的额度。

## 影响

- 行为：准入需求从 `specified`/`plan_proposed` 到提交可全程无人工点击；失败按上限自动重试，超过上限或属于人工判断类的阻塞继续停在 `blocked`。
- 记录：失败轮次、请求来源（`system:auto-retry:<n>`）、问题单、验证历史与工时继续累计，不清零。看板展示 `remainingRounds: null`（MAX）。
- 测试：新增 `auto-retry.test.ts`（退避、上限、人工阻塞、停止、在途去重）；更新额度、看板动作、规划评审与协调器相关用例；`issue-retry-loop` 覆盖单次推进 5 轮边界。
- 兼容：`approve`、`grant-rounds`、`extend-budget` 端点与领域函数保留；旧批准记录仍可查询，但不再决定推进。
- 未完成：两条验证执行路径的收敛（ADR 0012）；运行中真实模型场景下的自动重试验证需在后续批次补做。

## 待确认

- 非准入、无批准的旧任务包是否会长期停在 `plan_proposed`：按“系统准入是唯一研发门禁”的现状保留，是否提供准入失败的人工补救入口未决。

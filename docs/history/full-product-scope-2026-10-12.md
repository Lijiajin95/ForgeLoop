# ForgeLoop 产品需求与流程规则

日期：2026-10-12，Asia/Shanghai。状态：**用户已确认的设计草案，尚未实现或验收**。

本文件以 grill 中的最新明确决定为准。领域词义见 [CONTEXT.md](../../CONTEXT.md)，实现职责见 [架构草案](../architecture.md)，里程碑见 [RoadMap](../roadmap.md)。技术方案待定项集中列在文末。

## 1. 目标、用户与成功依据

ForgeLoop 为已接入项目提供从需求澄清、解决方案、技术实现、独立审查、测试验证到部署上线的研发流程。首版用户为一名项目所有者，主要负责范围、方案和验收决策；Agent 承担批准范围内的研发工作。

首要价值是减少每个合格交付工作项实际需要的人工作业时间。人工时间包括澄清、决策、验收、故障处理和返工；ForgeLoop 自身维护时间另行记录，评估净收益。质量是验收条件，费用与交付周期是辅助指标。

用 3–5 个真实工作项建立基线与观察结果，再确定目标改善比例。比较优先使用可核对的历史人工记录；缺少记录时，执行前估算并明确标为估算。本轮只定义 ForgeLoop；受管项目的业务需求由各自的研发工作项提供。

## 2. 首版边界

| 范围 | 规则 |
| --- | --- |
| 项目接入 | 用户手动创建项目和 GitHub 仓库并同步代码，随后登记给 ForgeLoop 自动迭代；包含 ForgeLoop 自身 |
| 项目数量 | 首期支持两个受管项目；业务与任务按项目隔离 |
| 代码基线 | 支持已有可运行仓库，也支持空仓库或缺工程、测试、部署基线的仓库；补齐方案需要批准 |
| 目标技术栈 | 不限制受管项目语言和技术栈，由 Agent 提出方案、用户批准 |
| 系统底座 | 统一 LangGraph 编排底座；ForgeLoop 定义自己的业务图，首版执行器为 PI |
| 执行节点 | 首版一个主要执行节点；用户电脑用于开发、决策与访问，额外研发执行节点放入 RoadMap |
| 自动工作来源 | 首版处理用户提交的工作项与已批准流程产生的修复工作项；主动发现产品需求放入 RoadMap |
| 工具 | 受控的文件、命令、API、浏览器测试及业务工具；MCP、通用桌面控制放入 RoadMap |
| 自研 Runtime | 放入 RoadMap，首版不建设完整自研模型／工具执行循环 |

讨论中的执行节点计划为 Debian 13、i7-6700K、16 GB 内存、512 GB 系统盘，另挂载独立备份硬盘；尚未连接或核验该节点。具体安装、资源配置和部署步骤由技术方案列出。

## 3. 工作对象与修改规则

一个项目拥有多个研发工作项；每个工作项可拆成多个任务，任务可继续拆成子任务。任务必须绑定一个项目，不支持跨项目任务。

研发工作项分为需求和线上问题单。线上问题单具有独立身份，关联受影响项目与版本，复用澄清、方案、实现、审查、测试、验收流程。线上功能遗漏属于测试与验收逃逸的问题，应建立高优先级问题单，不能将已验收需求重新打开并与运维状态混合。

同一目标的补充或修改形成需求的新修订，保留原始输入、方案、批准及执行历史，重新批准受到影响的范围。不同目标建立独立工作项。修订不会自动清零失败记录、已消耗工时，也不会自动生成追加授权。

## 4. 邮件与管理页面

正式首版的两个入口均支持提交、追问、进展、成果、确认和通知，操作同一套权威业务记录。

管理页面通过私有网络／VPN 访问。系统使用专用邮箱，与所有者的个人邮箱往来，只处理系统邮箱中的研发邮件。唯一用户身份、允许的邮箱及邮箱权限需要在技术方案中明确。

自然语言用于描述需求和沟通。正式批准、拒绝、修改决策使用可确定解析的格式，至少绑定审批身份、业务对象版本和动作；页面动作绑定相同审批对象。旧版本回复、重复决定或无权来源不能直接触发新的执行。具体回复格式与身份校验方式待技术方案确定。

首版输入包括文本正文、链接和附件。附件支持文本／日志、PNG/JPEG、PDF、DOCX；Excel 和 ZIP 不在首版解析范围。保存原始文件、解析结果和解析状态，并与需求修订关联。无法读取、受密码保护、扫描内容未成功提取或格式不支持时明确标记，不能声称已经理解。

附件解析由 ForgeLoop 业务工具负责；Agent 根据批准范围使用解析结果和原文件。文件大小、数量、解析时限、链接访问范围及具体解析实现待技术方案确定。

## 5. 三个人工检查点

| 检查点 | 用户确认内容 | 后续自动工作 |
| --- | --- | --- |
| 范围确认 | 目标、边界、用户场景与验收标准 | 形成技术方案及可执行验收场景 |
| 方案确认 | 总体方案、任务拆分、依赖、改动范围、工时、资源与恢复方案 | 在授权内实现、自验证、独立审查和正式测试 |
| 整体验收与发布授权 | 完整场景、真实验证证据、交付产物与发布计划 | 结束研发工作项，向版本部署／运维流程交付验收产物 |

任务和子任务在批准方案内推进；范围扩大、预估超过剩余工时、权限不足或额度用尽等例外由用户决定。子任务不另设常规人工审批门槛。

方案阶段由独立测试角色参与制定正常、异常和边界场景。验收以工作项的完整用户场景为单位，例如需求有 10 个任务、内部拆成 100 个子任务，也要等需求相关工作完成后统一验证与用户验收，不逐任务上线。

## 6. 研发与质量流程

1. 保存原始意图，澄清需求并完成范围确认。
2. 制定方案、拆分任务、设计验收场景及恢复步骤，完成方案确认。
3. 按 small diff first 实现小任务，执行自验证。
4. 独立代码审查；修复阻断问题并重新验证。
5. 相关任务全部完成后正式转测，运行完整用户场景及安全可执行的其他用例。
6. 提交通过、失败、阻塞、跳过及未验证事项，完成用户整体验收与发布授权。
7. 冻结并交付已验收产物，研发工作项结束；版本部署／运维另行推进。

开发、代码审查和测试角色使用独立上下文。开发者的主观结论不能作为审查或测试通过的依据。每个开发任务独立会话，子任务可在任务内续跑；任务之间通过代码、批准方案与结构化交付记录衔接。

代码审查阻断明确缺陷、数据与权限问题、批准要求或强制工程规范的违反。一般风格和可维护性建议记录下来，不自动扩大范围；主动重构放入 RoadMap。

测试尽量运行完整的安全用例集，批量报告结果；不安全操作先停止。工具退出成功、模型声称完成、mock 或 fixture 通过不能替代真实交付质量证据。

## 7. 调度、工时与模型费用

首版同一时刻执行一个研发／测试作业，任务排队。等待用户输入释放执行容量；同项目普通工作项串行实现，后续工作可先做受控的收集与澄清。首版研发验证在主要节点执行，不使用外部 CI 代替该节点的执行记录。

跨项目可执行作业默认 FIFO，用户可调整排队顺序。普通运行中工作先明确暂停；线上问题单拥有最高研发优先级，修复方案获批后可在安全点抢占普通研发。保留原现场，恢复时核对代码基线、有效方案与旧验证结果。

小任务默认执行工时为 2 小时，分发时明确具体限额；实现前预测所需工时，超过剩余批准工时则先请求决策。批准方案同时规定工作项累计工时，拆分不能绕过总限额。用户等待时间不计入实际执行时间，失败与恢复工作据实记录；必要恢复时间从批准的总工时中预留，依据具体恢复步骤估算。

**首版不设置模型费用预算上限**，撤销此前任务级、月度模型费用硬上限及相关自动停止规则。继续统计模型、Token、时间及可取得的实际或估算费用；无法核算时标记未知，不能填为零。费用未知本身不触发已撤销的额度阻断。

支持多模型服务，各角色配置主模型和预批准备用链；在故障、限流等情况下按授权切换，记录原因，受剩余工时及权限约束。实际接入能力由 PI Adapter 验证。每次执行绑定有效配置快照，普通配置变更用于后续执行；当前执行变更先明确暂停、批准并记录新配置版本。

模型费用无限额不意味着自动授权所有外部资源。新增付费 API、存储或主机资源须列出一次性及持续费用；在已有账户和批准权限内可自动配置，新账户与支付设置由用户完成。

## 8. 暂停、恢复与取消

首版提供工作项／需求级控制，不提供独立子任务控制。控制窗口截至测试通过并完成用户验收、发布授权之前；该时点后属于版本部署／运维，页面只报告状态，不提供部署／运维暂停、恢复或取消按钮。

收到暂停指令后，停止启动后续动作，等待当前工具完成并保存结果。当前工具有预先批准的超时限制；被迫终止后结果不确定的，标记待核对，不直接重放。PI 侧如何实现安全点拦截必须通过适配验证，不能仅把中断指令发送成功当作已经暂停。

节点或进程故障后，先核对业务记录、编排检查点、PI 会话和实际副作用。确认的工作可恢复；未知的文件修改、通知或发布结果进入核对／人工决策。恢复不是重新执行整段流程的默认理由。

完成、取消或暂停后的工作区、临时环境及记录默认保留，由用户明确决定清理。后续清理必须描述目标与保留材料，不能通过普通取消动作隐式删除现场。

## 9. 失败轮次与追加授权

| 计数模式 | 计数对象 | 纳入失败 | 不直接纳入 |
| --- | --- | --- | --- |
| 研发 | 研发工作项 | 正式转测后，一轮测试或用户验收失败 | 转测前编码、自验证、审查失败；普通模型／网络异常；同轮重复反馈 |
| 部署／运维 | 项目内的基础版本号 | 进入部署／运维后的一轮处理失败 | 研发失败；后缀变化；同次失败的重复上报 |

同轮多个失败用例只计一次。计数记录须能定位计数对象、候选轮次、原因和所属授权；每次失败只归属一种计数模式。运维失败的具体判定边界及子步骤重试规则在技术方案中列明，不自行猜测。

**每次自动处理授权最多允许 3 个失败轮次；达到后停止自动推进并通知用户。** 用户可追加授权，每次继续允许最多 3 个失败轮次，无预设的累计授权次数限制。保留完整历次授权与累计失败，不因授权、修订或会话重建清零：

| 授权 | 本次失败额度 | 示例累计范围 | 用尽后 |
| --- | --- | --- | --- |
| 初始授权 | 3 | 1–3 | 等待追加授权或其他决定 |
| 追加授权 1 | 3 | 4–6 | 再次等待追加授权 |
| 追加授权 2 | 3 | 7–9 | 再次等待追加授权 |

授权额度是失败轮次额度，不限制转测前自验证的调用次数，也不自动延长已耗尽工时。新的授权具有独立记录并明确计数对象；需求修订、会话重建、服务切换和候选后缀变化都不能隐式新增额度。

运维追加授权通过研发侧修复任务的审批记录关联到相应版本计数对象，版本页面继续只报告状态。研发修复工作项与版本分别消耗各自的失败额度，不合并为一个计数器。

## 10. main、交付记录与验收产物

main 为主干，普通研发及修复使用独立工作区／detached HEAD worktree 等方式隔离，不强制为每个需求创建分支或 PR。每个工作项建立可回查的交付记录，包含改动 diff、候选提交、审查、测试与验收证据。

批准范围内可生成候选提交；候选结果通过验证与用户验收后，由受控流程更新 main。main 基线变化时需要核对改动与验收结果，不能未经验证将差异拼接后沿用旧批准。正式版本由明确提交和产物定位，不能用“main 最新”替代。

**部署使用通过测试与用户验收的同一份产物**。版本号、代码提交、产物校验值与验收记录关联保存；部署前核对产物身份。生产配置和迁移步骤也在批准发布计划中明确，但不通过重新构建替换验收产物。

发布与运维以版本为工作对象，研发工作项的状态及失败计数不等待运维结束，也不因运维失败回退。运维问题建立高优先级研发问题单，修复结果再次验证、验收并交付对应版本流程。

## 11. 版本规则与自迭代

每次转部署／运维都有基础版本号。未成功版本的修复、转测和再次交付保持基础版本号，用 alpha、beta 等递增候选后缀区分记录；它们共享同一计数对象和追加授权历史。

运维成功后使用去后缀的正式版本号，保留旧候选、校验值、授权与失败记录。已成功正式版本的线上修复产生新的基础版本，例如 `1.2.0 → 1.2.1`，具有新版本自己的运维计数对象。具体版本分配及后缀顺序算法待技术方案确定。

候选提升正式版本需保持验收产物不变；如果程序内嵌版本号，应在技术方案中解决“去后缀”与“不重新构建”之间的对应方式。

ForgeLoop 支持全部自身 Module 的自动迭代，包括执行适配、发布、恢复和权限控制。首版采用同节点双版本切换，保留前一版本和可独立进入的恢复路径。数据变更优先兼容、增量与分阶段清理，保留恢复所需旧读取能力；数据库与流程检查点的版本兼容需要验证。

允许计划内短暂中断，在方案中估计时间、通知及恢复动作。授权内、安全明确的恢复可自动执行；无法判断或未授权的动作交由人工决定。回滚成功不等于新版本发布成功。

## 12. 记录、备份与交付包

ForgeLoop 管理权威需求、审批、调度、失败授权、交付与版本记录；GitHub 管理代码和提交引用，GitHub Issues 不作为首版核心权威记录。

交付记录至少包括：

- 原始用户意图及附件；需求、方案、验收标准与历次审批。
- 任务拆分、配置版本、工时估算与实际用量。
- 代码改动、独立审查意见及处理结果。
- 真实测试的通过、失败、阻塞、跳过和未知状态。
- 结构化执行结果、候选提交、验收产物与用户验收决定。
- 版本授权、部署检查、失败及恢复结果。
- 实际可取得的 Agent 原始执行轨迹；PI 会话、压缩摘要和事件与运行身份关联。

记录中区分原始数据、提取数据、摘要、估算和未知项。执行器没有暴露的数据如实说明，不能声称收集了完整模型内部思维或未实际取得的请求。

**备份到本机额外挂载的独立硬盘**，取代之前节点外备份方向。关键需求、审批、授权、额度使用和状态等目标是不丢失；相关关键动作在备份确认后推进，备份不可用时等待并报告。原始轨迹允许最多 1 小时损失。备份及恢复流程、完整性与恢复时间需要实际验证。

这是同节点磁盘备份，不能宣称整机不可用时仍可自动提供服务；该场景需要修复节点或迁移硬盘。工作区保留、GitHub 同步和独立磁盘备份是不同的恢复材料，不能彼此代替。

## 13. 里程碑边界

首轮验证限定为 **30 小时人工投入的只读任务状态页**：由真实编排和 PI 执行记录驱动，展示状态、执行步骤、时间、结果与失败原因，并验证刷新／重启后的回查。

首轮可以使用受控测试入口发起执行；邮件、操作页面、完整发布自升级等正式首版功能仍在整体产品范围内。首轮不声称已经交付全部首版能力。详见 [首轮验收计划](../first-validation-plan.md)。

以下事项保留为开放问题，不能据此假定已批准某个实现：

| 事项 | 需要明确的内容 |
| --- | --- |
| 存储与技术栈 | 业务记录、持久 checkpointer、轨迹文件的实现；后端、页面、迁移、测试工具及版本 |
| 身份与邮件 | 页面身份、邮箱接入、发件来源验证、确定性审批格式、去重、过期与回复关联 |
| 工具与隔离 | PI 有效工具配置、原生扩展／脚本接入、容器权限、网络与测试资源配置 |
| 失败定义 | 运维失败轮次与子步骤重试；阻塞／未验证结果的判定；初始授权及追加授权的具体落点 |
| 基线变化 | main 在等待验收或抢占期间改变后，如何接回候选并重新验证 |
| 产物与版本 | 构建格式、完整性、版本分配、候选顺序及去后缀时的产物身份 |
| 恢复与自升级 | 双版本恢复路径、控制面不可用时入口、执行／检查点兼容、数据恢复与实际恢复时长 |
| 备份与保留 | 备份硬盘身份、目录、空间、挂载失效策略、关键记录备份确认及恢复演练；档案保留周期 |
| 执行限额 | 各任务具体工时、聚合工时、工具超时、预分析与恢复时间；追加失败授权是否另需延长工时 |
| 输入与外部资源 | 附件限制与解析实现、链接访问策略、凭据管理、资源创建权限和非模型费用 |
| 评价 | 真实工作项选择、人工基线、维护成本与改善目标；不能用首个状态页结果替代全部 ROI 验证 |

## 15. 已被替代的讨论方案

| 旧方向 | 当前规则 |
| --- | --- |
| 首版完整自研 Agent Runtime | LangGraph 编排＋PI Adapter；自研放入 RoadMap |
| ForgeLoop 不使用共同流程框架 | 统一 LangGraph 底座，独立业务图 |
| 上下文不足立即停、压缩仅放 RoadMap | 首版复用并验证 PI 原生自动压缩；自研压缩仍属未来 Runtime 工作 |
| 一需求一 PR／任务分支 | main＋隔离工作区，取消强制 PR，保留交付记录 |
| 完成／取消后归档并自动清理现场 | 默认保留，人工决定清理 |
| 任务级、月度模型费用硬上限 | 首版不设模型费用上限，保留统计与工时控制 |
| 节点外备份 | 本机额外挂载独立硬盘备份 |
| 失败最多三次且无法追加 | 每次授权最多三个失败轮次，可追加，累计记录保留 |
| 研发与运维共用失败轮数 | 两种模式，分别绑定研发工作项与基础版本号 |
| 运维失败使原需求重新进入实现 | 版本流程处理，新增独立高优先级研发问题单 |

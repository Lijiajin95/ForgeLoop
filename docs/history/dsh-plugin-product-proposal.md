# ForgeLoop：基于 DSH 的产品重定位提案

日期：2026-10-20，Asia/Shanghai。状态：**可评审草案，未实施**。

本提案依据所有者关于DSH插件、项目经验、中大型系统和多人协作的连续讨论形成。它提出新的产品方向与验证范围，不把未来能力视为当前实现，也不直接替代[现行产品基线](product-requirements.md)、[领域语言](../CONTEXT.md)、[架构事实](architecture.md)或[状态记录](status.md)。本轮只新增本文件，不授权迁移、删除现有能力、训练、部署或公开分发。

文中用户划分、首版范围和商业路径属于建议与待验证假设；DSH能力另附一手来源。未开展用户访谈、外部试点或迁移原型。

## 1. 建议采用的产品定位

**ForgeLoop是面向中长期、中大型软件项目的DSH研发协作与经验插件：让不同会话、不同成员和不同Agent承接当前目标、有效规则、任务进展与交付依据，持续完成有边界、可验证的需求变更。**

核心工作单位是项目内的研发工作项。一个工作项可以经历多次会话、不同执行者和多版方案；一次会话、一个todo条目或一次模型调用不等于一个研发工作项。

DSH提供主要工作宿主和分发入口；ForgeLoop维护项目级业务关系。首版优先验证跨会话、跨人接手的正确性和完整成本收益。

### 长期愿景

当AI参与构建、连接和运行复杂系统时，使相关人仍能理解关键目标、边界、规则、变化理由与证据，并保留有效决定和干预能力。这一愿景不依赖未来一定出现单一庞大系统，也不等于首版承诺完整自动架构、自动运维或全行为可解释。

### 当前使命

在真实研发过程中，维护“目标—规则／决定—任务—候选—验证—交付—经验”的可回查关系，并在工作发生时提供当前有效依据。

### 第一阶段结果

一项真实需求经过修订、至少两个会话和两名成员后，新接手者仍能正确判断当前目标、有效规则与批准、已验证内容、待复核事项和允许的下一步，完成真实验收；同时记录新增机制的全部使用成本。

## 2. 为什么要从项目而不是会话出发

DSH官方已有[持久化单会话goal](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/goal/goal/README.md)、[会话所属todo清单](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/todo/tool-todo/README.md)、技能和会话历史。goal可跨重启保留并拒绝旧修订更新，但本身不是业务调度器或独立验收器；todo也不是多人共享的项目任务账。

因此，“保存目标、列出任务、读取文档”不能单独构成ForgeLoop的充分差异。需要验证的增量是：同一项目的要求、决定、批准和证据在跨人、跨会话以及连续变更后，仍能正确衔接。

长周期与复杂性优先按真实协作条件判断：需求反复变化、跨模块依赖、业务例外、成员接手和验证负担。代码行数、Agent数量和团队人数只能提供背景，不作为需求强度的替代指标。

存量系统可从一条真实变更开始；新系统可从目标与关键规则开始，随实际变化积累关系，避免启动时要求完整建模。

## 3. 目标用户与采用单位

| 角色 | 主要任务与痛点 | 应获得的结果 |
| --- | --- | --- |
| 主要用户：技术负责人／核心维护者 | 维护长期项目，对目标、历史规则和交付质量负责，常需重新核对AI改动 | 更快且正确地判断一次变更能否接纳，并保留依据 |
| 日常使用者：开发者／Agent操作者 | 实现需求、处理失败、切换会话或接手他人工作 | 自动获得当前范围、相关规则、前置产物和下一步条件 |
| 日常使用者：审查／测试／验收者 | 检查改动与要求、版本和验证是否一致 | 能回查原始证据，识别未知和失效依据 |
| 配置与管理者：项目负责人 | 管理项目接入、成员、角色和共享记录 | 明确谁能读、修改、执行和批准，处理冲突与恢复 |
| 潜在预算者：工程负责人／创始人 | 决定研发效率与质量工具投入 | 可观察的净收益和可承担的维护成本 |

这些角色在小团队中可能由同一个人兼任，但身份与权限语义应区分。采购角色、预算和实际痛点频率尚需验证。

### 首个理想试点

一个已有真实交付节奏、至少两人会反复接手、维护者愿意用DSH处理实际需求的项目。要求能提供任务、改动与验证依据，并有明确验收者。

采用单位建议是一名维护者带入一个项目，而非要求整个组织先迁移。其他成员可以沿用既有Git、CI和开发工具；实际改动来源如实记录。外部提交和CI结果是否足以作为批准或验收依据，需要明确协议，不能自行推定。

独自维护项目可以先验证机制，但不能替代多人协作试点。高合规大企业、短期一次性原型、没有明确维护者的任意仓库，不作为最先验证的客户类别；这是试点优先级，不是永久排除。

## 4. 用户需要完成的四件事

| 时刻 | 用户需要完成的工作 | ForgeLoop的候选职责 |
| --- | --- | --- |
| 开始一条需求 | 讲清目标、边界、相关规则与验收依据 | 保存来源和版本，提示缺失／冲突信息，准备可批准任务包 |
| 继续或接手 | 知道什么仍有效、已经做过什么、接下来允许做什么 | 从权威记录重建项目上下文，关联前置产物、未完成动作与未知项 |
| 接纳一次变更 | 判断要求、候选和验证是否对应 | 提供真实改动与测试／审查身份，核对批准与范围 |
| 开始下一次相似工作 | 复用有效方法，避免重复失败 | 按条件提供案例、技能或检查，保留反例与失效信息 |

首个价值主张是减少重新理解、错误接手、遗漏验证与整理依据的成本。顺畅不是减少所有确认；应使必要决定有足够依据，并减少无用途的往返。

## 5. 一条代表性的用户过程

以下是待验证的交互过程，不是现有命令或界面声明：

1. 维护者在DSH中将仓库接入一个项目，选择现有需求与规则来源，确认少量当前事实；缺失信息保持未知。
2. 提交需求，例如“支持分次退款，累计退款不得超过实付金额”，确认验收场景与范围。
3. 插件提供相关规则、架构决定和已验证案例，生成带依赖、范围与正式测试的任务包；当前任务包取得明确批准。
4. 开发者在关联的DSH会话中执行一个任务，相关上下文来自当前记录；实际候选和验证结果被记录。
5. 另一名成员接手下游工作，直接看到前置产物、现行要求、待核对项及证据，而无需重读全部对话。
6. 中途修订需求时，标明任务包和相关依据的复核状态；按业务规则处理旧批准，不以聊天中的模糊同意替代批准。
7. 独立审查、程序正式测试与人工整体验收关联到实际候选；已知未验证部分清楚呈现。
8. 真实结果形成候选经验。后续相似任务按适用条件取用，不直接将一次成功或失败升级为全局规则。

用户可以进行普通DSH探索。显式纳入ForgeLoop管理的工作项才取得相应身份与受控流程；产品不应宣称接管项目中所有会话、工具或非ForgeLoop写入。项目的合入／交付要求如需更广范围生效，应在适用的CI或服务端入口实施。

主要交互建议围绕当前项目、当前需求及版本、当前阻塞和下一步决定呈现。关键批准应展示具体对象与依据；一般探索保留DSH原有使用习惯。接入时先引用已有资料并标记缺口，避免要求用户先提交完整架构或领域本体才能开始。

## 6. 产品能力与职责边界

| 能力 | 首版方向 | 主要责任 |
| --- | --- | --- |
| 模型接入、会话、工具循环 | 优先复用 | DSH宿主；ForgeLoop验证使用范围 |
| 上下文与工作项交互 | DSH内提供项目与需求视图 | ForgeLoop插件 |
| 任务版本、依赖、批准、验收 | 明确业务对象与状态流转 | ForgeLoop业务模块和权威写入端 |
| 相关经验 | 来源、条件、候选／已验证范围／失效关系 | ForgeLoop维护，并由实际反馈核对 |
| 真实执行与证据 | 关联会话、代码、正式测试、审查和产物 | 宿主执行能力与ForgeLoop规则协作 |
| 团队共享 | 成员身份、最小角色、版本冲突和幂等 | 团队业务端；不能假定插件安装自动提供 |
| 展示和分发 | 插件bundle，按需要组合宿主配置 | 复用DSH能力，实际兼容另验 |

核心业务规则建议保持为可独立测试的普通模块，不为潜在的其他宿主先建设通用Runtime框架。用户操作仍在DSH中完成；共享服务是多人协作职责，并不要求另外创造一套完整Agent产品。

DSH的goal／todo可以作为当前会话的工作投影，引用项目工作项身份；项目完成状态由对应验证与验收确定。不能因为模型勾选todo或宣告goal完成，就自动把研发需求记为已验收，也不应让用户手工维护两份相互独立的计划。

## 7. 多人协作与数据归属

推荐首试采用单节点权威业务端，数据可存其本机SQLite；成员本地DSH插件通过业务接口访问。若DSH插件可直接提供所需接口，可以在服务器DSH宿主内承载，具体实现先验证，不预设一定要新进程或新服务框架。

SQLite允许服务器应用访问同机数据库并向远程客户端提供业务接口；多人访问的正确性仍需由认证、事务和版本核对保证。[SQLite官方说明](https://www.sqlite.org/whentouse.html)

| 数据 | 建议的归属与权威 |
| --- | --- |
| 当前需求、任务包、批准、分配与交付 | 团队业务端的一份权威状态 |
| 规则、重要决定、技能和测试定义 | 项目明确指定的版本化来源，关联批准快照 |
| 原始改动、CI与外部成员贡献 | 保留真实来源与身份，经规定方式核对后引用 |
| 共享经验 | 项目范围内维护效力、来源和修订，成员按权限取用 |
| 个人草稿、上下文缓存及临时探索 | 本地状态，不隐式取得团队批准效力 |
| 支撑验收的记录与产物 | 授权成员能够回查，不能只存在于某个人磁盘上 |

成员对需求更新应携带预期版本，批准和执行时核对当前状态；任务占用与副作用动作需幂等。断网时可保留草稿、分析或明确允许的本地工作，不能以本地缓存批准新的共享副作用；回连后的冲突需显式处理。

不采用同步多个成员的SQLite文件来合并权威状态，也不要求多人直接打开共享盘上的同一个数据库。高并发写、多实例或高可用需求明确后，再评估其他存储，不因代码库规模提前迁移。

首版仅需覆盖试点所需的项目管理员／维护成员／审查批准权限；不同时建设复杂组织层级、跨组织授权、计费和企业身份平台。具体角色及能否职责兼任，应按项目规则确认并在服务端落实。

## 8. 经验如何进入工作

经验维护的建议闭环是：实际执行与人工反馈 → 提炼候选 → 核对来源和条件 → 按类型进入案例／技能／脚本／测试 → 在后续工作中取用 → 观察效果并修订或失效。

每条经验至少能够解释来源事件、适用范围、建议做法、已知反例和当前效力。关键阶段按工作项提供少量相关材料，避免每轮装入全部历史。

权威事实、业务规则和策略建议分开维护：观察到一次失败，不自动产生新的永久禁令；模型总结不自动修改产品目标、批准或正式验收。稳定且可判定的规则可以在已授权范围内固化为代码检查。

首版可以使用现有记录、简单检索和人工纠正。参数强化学习、复杂图谱、通用本体与策略自动晋升均不是首个闭环的必要条件。后续只有在反馈可信、比较基线和净收益明确时，才扩展学习机制。

系统工程、DDD与本体等方法作为表达目标、边界、术语和关系的工具按场景引入，不作为用户接入前必须完成的全量建模工作。

## 9. 首版范围与验收对象

以下是新路线建议的验收清单，不是旧需求编号的替代，也不是实现文件授权。

| 项 | 必须展示的业务行为 |
| --- | --- |
| 项目接入 | 固定DSH版本下安装并绑定一个真实项目，能识别规则来源与未知信息 |
| 稳定工作项 | 一项需求跨会话保持身份和修订，任务与当前任务包关联 |
| 上下文接手 | 第二名成员能看到当前目标、有效规则、已做事项、前置产物和待复核依据 |
| 业务批准 | 服务端核对成员权限、版本和范围；旧批准与过期写入被拒绝 |
| 候选与验证 | 真实改动、正式测试、独立审查和产物按身份关联；外部来源如实标记 |
| 团队协调 | 两名成员参与同一需求，冲突和重复请求有确定性处理，不串项目 |
| 中断处理 | 保留不确定现场，核对前不盲重放；不承诺首版无损自动续跑 |
| 最小经验闭环 | 一项实际纠正被保存为有条件经验，后续任务能取用，反例可使其降级或失效 |
| 可回查 | 关键决定和证据可由有权限成员检查，插件更新不隐式丢失记录 |

首个验证不包括通用多Runtime、完整项目管理替换、所有入口双向同步、自动部署运维、大规模多Agent调度、复杂企业权限与全量架构建模。它们作为后续候选，不能未经效果验证一并扩建。

上述取舍仅定义新路线的验证优先级；现有邮件、发布、部署、PI适配等能力本轮没有被取消、删除或重新验收。

## 10. 与原生功能及现有工具怎样区分

| 基线 | 应复用的能力 | ForgeLoop须证明的增量 |
| --- | --- | --- |
| DSH goal／todo／会话／skills | 单会话目标、计划、上下文和执行 | 项目内跨人跨会话的业务身份、有效性与交付衔接 |
| 项目文档与AGENTS | 人可读说明与已有约定 | 在需要时提供相关且仍有效的依据，并用机器约束确定性规则 |
| Git／CI／Issue／ADR | 改动、验证、需求来源与历史取舍 | 减少跨工具查找和关系失效造成的接手／验收成本 |
| 成熟需求追溯与交付治理产品 | 已有结构化流程与证据能力 | DSH内采用成本、实际净收益和适用人群；不能仅靠新增数据库证明优势 |

若少量文档和CI检查已解决问题，应采用简单做法。原生DSH已经充分覆盖的单会话能力，应减少重复实现。产品边界应由真实用户下一项决定需要什么支持，而非模块数量确定。

## 11. 对现有工程的处理建议

| 现有资产 | 建议处理 |
| --- | --- |
| 需求版本、批准、失败与交付绑定规则 | 保留业务语义与负例，先评估复用，再决定语言与落点 |
| 真实验证与原始记录 | 保留来源和身份；迁移时不补造历史或改写执行来源 |
| PI／DSH协议适配 | DSH原生路径验证后再评估收缩；本轮不删除已跑通能力 |
| LangGraph业务图／检查点 | 列明实际职责，再与DSH会话及业务状态逐项映射；不能直接视为等价 |
| 独立CLI／页面／邮件 | 可用作迁移核对依据；DSH新入口先验证，避免长期维护多份状态 |
| 发布、部署与运维 | 保留现状与已有结论，暂不作为新插件首个效果目标 |
| SQLite记录 | 保留项目归属、身份与可回查关系，团队访问需明确唯一权威写入端 |
| Python核心 | 先核算可复用程度和分发成本；不预设全部重写TS或长期双实现 |

方向确认后，具体迁移应另列文件范围、数据迁移与回退、行为保持和验收计划，并按[贡献规范](../CONTRIBUTING.md)及[研发纪律](development-discipline.md)同步架构与契约。研究提案本身不改变当前实际架构。

## 12. 验证路线

### 阶段A：宿主可行性

在固定DSH版本中验证插件入口、上下文、业务工具、真实执行与证据获取。记录所依赖API与profile组合，不将master文档能力视为本机已验收能力。

### 阶段B：需求跨会话

一项真实需求经过两次会话和一次修订，当前目标、任务包、批准与候选能正确衔接。修订和材料替换的拒绝侧也须运行验证。

### 阶段C：最小团队协作

至少两名真实成员分别开发、接手或验收。允许其中一人继续使用原工具，但必须验证身份与证据进入权威业务端的方式。并发修订、重复请求、权限拒绝和断开后的处理可观察。

### 阶段D：经验复用

在后续真实需求中复用一项经核对经验，并引入一次条件变化或反例，检查是否能及时提醒复核，而非机械沿用旧结论。

### 阶段E：外部采用与商业验证

选择具有相同问题的外部项目，与正常配置的DSH＋文档＋Git／CI／Issue／ADR比较。看真实重复使用、完整成本和明确预算，不据安装量、赞同愿景或免费演示推断付费。

这些阶段是建议的验证顺序，不构成排期、预算消耗、人员安排或外部接触授权。

## 13. 衡量产品结果

| 维度 | 应观察的指标与材料 |
| --- | --- |
| 接手是否正确 | 未参与实现者解释当前要求、有效规则、批准和未知项的准确性及耗时 |
| 交付是否可信 | 误接纳、漏验、候选与测试错配、失效批准被沿用等真实事件 |
| 过程是否顺畅 | 重新澄清、人工重建历史、重复操作、误报处理及总等待 |
| 接入是否可接受 | 从安装绑定到首次产生可核查结果的步骤、耗时和所需人工整理 |
| 是否产生净收益 | 接入、录入、维护、模型、审查与返工的完整成本，与基线分别比较 |
| 团队是否愿采用 | 在下一项真实需求继续使用，维护者能带入另一位成员参与 |
| 商业是否成立 | 有预算主体愿为明确收益承担试点费用，后续交付和维护可重复 |

先约定任务、评分依据和最低可接受收益，保留失败与人工帮助；小样本先报告具体情景和不确定性。不能通过降低验收或删除基线材料制造改进。

如果只有更多报告、重复数据库和提醒，实际接手与审查负担未下降，应收缩功能。若正确性不足、维护负担超过节省，或外部没有重复使用，应停止平台扩张，重新选择场景。

## 14. 分发与商业路径假设

建议先以一个DSH bundle承载体验，项目级数据可检查、可迁移；团队共享能力用一个明确部署方式试点。单人本地可作为同一业务能力的试用情景，不同时打造多套后端和管理平台。

团队协作、长期证据和交付支持可能形成商业价值，但当前没有足够证据确定价格、计费单位、托管或自托管的最终模式。首试可以评估单节点自托管团队端的接入与维护成本，再决定是否建设托管服务。

官方[README](https://github.com/deepseek-ai/deepseek-harness/blob/master/README.md)提供dsh-plugin topic发现路径，并明确开发预览阶段的兼容变化；它不提供本产品目标用户规模、留存或收入证据。

公开分发前需按现有[贡献规范](../CONTRIBUTING.md)明确项目许可；本提案不决定开源方式、收费模式或公开发布时间。

## 15. 必须验证的假设

- DSH用户中存在足够频繁的跨会话／跨人长期项目问题，且愿意引入受管工作项。
- 一名维护者接入即可产生收益，不需要先完成全团队工具迁移。
- 团队愿意提供实现该场景所需的代码、需求和验证访问，并接受共享权威状态的维护责任。
- 原始依据与经验质量足够，相关上下文不会经常过期、误导或增加理解成本。
- 插件集成、宿主升级和共享服务成本小于节省的工作。
- 收益能在另一个项目复现，并有明确预算主体愿意持续采用。

这些均不能由DSH插件API存在或ForgeLoop已有单用户闭环推出。多人身份、运行恢复、隔离和跨版本兼容必须按实际部署验收。

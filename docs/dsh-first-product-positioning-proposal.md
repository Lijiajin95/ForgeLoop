# ForgeLoop：从 DSH 插件出发的产品定位草案

日期：2026-10-20，Asia/Shanghai。

**状态：定位草案，非已批准实施需求。** 本文响应所有者“基于 DSH 插件重新思考整个项目目标、定位、用户”，并按要求分别分析个人／独立开发者、中大型项目中的研发小组、企业研发平台／管理团队三条路线。三者是待选择的产品方向，不自动组成个人版、团队版、企业版的开发顺序。后续关于无服务器、分布式多人研发的讨论已暴露纯本地插件路线与团队目标之间的条件冲突，更新后的判断见第 9 节；没有因此自动选定个人路线。本文不改变当前 PRD、领域术语、架构契约、代码或运行授权，也不承诺重写、上线或公开分发。

## 1. 先定义产品问题，再决定保留哪些代码

DSH 插件是接触用户、参与开发和分发能力的载体。它能减少自建通用执行与交互基础的工作，但不能单独回答 ForgeLoop 为什么值得安装、每天何时使用、谁愿意引入以及效果如何判断。

产品目标优先于插件形态。若主要服务多人、跨机器的研发协作，就需要为共享决定及受控动作选择有效的权威与协调机制；它可以复用既有 Git／CI 平台，也可以由团队节点承载。每人独立运行、各自本地数据库、没有共享权威的组合，不能仅靠事后数据合并实现全局授权、共享额度和互斥发布。不能为了坚持纯本地插件，未经明确选择就把团队目标改成个人工具。

建议把共同研究问题改为：

> 个人或团队使用 Agent 持续修改一个已有软件时，如何让当前需求、项目约束、候选实现、验证结果与交付决定持续一致，并使使用者容易判断下一步？

这是候选问题定义，不是已经完成市场验证的需求。个人更关心“少操心地得到可以验收的结果”，小组更关心“交接和合入时知道哪些事实有效”，企业更关心“项目制度能否一致执行且可以解释例外”。不能用同一套重流程同时满足三种预期。

本文中的“需求版本”“候选”“证据”“有效”仅为草案工作定义，不修改 [现行领域语言](../CONTEXT.md)。证据关联与版本核对可以说明出处、身份和适用条件，不能证明验收标准完整或软件无缺陷；本地文件和 SQLite 也不天然不可篡改。产品应区分通过、失败、未知、过期，并将模型推断的关联与实际执行结果分开呈现。

现有代码不决定新产品边界。LangGraph、SQLite、邮箱、独立 CLI、运行时切换、常驻运维，以及既有审批步骤，都必须在路线选定后逐项判断其用途、复用条件和维护成本；既不预设全部保留，也不以插件化为理由全量重写。

## 2. DSH 已有能力与产品差异的最低要求

核查范围为 DSH 官方文档及其官方参考仓库。参考仓库路径为 `/Users/lijiajin/Project/references/deepseek-harness`，本轮读取时 HEAD 为 `687f282e8625c6b8d11ff58211a90524be2e4317`；同时核对当日可读官方 master 文档。两者未经版本等价性验证，以下是能力与边界研究，不能视为 ForgeLoop 已集成、安装版本已支持或真实场景已验收。

| DSH 原生能力 | 对 ForgeLoop 定位的约束 |
| --- | --- |
| 插件化模型、工具、Agent 循环、Session 持久化、命令和 Web 扩展 | 通用执行器、会话界面、日志和工具注册不适合再作产品核心 [S1][S2] |
| 同会话 goals：持久目标、revision、暂停／阻断／完成、轮数上限 | “目标可以持续推进和恢复查看”本身不足以形成差异；业务需求完成与目标状态的关系仍需定义 [S4] |
| 实验 Agent Teams：成员、共享任务 DAG、owner、CAS revision、消息 | 再造多 Agent 任务板或委派循环不够；文档的成员身份是 Agent／Session，不能据此推定多人组织权限已满足 [S3] |
| jobs：任务所有权、运行／停止／结算和 Session 生命周期记录 | 复用后台执行与观察；结算缺失保留未知，turn 结束不能自动等同所有工作停止 [S5] |
| 单次动作 approval、失败关闭的 outcome 与审计事件 | 复用动作许可接缝；“某次工具获准”与“某个需求版本获业务批准”需要显式关联 [S6] |
| 插件安装、组合、启停、Web 管理和兼容性准入 | 分发与体验可以复用，但安装入口不等于已有稳定用户来源 [S7] |

官方参考仓库还已有 skills、实验 worktrees 和回合级变更／文件展示，分别可从 `docs/subsystems/skills.md`、`worktrees.md`、`deliverables.md`回查。因此提示词包、分支创建、diff 展示、声明交付文件都不能独立支撑“新研发系统”的定位。需要核查具体接缝时再深入这些官方模块，而不是在本轮扩写插件清单。

**候选差异价值是跨会话、跨修改、跨参与者的交付一致性。** 最小可观察结果应是：审查者能从当前需求追到候选代码和实际证据，能看出哪些依据因变更过期，并据此作出有效决定。它是否足够有用，必须与原生 DSH、Git 平台和轻量规范的组合比较。

需要认真比较的现成替代还有：

- [Spec Kit](https://github.com/github/spec-kit)：已包含规范、计划、任务、实现与 converge，还提供缺陷修复、想法评估、扩展、工作流和私有目录等机制；不能将其概括成“只生成需求文档”。
- [Superpowers](https://github.com/obra/superpowers)：已有需求讨论、计划、worktrees、子 Agent 或同会话执行、TDD、分阶段审查及完成验证；不能将其概括成“没有验证和证据的提示词”。

ForgeLoop 可以提出“自动关联某个需求版本、某个候选代码版本与真实执行证据，识别失效／缺失／未知，使接手者少重新推断”的差异假设。现有资料不足以宣称该能力独有，也不能证明用户愿意为它另装工具。若现成工具稍作配置即可达到同样效果，优先考虑集成、贡献或缩小产品，而不是靠命名另建平台。

## 3. 路线一：个人／独立开发者的持续交付助手

### 用户、目标与价值主张

- **首批使用者假设**：已经使用 DSH，具有必要工程判断，在真实已有项目上持续开发，愿意核对需求与验收结果的独立开发者或个人维护者。
- **采用和付费决策者假设**：使用者本人。尚无付费意愿、预算或市场规模证据。
- **核心目标**：隔一段时间再回来时，用户能直接判断软件做到了什么、哪些还不确定，以及哪里需要自己决定。
- **价值主张**：把一段自然语言目标推进为有验收依据的候选改动，同时保留中断和返工后的有效上下文。

用户问题假设是：会话很多但项目状态难以确认；Agent 自评完成与实际需求有差距；下一次会话重复理解问题；已经通过的功能在后续修改中回归。只想快速生成代码片段、一次性演示或完全不愿审阅输出的人，未必适合首批用户。

### 核心旅程与最小闭环

1. 在已有仓库安装插件，识别现有测试、构建和项目说明，用户修正识别错误；不要求先建立组织或迁移任务系统。
2. 输入一个实际改进目标，确认少量可观察的验收条件和必要约束。
3. 复用 DSH 开发与工具执行，按任务风险决定检查节点；相关功能可以连续实现，不强制每小步结束一次 sprint。
4. 插件呈现固定候选的改动、已执行验证、需求覆盖和未确认事项；代码改变后标记受影响的旧证据。
5. 用户选择接受、要求补充或继续修改；形成能在下一次会话直接续用的结果记录。

**MVP 验收**：单仓库、单需求完成一项真实改进；用户直接查看当前候选的验收缺口及真实证据；跨会话续接先检查旧证据是否适用，过期证据不会被展示为当前已通过；用户能实际运行并验收；未知和跳过没有被填成成功。这里复用 DSH 会话恢复，新增的是交付依据的有效性核对。首版不要求无人值守数天、不自动上线，也不因旧系统已有能力就加入邮件、跨 Runtime、组织审批和主动运维。

### 部署、复用与采用

单机插件＋本地记录足以支撑这一方向，记录可以是文件或本地数据库，格式服从追溯和升级需要；数据私有、本地优先可作为个人价值假设，是否影响采用仍需验证。用户需要导出可分享的结果，而不是复制完整会话数据库。DSH 负责执行、Session 和交互；Git 保存代码身份，现有测试负责行为验证。独立检查可以由另一会话承担，但必须说明它实际检查了哪个候选及什么范围。

推广假设是通过可复现案例、安装示例和 DSH 插件发现入口获得试用；收费可探索持续交付能力、托管便利或支持，但不得据此预设用户愿为流程付费。

**最大风险**：原生 DSH 加项目说明、skills 和测试已经够用；额外文档和决策步骤打断开发；因设计得过于通用而比手工操作更难。验证应观察用户是否愿意再次使用、是否少翻旧对话、能否明确验收，以及插件带来的等待和困扰；费用与时延可辅助解释体验，不恢复已撤销的强制人工工时／ROI 门槛。

## 4. 路线二：中大型项目中一个研发小组的变更与验收协作

### 用户、目标与价值主张

- **首批使用者假设**：在已有代码库、Issue／PR 和 CI 中协作的小组，已有多人或多个 Agent 并行开发，并出现需求变更、交接、重复工作和验收依据失效的问题。项目规模不直接等于使用者规模。
- **日常使用者**：开发者、审查者、测试或产品验收者；不要求每个角色都学习 DSH 的所有功能。
- **引入决策者假设**：技术负责人／项目负责人；预算负责人可能不同，需访谈确认。
- **核心目标**：让一项跨人跨会话的改动，从需求到合入保持同一组有效事实，减少遗漏、交接歧义和错误验收。
- **价值主张**：在现有开发流程中给出清楚的候选与证据，提示变更造成的失效和依赖影响，帮助团队作出可信交付决定。

产品首先服务一项具体变更，不接管组织全部任务和日程。进度不能仅由“Agent 忙不忙”或“子任务是否打勾”决定，需要同时呈现需求覆盖、候选版本、依赖、阻断和仍缺的证据。

### 核心旅程与最小闭环

1. 从既有 Issue 或需求材料启动，关联需求版本和验收条件，明确谁负责需求解释、实现和最终决定。
2. 识别项目中已有约束及受影响区域，开发者确认分工和交接产物；实现可以由人、DSH 或其他已授权工具完成。
3. 多条开发线产出候选，插件自动关联 PR、提交、实际测试和审查；对依赖不满足、需求版本冲突和证据过期给出具体提示。
4. 审查者查看“当前候选满足了什么、证据是否对应、遗漏什么”，在团队既有可信入口决定补充、批准或拒绝。
5. 通过平台合入规则完成整合，保留该需求最终交付了哪些代码、检查和决定；新的改动不能静默继承旧通过结论。

**MVP 验收**：一个真实小组在一个仓库完成一个真实 PR，覆盖负责人、开发者、审查者的交接；建立验收条件→commit→真实 CI／测试→人工决定的可回查关系，Git 平台继续控制合入。负例为 A 已改为 v8，B 仍查看 v7 证据：必须标明过期或拒绝把旧证据当成 v8 通过；重复事件按对应业务动作幂等处理，并行决定冲突或连接中断导致的结果不明须明确呈现，不静默覆盖或推定成功；负责人不必手工重复维护第二张任务板才能判断结果。首个 MVP 可选择辅助已有合入流程，不必同时实现跨机无人值守执行或 ForgeLoop 服务。

### 团队权威与本地数据库

**先决定谁拥有哪项业务事实，再选择数据库。** 推荐从以下两种方式中选一个验证，而不是默认先建设服务器：

| 方式 | 权威事实 | 本地记录的职责 | 适用前提 |
| --- | --- | --- | --- |
| Git 平台协作优先 | Issue／需求记录、PR、提交、审查与必需检查；ForgeLoop 导出或提交相应记录 | 缓存、个人会话、临时执行现场和待同步数据 | 插件主要辅助准备与验证，既有平台负责合入；暂不跨客户端自主领取或共享预算 |
| 团队协调节点 | ForgeLoop 新增的共享领取、业务批准、额度与执行状态；Git 仍拥有代码和原生审查事实 | 可丢弃缓存、执行日志和离线草稿 | 确实需要跨客户端推进、共享额度、独立于个人电脑的持续执行 |

第一种方式也必须明确需求版本、候选绑定、并发决定和权限如何落实，不能把 PR 评论文字天然当成安全账本。平台原生审查不自动覆盖 ForgeLoop 的所有业务规则；若所需规则无法通过平台可执行机制表达，应缩小承诺或选择第二种方式。

第二种方式允许数据库位于团队节点本地磁盘，客户端通过经认证的业务接口访问；“本地”指服务节点的位置，不是每个成员独立批准。共享数据库文件、Git 同步 SQLite 或会话摘要同步，都不能代替并发授权判定。备份、恢复和可用性责任也必须有明确承担者。

DSH Agent Teams 可以参与单个执行过程，不能直接当作人类团队的身份目录或跨个人客户端协作账本。原生文档中 `writeScopes` 是建议路径前缀，不是写锁；任务 owner 与 CAS 也不自动提供仓库合入和组织职责分离。[S3]

### Git 平台分工、采用与风险

Git 平台继续承担代码、PR、原生审查和 CI 准入。以 GitHub 为已核实示例，受保护分支支持必需审查、必需检查、旧批准失效和合并队列；具体是否可用及如何配置应按团队仓库条件验证，不直接推及所有 Git 平台。[S8]

推广假设是由技术负责人在一个仓库试点，通过真实协作案例扩展到相邻小组。收费可以围绕团队共享记录、管理与支持提出假设，不能把仓库数、席位或执行次数直接定为最终计费方式。

**最大风险**：与 Issue／PR／CI 重复记账；开发者获得流程负担而收益主要给管理者；所有人必须换工具才能用；“统一状态”掩盖异步和外部修改。应验证端到端交接是否清楚、审查者能否依据真实证据判断、变更后是否暴露失效、普通开发者是否愿继续使用；允许外部工具参与并记录来源，不恢复排他提交要求。

## 5. 路线三：企业研发平台／管理团队的工程保障能力

### 用户、目标与价值主张

- **实际使用者假设**：研发平台工程师、架构／质量负责人、安全治理人员，以及被接入的研发团队。
- **引入和付费决策者假设**：平台负责人、研发负责人或组织采购方；用户与决策者通常需要分别验证，尚无采购证据。
- **核心目标**：在多个项目和多种执行来源中，把选定工程要求变为可执行、可说明、可回查的保障，允许有依据的例外。
- **价值主张**：连接项目目标、架构／工程约束、执行事实和交付证据，让组织知道哪些要求落实、在哪里失效、由谁处置。

这条路线中的 DSH 插件更接近开发者入口；产品价值更多来自共享服务、平台接缝、策略生命周期和证据使用方式。因此它不能仅凭“装一个插件”就宣称企业级治理已具备，也不适合在没有实际设计合作方时先建设通用平台。首版不默认多租户 SaaS，也不要求全员替换开发工具。

### 核心旅程与最小闭环

1. 选择一个真实项目、一条重要工程规则及其风险场景，例如禁止越层依赖、某类变更必须经过指定审查，或候选变更后必须重验关键行为。
2. 平台负责人指定规则所有者、适用范围、版本、例外审批和实际执行入口，研发团队确认操作方式。
3. DSH 插件提供及时反馈并收集相关事实，CI／服务端准入承担跨工具的强制执行；远程决定由组织身份与权限确认。
4. 对新需求或代码变化，指出规则、证据和决定的影响；失败或例外有可回查原因，升级规则后能判断哪些项目需复查。
5. 负责人抽查真实交付，从目标追到规则版本、候选、执行结果与例外，研发团队能解释并修正问题。

**MVP 验收**：一个部门在已有平台中选择一条已存在的准入制度，把制度版本、批准身份与证据绑定到真实合入或部署入口，接通通过／拒绝／例外路径。DSH 插件仅是入口之一，外部工具提交同样受纳管最终入口校验；插件禁用时不把可跳过本地提示当成强制保障；升级规则或变更候选后能够正确处理旧证据。没有真实试点和预算方时不扩建通用平台；首版不追求全组织、全语言、所有合规标准或统一架构总分。

架构属性可以成为规则来源之一，例如“可恢复”落实为中断场景和无盲目重放性质；PBT、静态依赖检查、负载测试或人工评审分别提供证据。不能把所有架构属性都转成 PBT，也不能从测试通过推出需求完整或企业风险已清零。

### 部署、复用与采用

共享权威和执行控制应接企业现有身份、Git 平台、CI、制品与审计设施。开发者本地状态主要用于体验和断线缓冲；只有共享入口确认的决定才影响组织状态。DSH 继续提供执行与交互，ForgeLoop 聚焦业务规则、证据关系与适用范围，不自研一套模型服务、员工目录或通用代码托管。

企业可能要求私有部署、权限分层、保留期限、敏感信息处理、备份恢复和升级兼容。它们是该路线的待验证产品要求，不能从个人版自然推定已具备，也不能在当前阶段直接宣布全部进入范围。

推广与收费假设是设计合作、私有部署与服务支持，最终需要确认谁有预算、是否接受 DSH、怎样采购和维护。不得用“企业需要治理”代替具体购买理由。

**最大风险**：销售与接入周期长；各组织制度差异巨大；先做配置平台后仍没有核心用户；DSH 只是若干执行工具之一，绑定单一生态限制采用；用高层指标制造虚假安全感。验证重点是规则是否在真实动作入口生效、证据是否可用、研发者是否能顺利工作、平台方是否愿持续维护；不预先设定强制 ROI 或人工工时门槛。

## 6. 三条路线的选择冲突与迁移边界

| 决策维度 | 个人 | 研发小组 | 企业平台 |
| --- | --- | --- | --- |
| 主要产品结果 | 一个目标有可验收候选 | 一项跨人变更可交接、可合入 | 一组工程要求在多个项目可信落实 |
| 权威范围 | 单人项目记录 | 项目协作事实 | 组织制度、项目与例外 |
| 默认体验 | 直接使用，少配置少打断 | 嵌入现有协作，避免二次维护 | 可管理、可追查、适配既有平台 |
| 引入者 | 本人 | 技术负责人和参与小组 | 平台／研发负责人及采购链条 |
| 最大替代压力 | 原生 DSH＋skills＋测试 | Issue／PR／CI＋团队约定 | 既有平台、安全与质量设施 |
| 产品主要难点 | 比原生体验更有用 | 多人事实、责任与证据一致 | 跨项目强制、例外与运维责任 |

三条路线可共享需求版本、候选身份和验证结果等少量概念，但不能为了兼容全部未来用户先建通用工作流引擎。个人使用成功只证明个人场景；团队采用需要另外验证多人权限、协作状态和交接；企业采用还需另外验证组织策略、部署和管理责任。

个人记录升级到团队权威，不能把历史自批提升为组织批准；团队证据进入企业环境，不能把旧规则结果当成新政策通过。迁移必须明确来源、适用范围和缺失项，导入记录不会追溯产生授权。

## 7. 共同产品原则与分工

1. **先识别用户要作的决定。** 产品主界面突出当前目标、候选、缺口和需要谁处理；不以 Agent 数量、Token 消耗或内部阶段名称作主要价值表达。
2. **连续开发与验证粒度可调整。** 保留有意义的验收和授权边界，按风险和反馈决定何时检查，不把固定 sprint、每步独立 QA 或全程无人介入当作产品原则。
3. **证据跟随具体版本。** 需求、代码、环境、规则和测试结果建立可回查关系；明确证明范围与失效条件。发现变更不等于所有旧测试一律失效，也不能无条件沿用全部旧证据；无法确认适用性时标为待复核，不自动视为当前已通过。
4. **先复用权威事实。** DSH 拥有运行时事实，Git 平台拥有代码与原生审查事实；ForgeLoop 只维护新增业务关系和自身规则，展示引用、同步延迟与冲突，不虚构单一万能账本。
5. **硬规则进入动作入口。** 插件提示或模型自觉不能代替受保护分支、服务端准入、隔离与业务校验。对暂未强制的规则如实显示，不宣称已保障。
6. **允许人和其他工具参与。** 记录实际来源和补救；优先兼容现有协作，未安装插件的审查者也应能通过团队原有入口查看必要材料。
7. **逐步解释复杂度。** 先完成一条真实闭环，再根据观测痛点增加规则；长期愿景不自动成为当前功能清单。

## 8. 价值验证与推进条件

三条路线应各自选择真实问题开展试点，明确任务来源、参与者、运行版本、环境、原始结果与未覆盖情形。尚未访谈或试用的内容保留为假设，不把自身 DogFood 写成外部用户证明。

| 验证问题 | 观察证据 | 何时重新考虑定位 |
| --- | --- | --- |
| 是否得到可验收软件 | 实际运行、需求覆盖、回归、独立检查和最终用户决定 | 状态漂亮但用户仍不能验收 |
| 是否让协作更清楚 | 交接材料、失效提示、重复工作或冲突事件的实际处理 | 用户要重复维护多处状态，仍需翻完整对话 |
| 是否容易采用 | 安装、接入、失败恢复、日常使用反馈与再次使用 | 采用成本长期超过用户感知收益 |
| 核心保障是否可信 | 版本漂移、重复请求、中断、旧批准、外部修改的真实负例 | 只能依赖提示词避免违规或未知被当成功 |
| 是否超出原生组合的价值 | 与同项目原生 DSH＋既有文档／测试／Git 流程比较 | 轻量配置就能以更清楚方式获得同样结果 |

费用、时延、等待和人工补救可以按使用者同意的方式记录，用来解释质量与体验；**不恢复所有者已经撤销的强制人工工时测量、30 小时上限或 ROI 验收门槛**。不凭少数任务得出普适效率提升结论。

分期采用可验收条件，不承诺日期：

- **定位验证**：分别找出三类用户当前如何完成同一核心工作，确认哪个问题不能由现有工具轻易解决，再选择一个首发方向。
- **单场景闭环**：在所选方向的一项真实任务中，让用户实际使用需求—候选—证据—决定关系；完成失败和过期证据场景，不先搭全套平台。
- **重复使用验证**：在新的任务、第二位使用者或第二个项目中验证可复用性与接入成本，按该路线自己的要求扩展。
- **产品化**：在需求与责任边界稳定后完善版本兼容、支持方式、数据迁移、升级与恢复；任何公开试用或分发之前先确定许可与可公开内容，企业能力单独确认范围。

## 9. 暂定选择建议与必须保持开放的问题

**修正此前的“小组路线优先＋整体插件化”建议：不能在未解决共享权威与协调机制之前，把纯本地 DSH 插件作为团队产品的完整形态。** 分布式协作讨论说明，需求与证据可交换，不等于批准、额度、执行占用和发布可以在多个离线节点上各自生效后再合并。

需要分别评估以下两种取舍，而不是自动改变用户目标：

| 优先保留的目标 | 合适的产品职责与形态 | 需要接受的条件 |
| --- | --- | --- |
| 中大型项目中的多人、分布式研发协作 | 独立定义团队业务规则和共享事实，DSH 作为首个入口与执行接入；共享权威可复用既有 Git／CI 平台，缺口再由团队节点承载 | 不能省略身份、并发决定、证据与候选绑定、恢复及交付准入；插件化不自动消除这些工作 |
| 纯本地安装、较低接入与运维负担、优先借 DSH 生态传播 | 单一负责人驱动的持续研发插件，在一个明确的记录与执行权限范围内工作 | 这是产品目标的收窄；可参与团队仓库，但不承诺承担全团队的共享授权、跨节点调度和发布互斥 |

DSH 插件本身并不排斥团队能力：插件也能承载共享业务模块或作为客户端。但一旦承担跨用户的共享职责，就必须验证相应的部署、身份和协调语义，不能继续以“每人本地安装便自然具备团队治理”描述产品。

**若仍以团队分布式研发为核心目标，建议保留该目标作为评估基准，重新选择插件的职责，而非为了插件形态改换用户。** 若最终明确选择纯本地路线，再按路线一验证单一负责人对真实项目需求的持续推进。项目规模、负责人数量和 Agent 数量分开考虑：单一负责人仍可维护中大型代码库，并使用多个 Agent；这不构成全团队协作能力的证明。

上述均为待选择方案，没有外部用户访谈、采用率或购买证据。三条用户路线的比较保留，但不作为同步开发清单。个人 DogFood 只能证明对应场景；企业路线仍需真实平台合作方、具体制度与部署责任。

### 放弃或转向信号

- 原生 DSH、Spec Kit／Superpowers 或既有 Git 流程已足以解决目标问题，新增插件主要产生重复操作：考虑集成现成工具或缩小独立产品。
- 真实使用者没有再次使用意愿，主要价值只能由开发者解释：回到问题和使用场景，不靠继续加功能挽救定位。
- 协作资料和审批维护负担超过用户感知的验收收益：减少记录、自动引用原始事实，或改为辅助交付材料而非接管流程。
- 企业不接受 DSH-only，而价值主要来自跨工具准入：重新评估插件是否只是一个入口，以及是否仍选择这条产品路线；不能未经确认自动扩成多 Runtime 平台。
- 证据无法可靠绑定候选、未知被当成功，或强制规则只能依赖提示词：停止宣称相关保障，先修复核心可信性或明确降低承诺。

仍需确认：首批用户实际使用 DSH 的条件；当前最痛的交付决策是什么；现有 PR／CI 和 skills 为什么不够；谁负责需求版本；谁认可最终证据；是否真的需要共享自主执行；什么信息可以上传或共享；什么失败会让用户停止使用。收费、开源许可、插件市场发现和组织采购均保留为假设。

## 2. 产品目标与首版范围（已确认）

### 2.1 产品目标

**ForgeLoop 面向需要软件但不懂研发的人，在客户确定的业务目标和授权边界内，通过多 Agent
完成软件建设、持续迭代与线上运维，并提供全过程可追溯的交付证据。**

客户掌握业务目标、预算与不可突破的边界，决定例外情况下的业务取舍。日常需求细化、任务拆解、
架构、实现、测试、验收和部署由 Agent 与工程工具完成，不要求客户逐项批准。
客户决定时看到方案、成本、优缺点、风险及推荐理由，不以阅读技术细节或判断代码正确性为前提。

“全 Agent 执行”允许人类处理明确的例外；不意味着把人类授权身份授予 Agent。
研发与运维最终分别考核少于 10% 的人工介入率，先验证闭环，再独立验收自主程度。

### 2.2 首版范围

| 维度 | 已确认范围 |
| --- | --- |
| 首个场景 | 从零建设 ForgeLoop，以 ForgeLoop 自迭代、发现问题、修复问题和优化自身作为 DogFood |
| 起点 | 外部 Agent 建设最小种子；随后由运行中的 ForgeLoop 承接自身真实需求，外部投入分别记账 |
| 软件规模 | 首先验证复杂业务与架构下的持续演进：多个业务域、真实依赖、跨模块变化、数据迁移、多轮兼容性和架构一致性 |
| 研发闭环 | 需求 → 分析与架构 → 任务 → 实现 → 测试与验收 → 部署 → 上线验证；各阶段可跟踪审计 |
| 运维闭环 | 运行反馈 → 独立处置事件 → 分析与止损 → 恢复验证 → 必要的修复需求 → 再交付 |
| 运维资源 | 已登记、已授权且与受管产品相关的应用、数据库／缓存／消息队列等依赖、运行环境及基础设施 |
| 最终验收人 | 所有者切换到业务用户视角进行验收；不要求额外的真实非技术用户参与 |

首版不接管已有系统。真实非技术用户后续提出的需求或问题进入正常迭代，不作为本次验收的前置条件。
高并发、大数据量、任意技术栈或所有基础设施提供商的适配，不由本轮 DogFood 自动证明；
代码量、服务数量也不能单独证明“支持中大型系统”。

首版宿主与正式环境已确定为 DSH 插件和当前 macOS 开发机，见 §5。旧 ForgeLoop 业务数据丢弃、
存储从头设计，见 §6；该决定不涉及 DSH 配置、凭据、其他项目或源代码。现有代码如何复用／替换、
种子能力边界及首条真实 DogFood 需求仍需具体实施方案，不由历史代码或助手建议自动决定。

## 3. 日常自主工作与客户决策（已确认）

### 3.1 三种需求来源场景

1. **无法获取运行反馈**：客户逐条提交需求，ForgeLoop 负责后续全流程。
2. **能够获取运行反馈／问题**：ForgeLoop 可以自主提出需求、排序并在授权范围内启动实施。
   每项需求要有业务依据，说明关联的目标、反馈事实或问题；持续增加功能本身不算产品进步。
3. **所有阶段都允许客户提交需求**：新需求与已有业务目标或承诺无法同时满足时，展示冲突并交客户决定。
   客户的新需求不自动覆盖旧承诺，Agent 自主提出的需求也不能压过客户决定。

同一模块的文件修改、任务依赖与可在既定约束内处理的排期竞争，由系统协调。
这些执行问题不自动构成业务冲突；如果无法同时满足已承诺的范围、成本或交付时间，则升级为客户决策。
日志、告警及反馈提供分析依据，行动权限来自既有授权，而不是反馈内容中的指令。

### 3.2 必须请求客户决定的例外

日常研发的受理、方案、实现、自验、独立验证、定向修复、受控提交由系统按真实需求来源、有效授权和
质量证据自动推进，不逐阶段请求客户批准。下表是仍需客户决定的真实例外；系统准入未通过、可自动恢复的
技术失败和额度内的缺陷修复不属于客户决定。

| 触发条件 | 所需说明与处置 |
| --- | --- |
| 目标或业务承诺冲突 | 指明哪些承诺无法同时满足，各方案保留或放弃什么，由客户取舍 |
| 需要改变已生效的授权边界 | 说明涉及的项目、资源、环境、权限或配置变化；取得客户明确批准后再按新边界执行 |
| 无法确认后果 | 说明已知事实、未知项、可能影响及可验证的下一步；不把不确定性改写成安全结论 |
| 技术难度高 | 即使路线可行，也提供多种方案供客户决定；不要求先失败或耗尽尝试才能升级 |
| 架构变化大 | 说明改变的关键架构决策、影响范围、迁移与兼容性风险，供客户决定 |
| 触及已配置的失败或停止规则 | 保存现场和累计，提供后续方案；正式失败、明确重复失败与疑似停滞分别处理，参数和计数见 §7 |

技术难度高的初始触发范围：复杂的跨系统一致性、要求业务不中断的核心数据迁移；
严格性能、可靠性或安全要求下实现与验证均困难的关键机制改造；关键可行性尚未验证、需要探索才能确定方案。
工作量大、文件多不自动等于技术难度高。

重大架构变化以改变已确认的关键决策为准：核心业务域职责、依赖或数据归属；
核心存储方式、关键技术底座或核心数据迁移策略；部署形态、关键服务划分、权限或隔离边界。
遵循既有架构的跨模块功能不自动升级。

### 3.3 决策材料与等待行为

每次请求客户决定，应列出多个可比较方案，说明业务效果、成本、时间、优缺点、风险、证据及推荐理由。
无法证明可行或缺少估算依据的部分必须标注；不为凑选项虚构可行方案。
客户可以理解取舍，无需先理解技术实现细节。

等待客户时，先执行已经授权的止损、回滚或降级措施，暂停待决动作及其依赖任务。
确认无关的工作继续；影响范围不明时扩大暂停范围。等待超时只触发提醒或预先约定的策略，
不视为批准，部分服务可能因此暂时保持降级状态。

## 4. 目标、架构和执行边界（已确认）

### 4.1 不漂移的含义

产品目标与硬约束不得被 Agent 擅自改变。架构允许有依据、可验证、可追溯地演进：
每次调整说明服务于哪个目标、为什么需要改变、影响哪些模块，更新设计依据并验证实现与设计一致。
历史决定保留版本和替代原因，不能通过改写文档掩盖代码偏离；重大变化仍执行 §3 的人工决策规则。

### 4.2 配置与强制执行

质量、预算、授权边界作为配置项，由客户根据实际情况调整，并通过确定性代码或工程准入执行。
控制规则的业务域与执行 Agent 隔离，执行 Agent 对生效规则只能读取，不能自行修改或绕过。
多 Agent 分析、审查和多种方法／工具提供证据；硬逻辑根据配置和证据执行放行或阻断。
模型一致认为正确不等同于业务事实已经证明，缺少判定依据不得冒充通过。

费用上限、失败暂停和执行超时的首版配置统一见 §7；更换 Agent、重试或重新拆任务不能清除既有失败记录。

客户调整配置时保存版本、来源和影响，既有失败记录不覆盖。
ForgeLoop 部署后，其自身配置变更必须取得客户明确批准；改变已批准边界也必须取得客户明确批准。
经批准的需求变更可以使原约束被新基线替代；BUG 使配置未能生效属于缺陷，需要追溯审查和验证流程，
不能用事后修改配置或记录将旧的越界追认为正常。

### 4.3 DogFood 的代码与运行边界

| 对象 | 边界 |
| --- | --- |
| 普通受管项目的 Agent | 修改 ForgeLoop 管理的目标项目，不因此取得运行中 ForgeLoop 的控制权 |
| DogFood Agent | 目标项目是 ForgeLoop 自身，可以产生自身代码改进候选；仍遵守相同执行边界 |
| 自迭代代码 | 候选开发不直接改动已部署的应用或生效配置；BUG 修复与改变需求分别记录 |
| 自动部署 | 由成熟软件工程工具约束，Agent 无法自行修改或绕过部署控制；发布证据对应实际运行版本 |
| 生效规则变化 | 无论通过配置还是升级代码改变已批准边界，都需要客户明确批准；普通代码升级不因此一律要求人工批准 |

角色权限方案见 §5，发布规则见 §8；具体身份、隔离与工具接线仍需实现和实测。业务域命名、提示词声明或目录划分本身，
都不是“执行边界已强制”的完成证据。

## 5. 宿主、协调与多 Agent 流程

### 5.1 技术结构与执行方式

| 项目 | 当前决定 |
| --- | --- |
| 产品宿主 | 使用 DSH 插件，复用 DSH 能力、生态和影响力；不采用独立 ForgeLoop 常驻后端方案 |
| 正式环境 | 当前 macOS 开发机，不先迁到 Linux 服务器 |
| 主宿主 | DSH Desktop；关闭窗口后台继续，真正退出后停止，再次启动核对恢复；休眠／关机期间不承诺继续执行 |
| 控制与执行 | 主 DSH 中的确定性协调器掌控业务状态与阶段推进，独立 DSH 子运行时承担 Agent 执行 |
| 动态规划 | Agent 提出任务、依赖、修复路径与结果；主控依据有效规则、授权、状态和证据决定推进 |
| 派发 | 首版由协调器统一派发；三个角色可以提出协作请求，不开放自行再创建子 Agent 的工具 |
| 实施并发 | 同项目代码实施先串行；等待客户的任务安全停稳并保存现场后释放执行槽位，其他可执行工作继续；只读分析／验证可独立安排 |
| 工作区 | 以业务需求为隔离研发工作副本与集成交付单位，同需求内任务串行共享代码进展；具体 Git／复制机制未最终选定 |
| 执行粒度 | 按阶段和研发任务分别派发执行；一次任务内部可以多轮推理、编辑、自验，不用一个研发会话包办整条需求 |
| 基线 | 版本化项目基线＋执行输入快照，绑定目标、需求、架构、验收、方案和代码依据 |
| 需求修订 | 修订生效后先停止受影响执行、保存并核对现场，再重规划和派发；已有材料经适用性核对可复用 |

会话结束、工具退出或 Agent 自述成功，都不直接等于业务交付完成。
停止请求与实际停稳分别记录，结果未知时不盲目重放；影响范围不明时扩大暂停范围。

### 5.2 四个 Agent 与自动交接

所有者确认的角色是**产品 Agent、研发 Agent、验证 Agent、运维 Agent**。阶段、函数和状态可以细分，
但不再新增分析、规划、实现前评审、逐任务审查、业务终审、诊断等独立 Agent 身份；同一身份可以针对
不同需求或事件建立独立会话，同一需求的研发过程应复用工作区与上下文。

| 阶段 | 负责 Agent | 输入／工作与输出 |
| --- | --- | --- |
| 需求澄清 | 产品 Agent | 接收真实输入，识别行业与业务背景，必要时查阅领域材料，澄清真正的业务歧义；输出绑定需求版本的结构化需求说明（目标、场景、业务规则、异常与边界、验收标准、非目标）。不规定文件清单或实现步骤 |
| 系统准入 | 主控（确定性判定） | 依据真实需求来源、所有者、有效授权、需求版本与需求说明判定；单独写入系统准入记录。系统准入不是人类批准，不写 `by=owner`／`approved=true` |
| 技术方案与实现 | 研发 Agent | 在需求级工作区读取代码与配置，一次完成技术方案、实现、测试、自验和修复；方案是工作记录，不是批准门禁；计划文件清单是预期，不是硬白名单；只改当前项目，不改变生效授权、凭据、其他项目或已部署应用，不递增版本 |
| 独立验证与业务验收 | 验证 Agent | 从需求说明独立设计正常、异常、边界与回归场景，可在研发期间准备；在独立环境执行固定候选；结论绑定实际执行、候选身份与可核对证据；缺陷自动形成回研发的工单。原独立审查与业务终审合并到该身份，不再由产品 Agent 做最终业务验收 |
| 受控提交 | 主控（确定性执行） | 验证通过后，在真实项目干净且基线一致时只整合本需求候选；运行配置的提交检查后创建本地提交并记录提交身份。不 push、不打 tag、不递增版本、不混合其他在途改动 |
| 发布与上线 | 运维 Agent＋主控受控入口 | 使用独立发布授权，核对候选包身份与实际运行内容，执行安装、上线检查、监控与授权内恢复；需超出授权时请求客户决定 |

正常路径：真实需求 → 产品 Agent 澄清并形成需求说明 → 系统准入 → 研发 Agent 方案、实现、自验
（同一工作区可定向修复）→ 验证 Agent 独立验证与业务验收 → 缺陷回研发定向修复并产生新候选 →
验证通过 → 主控受控提交。该路径不需要人工“批准技术方案、推进任务、开始验证、整体验收、允许继续修复”；
发布/部署仍使用独立授权，不阻塞已授权的研发、验证与提交。

实现自验与独立验证分开。验证 Agent 不得修改被验收候选或降低标准；研发 Agent 不得修改生效需求、
验收基线、权威业务库或已部署应用。业务取舍、范围冲突与授权边界变化仍由客户决定，测试争议处理见 §10.7。

### 5.3 角色权限

- 采用**Agent 身份＋工具白名单＋工作区范围＋确定性动作入口**。身份只有四种，不得用新 profile、别名或提示词重新引入子角色。
- 产品 Agent：读取代码、记录与领域材料，提交需求说明与受控文档候选；不得直接改实现代码、生效授权或质量规则。
- 研发 Agent：在需求级工作副本修改代码和测试，运行自验并定向修复；计划文件清单只是预期，执行范围是当前项目工作区；不得改变生效授权／验收基线与版本号，不直接提交、发布或部署。
- 验证 Agent：读取固定候选，在独立验证目录设计并执行自动化测试，产出命令、场景报告与业务验收结论；只写 `verification/` 等验证材料，不得修改候选、生效标准或生产环境。
- 运维 Agent：只在既有安装、检查、恢复与动作目录内工作；部署或生产变更使用独立授权和受控入口，不向其他 Agent 发放通用生产管理权限。
- 主控是确定性协调者，不是第五个 Agent；负责调度、自动交接、状态、准入与授权校验、身份／版本绑定、停止与恢复、失败额度、证据与提交整合。
- profile 与独立目录不等于完整 OS 安全隔离；现有能力不足之处须如实披露和验证，不能靠提示词宣称已强制。

## 6. 全新存储与一致性协议

### 6.1 新旧数据边界

所有者明确要求：**项目从头开始，丢弃旧数据，不复用旧存储方案。**
新库从空库和新模型开始，不承担旧业务库兼容、迁移或只读历史查询的产品要求。

此决定针对旧 ForgeLoop 业务数据，不能扩展为删除 DSH 模型配置、凭据、其他项目、代码或他人的在途工作。
截至本次文档整合，尚未执行业务数据清理；实施前明确实际清理路径和文件范围。新系统自身后续迭代仍需保留审计、失败历史并支持约定的兼容迁移。

### 6.2 状态、审计与证据提交

- **SQLite 保存权威业务状态与审计；文件保存证据和产物**。不以 DSH 会话历史代替业务权威记录。
- 状态表保存当前状态，业务事件只追加；**状态变化与审计事件在同一事务提交**。
- 主控写业务库，角色子运行时提交结果，由主控核对后接纳。
- **证据先封存，再由数据库登记引用、更新状态和追加审计**。主控核对所属执行、完整性与摘要。
- 已封存材料不能原位覆盖，变化产生新身份或版本；运行日志可追加，用于验收时固定快照。
- 文件存在但未登记：核对残留与执行记录，不直接认定交付。引用对应文件缺失或摘要不符：阻断依赖它的交付并保留异常。

- **系统准入与人类批准分开记录**：系统准入绑定需求版本、来源、所有者、授权策略与判定依据；
  不写入 `by=owner`、`approved=true` 或伪造批准行。人类批准只保留给策略明确列出的例外。
- **代码候选与提交分开记录**：候选绑定需求版本、任务包版本、基线、快照与 diff 摘要；新修复产生新候选，
  旧候选、验证报告与失败轮次保留。提交绑定候选摘要、真实项目提交 SHA、检查命令与日志，
  不把临时快照基线提交当作产品提交。
- **失败与修复不重置**：定向修复沿用原需求、原任务包与原工作区，只处理被验证缺陷；失败轮次不清零，
  旧报告与旧候选不删除。

### 6.3 外部动作与中断核对

- 执行前登记意图、动作身份、目标、版本、参数和授权依据。
- 同一次执行的重复投递复用身份；后端支持幂等键时传入相应身份。
- 重启或中断后先查实际结果，证据明确时自动收口或恢复；不因超时、进程退出就直接重做。
- 结果不明则保留待核对并暂停相关动作；核对结果、处理必要残留后才能开始新尝试。
- 数据库事务不能保证外部操作只发生一次，需要上述执行与恢复协议。

## 7. 配置默认值、失败计数与暂停

| 项目 | 首版决定 |
| --- | --- |
| 费用预算上限 | 不设置；显示未启用，记录实际消耗及未知项，不把未知费用当作零 |
| 单次 Agent 执行硬时限 | 可配置，默认不设置 |
| 正式验收失败暂停阈值 | 同一需求累计 **3 轮**，可配置 |
| 明确重复失败循环暂停阈值 | 默认 **3 次**，可配置；与正式失败分别计数 |
| 其他疑似停滞 | 提醒、展示状态，默认不自动停止 |

正式失败以**需求的一次正式送验**为单位，绑定需求版本和候选身份，覆盖验证 Agent 的独立验证与
业务验收及约定上线验证阶段确认的候选缺陷。同轮多个失败用例、缺陷或重复报告只累计一次；
定向修复后重新送验形成新轮，继续使用原需求和原任务包的成果，不另建需求、不删除旧候选或清空累计。
研发自验失败在研发会话内修复，不单独形成正式失败轮。

研发自验失败与已确认的外部环境、模型服务或部署工具异常分别记录。后者标记运行异常／未验证，
不直接认定候选缺陷，也不能宣布交付完成。原因不明时不按环境异常排除，复验规则见 §10.7。
既有失败记录与已累计轮次不因拆任务、换 Agent、需求修订、重新归类、重跑或修改测试而清零。
客户允许继续时调整允许上限或授权，保留累计；追加方式未固定成旧实现的“每次 +3”。

重复失败循环关注同一任务在业务输入和相关资源状态未改变时，反复执行同一动作并得到同类失败。
正常状态轮询不计入，穿插日志或换 Agent 不能消除记录；精确签名、归并及运行异常重试细节在实施中确定。
DSH 的重复提醒不能代替 ForgeLoop 的确定性暂停。

模型／工具协议超时与 Agent 总执行时限分开记录；工具等待条件在用例和配置中明确。
不能借协议超时隐式增加默认总硬时限，也不因一次超时就认定副作用没有发生。

## 8. 客户入口、发布与运维

### 8.1 客户入口与业务工作台

- 首版提供 **DSH 业务工作台**，展示需求、任务、待决问题、各阶段报告、证据、候选和实际运行版本，并处理例外决定、暂停及恢复。
- 自然语言只在**专用 ForgeLoop 会话模式**受理；以 DSH preset 等已有能力作为接入基础，具体接线待真实验证。
- **首版不支持 ForgeLoop 斜杠命令。** 之前展示的 `/fl status`、`/fl approve` 只是旧机制说明，不是新命令承诺；
  2026-10-28 已从工作树删除该命令表面，替代入口仍待实现。
- 工作台显式操作和自然语言会话输入都可以形成正式决定。对象唯一、意图明确、版本有效时直接受理，不强制再点一次按钮。
- 有歧义、材料已变化或不能唯一匹配待决项时澄清；不将含糊表达自动扩大为授权。
- 保存原始用户输入、可信入口来源及决定的对象、版本和材料；不能凭 Agent 转述“用户同意”、消息的 `user` 角色标签或 `by=owner` 参数自证授权。
- 页面从主控业务记录和已登记材料读取事实，不另维护一份业务状态；“已受理／停止中／已停止／已发布”必须对应实际状态。

### 8.1.1 UI 优先交付（2026-10-29，所有者已确认）

所有者在开发中发现，缺少完整 UI 使功能查看与调试不便，明确要求将 UI 列为高优先级、优先开发；
首批选择“功能与调试并重：统一导航、需求／任务详情、执行过程与错误证据”。
这是本轮明确的优先需求，不再仅作为后续展示层优化；先交付可供日常开发使用的工作台，再继续扩展自主闭环。

- 沿用 DSH 内「天工」工作台，统一总览、需求、任务与问题导航；功能入口、可用操作及下一步清晰可见。
- 需求可查看原文、版本、分析、验收依据和任务进度；需求与任务详情相互关联，支持按身份或内容定位当前加载记录。
  新链路需求详情只读展示最近一次系统准入与受控提交证据（含提交信息 `commitMessage`）；无记录时显示空态，旧记录不需要补造批准或验收。
- 任务可查看执行状态、最后活动、Agent 过程、测试日志、审查结论和证据身份；错误、未知与缺失材料明确呈现。
- 操作继续通过主控校验，展示层不推断成功或另存业务状态；普通需求由系统准入与协调器自动推进，天工页不再展示旧批准、推进、独立验证或验收按钮，只保留停止、取消、恢复、构建与上线等显式动作。历史批准/评审/验收记录仅在存在时只读展示。
- 以“找到需求 → 查看任务 → 定位失败原因及证据 → 找到适用处理入口”为首批验收主路径，同时覆盖空记录、查询无结果、读取失败与窄屏。

首批实现复用现有接口；尚未接通的 Agent 提问回答、例外决定、真实候选发布等能力明确显示边界，
不能因 UI 可见而计为后端闭环完成。后续需要新增决定或执行机制时另列文件范围及行为验收。

### 8.2 发布与数据迁移

- **同一候选包贯穿独立验证、业务验收和正式部署，全部按摘要绑定**，不在通过验证后另构建一份发布。
- **发布/部署使用独立授权**：已授权的研发、验证与本地提交可以继续完成；发布授权缺失只阻断安装与上线，
  不把研发链路重新拉回逐阶段人工批准。
- 产物变化生成新候选，按影响重验；正式送验仍遵守已确认的全量适用回归规则。
- ForgeLoop 提交发布请求；安装、上线检查、回退交给**独立于被升级插件的第三方受控机制**，例如 CD、DSH 插件升级。具体接入工具尚未最终选定。
- **兼容迁移可以自动发布；不兼容或不可逆迁移单独方案、人类决策**。
- 普通自动发布应能安全回退到上一已验证版本；代码回退不能默认伴随整库恢复而丢掉升级后的新业务数据。

### 8.3 运维职责与简化要求

运维方案讨论已结束；首版按简单有效的方式运作，不扩展环境建设。

- 长期目标包含已登记并授权的应用、依赖和基础设施；首版围绕 DogFood 实际需要的状态检查、日志诊断、上线验证和少量恢复动作，不建设通用运维平台。
- 不新增专用 macOS 账户、虚拟机或 SSH 执行环境；沿用当前账户、DSH 能力、沙箱、受控工具与任务目录。
- **生产变更限定为预先登记、能够校验参数与结果的操作类型**；不接受任意生产 Shell 脚本直接执行。
- 运维复用三个角色：需求 Agent 整理业务影响和修复需求；研发 Agent 只读诊断、提出方案；验证 Agent 检查恢复结果；主控控制实际动作。
- **严重线上故障优先，必要时抢占普通研发；一般告警排队**。实际停止、资源互斥、授权与业务承诺冲突规则仍适用。
- 等客户时，先做已经授权的止损或降级；暂停受影响工作，无关工作继续；等待超时不是批准。
- 代码问题进入既定研发流程；范围外或无法确定的事项报告并请求决定，不临时扩权限搭平台。

恢复服务与根因修复可以是关联的不同工作：已经恢复服务，不等于永久修复完成；代码修复完成，
也不等于服务恢复。允许的动作、恢复目标和上线检查集合在实际执行前明确；无法安全处理或触发 §3 例外时请求客户决定。
固定上线检查集合通过才完成交付，不额外设置固定时长观察期，判据见 §10.6。

## 10. 首版验证与评测方案（已收口）

首版采用**小型回归库＋真实主路径＋独立业务终审**，复用现有工具链，围绕从零建设 ForgeLoop 的 DogFood 闭环验证。
测试环境遵守 §8.3 的简化边界，扩展条件见 §10.8；关键拒绝、恢复和配置保护要求仍须覆盖。

首版仍执行项目有效的工程门禁。关键判断、计算、状态流转和幂等逻辑，按[研发纪律](../AGENTS.md#关键行为测试与工程检查)先运行失败的行为测试，再实现使其通过。
预期独立于实现，不以空断言、测试数量、覆盖率数字或模型自评替代业务验收。现有检查入口以 [Makefile](../Makefile) 和项目配置为准。

角色交接按 §5.2 执行；业务终审实际复验关键场景，不重复整套技术测试。

### 10.1 全量适用回归与本次需求

每个候选正式验证执行：**全量已确认且适用的回归用例＋本次需求验收用例**。
适用性依据目标和验收基线版本判断，不能因为本次没有修改某个模块，就省略其仍适用的回归用例。
研发过程的自验可以针对当前任务；局部定位或诊断复跑不能直接作为整体验收通过的依据。

首版回归库围绕已有明确要求逐步形成，重点包括：

- 正常需求闭环、三个角色的交接及工作台关键操作。
- 授权、身份、版本或材料不符合时的拒绝，正常授权路径的通过。
- 失败累计、暂停、去重、停止确认与中断核对，禁止盲目重放副作用。
- 状态与审计一致性、证据及候选身份绑定、测试初始化的配置保护。
- 已接入发布链路的检查，以及适用的上一已验证版本迁移与回退。

范围以首版需求与实际接入能力为准，不预铺未来功能，也不以用例数量代替覆盖质量。

### 10.2 真实执行与可控替身

调度、状态、计数、版本判断和异常分支可以使用可控替身，保证输入可控、结果可重复。
涉及 DSH、数据库、文件、子进程、构建或部署等外部边界时，按对应要求提供真实集成证据。

**每个候选至少一条真实 DSH＋真实模型＋实际工具的端到端主路径是必过项。**
应验证角色交接、实际产物和结果接纳，不能只以模型问候、`--help`、工具退出成功或安装冒烟证明完整链路。
本次需求涉及新的外部接缝或模型行为时，增加相应真实用例。

真实链路没有通过时，依据实际证据区分候选缺陷、环境异常和未验证，不用模拟结果替代通过。
使用测试需求、固定数据或故障演练时标明目的和环境；这些证据不能冒充真实业务 DogFood 成果，也不进入真实需求／运维事件的自主程度分母。

### 10.3 验收计划与模型评测

**验收标准 → 场景用例 → 执行证据。**

验证 Agent 的前置计划必须建立这三者的映射。每个场景明确：

- 前置条件与适用的需求、架构及验收基线。
- 输入或操作、预期业务结果，以及检查结果的方法。
- 需要的环境、数据和证据，哪些属于必过项。

按适用性覆盖正常业务、异常／拒绝、边界条件、状态变化与中断恢复。
不适用维度可以说明理由，但不能借此跳过已经确定的必过要求。
没有对应验证方法或缺少执行证据的条目，保持未验证。

例如，“累计 3 轮失败后暂停”应检查 2 轮仍可继续、3 轮时暂停、重复报告不重复计数、重启后累计仍保留。

**结构与业务行为严格，表述允许变化。**

- 必需字段、身份、版本、依赖、候选摘要及证据关联必须正确。
- 依据实际行为、产物和状态变化判断业务要求是否满足。
- 需求未限定的措辞、任务数量和合理实现路径允许不同；明确规定的文案、格式与数值仍精确校验。
- 不把模型自由文本的逐字匹配作为通用评测方式，也不因报告写了“通过”就放行。

例如，客户说“先别采用方案 A”，应检查没有形成批准或触发执行，不要求系统回复固定句子。

### 10.4 正式回归库与用例有效性

正式回归库独立版本化，复用 §6 的数据库、文件封存和审计机制，不另建测试平台或独立仓库。

1. 研发 Agent 可以编写自验测试，但不能直接修改生效的正式回归库。
2. 验证 Agent 提交新增、修订或废弃建议，说明对应业务要求及理由。
3. 需求 Agent 复核业务含义，由主控登记、接纳新版本；原版本和失败记录保留。
4. 本次需求的新用例参与本次验收，交付完成后沉淀为相应版本的回归基线。
5. 报告绑定测试库版本、数据基线与候选摘要，不能悄悄替换测试依据。

**关键用例首次纳入或实质修改时，必须检查其发现错误的能力。**
同一用例在正确实现上应通过，在对应已知错误实现或受控测试副本上应失败。
例如，“3 轮暂停”的用例面对“4 轮才暂停”的错误实现必须能报错；有能够复现问题的基线时优先使用它。
此检查在独立测试环境进行，不修改正式候选包。首版只做针对关键规则的必要对照，不在每次送验时运行全仓库变异测试。
对照失败应指向对应业务规则，不能把与该规则无关的环境或编译错误当作有效性证明。

### 10.5 测试环境与模型接入

沿用当前 macOS 与 DSH 环境，以明确的验收配置基线准备每轮独立业务数据和运行目录。
跨版本迁移、升级、回退和恢复场景，显式保留所需状态链，不能只测试空库安装。

**保留模型接入基线，重建每轮测试业务状态，由初始化程序拒绝操作正式配置目录。**

| 对象 | 处理方式 |
| --- | --- |
| 正式 DSH 的模型设置与凭据 | 保留，不作为初始化或清理目标 |
| 验收环境的模型路由、工具与必要配置 | 形成稳定、版本化基线；按实际支持方式准备验收实例 |
| 测试所需认证 | 按认证类型显式接入，不假定新 `DSH_HOME` 自动继承原认证，不共享可写的正式凭据库 |
| 每轮测试业务库、任务现场与输出目录 | 在明确的测试资源范围内初始化，避免依赖上一轮残留状态 |
| 报告、日志和证据 | 封存后保留，不能随下一轮初始化清除已有验证依据 |

配置不足时报告验收环境未就绪，不能通过修改正式模型设置来修好测试。
旧 ForgeLoop 业务数据丢弃的决定不适用于 DSH 模型配置、凭据或其他项目数据；本方案不执行旧数据清理。
初始化路径校验、受控工具和沙箱的实际效果必须验证，不能凭不同 profile 或目录名称宣称完整安全隔离。

### 10.6 可发布与交付完成

**发布前门槛。**

本次需求验收、全量适用回归、必需真实集成、质量和授权检查全部满足，才可提交发布请求。
必过项失败、跳过或无法验证均不放行；明确不影响既定要求且不触发人工决策条件的建议，记录到后续清单。
不能临时降低标准，也不能把范围外优化不断追加成本次必做项。

按 §8.2 的同包发布规则绑定摘要；代码或包内容改变形成新候选，重新执行适用验证。

**上线验证通过后完成交付。**

首版采用**固定上线检查集合通过即完成交付**，不另设固定时长观察期。
上线检查覆盖：

- 实际运行版本与候选身份一致。
- 插件和关键入口正常。
- 必要业务记录与模型接入配置正常。
- 本次需求对应的关键业务检查通过。

发布前通过表示“可发布”；实际部署与上述检查通过才表示“交付完成”。
外部机制的安装回执不能单独代替业务检查。后续运行问题进入已确定的运维与修复流程；不因这组检查通过就声明长期稳定性已验证。
安装、上线检查、回退继续使用已约定的第三方受控机制，本方案不扩建运维基础设施。

### 10.7 缺陷、测试争议与有据复验

正式失败和重复失败的暂停、计数按 §7 执行，不另加复验重试上限。

| 情况 | 处置与放行条件 |
| --- | --- |
| 明确实现缺陷 | 验证 Agent 提供复现步骤、预期、实际结果及证据；研发修复代码，生成新候选再送验 |
| 用例或预期存在争议 | 需求 Agent 对照原始需求和生效基线独立复核，主控接纳处理结论；不能只听实现者或验证者一方解释 |
| 确认测试有误 | 验证 Agent 修正测试，保存理由和版本，经既定复核／接纳流程后复验；候选未改变时可复验同一包 |
| 明确环境异常 | 环境恢复并有依据后，可复验同一候选；之前的异常和未验证状态保留 |
| 原因不明 | 允许有计划的诊断复跑以取证；不能仅因下一次碰巧通过就放行 |
| 需求歧义、目标冲突或其他人工例外 | 按已确认规则请求客户决定，不由 Agent 擅自改变业务标准或授权 |

**允许有依据的复验，不以无解释地重跑直到通过作为放行依据。**
所有尝试、原始证据、修订和已累计失败保留。局部诊断、环境修复或单项重跑，不直接等同于整体验收通过；正式结果仍须满足本轮适用的完整清单。

### 10.8 后续扩展

以下按真实问题再评审，不属于首版新增建设范围：

- 回归明显变慢后，评估影响分析和选择性回归。
- 出现实际漏检后，扩展性质测试、模糊测试及更广的变异测试。
- 有实际运行规模要求后，增加压力、长期稳定性与更多故障组合。
- 扩大支持范围后，再增加多模型、DSH 版本和平台矩阵。

## 12. 自主程度与统计口径

### 12.1 研发

统计单位为独立业务需求，不是任务、工具调用、Agent 会话或失败尝试。
从受理到验证、部署完成，只要需要客户补充判断、选择方案或人工补救，该需求就发生了介入。
同一需求介入多次，需求级分子只计一次，另记次数和耗时；任务级统计只作辅助。

- `N研`：约定观察期内进入处理的全部独立业务需求数，保留失败、放弃、卡住及未完成项。
- `H研`：其中发生过人工介入或外部接管补救的需求数。
- `A研`：其中无需再次介入、已完成验证与部署且有完整证据的需求数。
- 人工介入率为 `H研 / N研`，目标严格小于 10%；自主成功交付比例为 `A研 / N研`，目标大于 90%。

同时报告自主成功比例，是为了忠实表达“超过 90% 无需再次介入即可完成”，避免未完成但无人处理
被算作自动化成功。100 项需求发生 10 项介入不满足“小于 10%”。

客户最初表达需求、主动改变业务目标本身不计介入；由系统请求的冲突裁决、技术指导、授权边界变化、
发布授权或人工补救计入。普通需求的系统准入、技术方案、实现、自验、独立验证、定向修复和本地提交
不再形成客户介入；不能为了指标保留形式化确认，也不能把应当自动完成的动作改写成客户批准。
需求修订和拆任务不能抹去介入历史；跨窗口修订和对象归属的具体结算规则须在 M2 前确定。

### 12.2 运维

- `N运`：约定观察期内需要处置的独立运维事件数，保留失败、卡住、未恢复及外部接管项。
- `H运`：其中发生过客户决策、人工处置或外部接管补救的事件数。
- 人工介入率为 `H运 / N运`，目标严格小于 10%，与研发分别判定。

同一故障产生的多个告警、诊断和修复任务合并计为一个事件；正常巡检不计入分母。
同时报告已验证恢复／处置、失败、未完成与恢复时长，少介入不等于恢复成功。
事件产生的研发修复需求分别进入研发统计，并以关联关系连接；不合并两类分母。

### 12.3 共同规则

统计从自主迭代期开始，不能到准备达标时才开始留记录。M2 的观察窗口及样本覆盖须预先确定，
历史全量账与窗口报告同时保留，不靠挑容易的需求、删除失败或更换窗口美化指标。
样本为零或未达到约定样本要求时，显示无样本／不足，不能显示已达标。

ForgeLoop 按授权调用工程工具不属于外部接管；外部 Agent 绕过 ForgeLoop 接手、所有者提供技术修复，
均如实标记补救，不能算独立成果。M0 的种子建设投入单列。
高技术难度、重大架构变化等必要人工决定仍计入介入率，不能为了指标免计。

目前已确认目标与上述基本口径，尚未确定样本数量、观察时长、截止时点和事件合并细则。
M1 先测真实基线，M2 条件补齐并取得证据后才能宣布达标；不把未知参数填成产品默认承诺。

测试用例、fixture、故障演练和真实业务样本分别报告，测试通过数不能作为真实自主交付分母。
M2 的统计观察窗口与首版“不设置发布后固定观察期”是两个不同概念。

## 13. 全链路审计与结果交接

每项交付应能回答：为什么做、依据哪个目标和需求版本、谁或什么机制授权、实际执行了什么、
结果如何、哪里失败、谁介入，以及当前运行的是否就是被验证的产物。

| 证据对象 | 至少需要关联的信息 |
| --- | --- |
| 目标、需求与设计 | 原始输入、反馈来源、版本、关键架构决定、任务依赖与修订影响 |
| 决定与配置 | 决策对象、适用版本、真实来源、选择及影响；生效配置快照和更改历史 |
| Agent 与工具执行 | 实际执行主体、模型／工具信息、可取得的轨迹、输入输出及动作结果；未知或不可取得的部分标注缺失 |
| 实现与验证 | 基线、候选改动、测试命令与实际结果、独立审查结论、业务场景证据和失败记录 |
| 部署与运行 | 候选身份与摘要、环境、工程门禁结果、实际运行版本、上线验证、恢复动作及结果 |
| 统计与成本 | 需求／事件关联、介入原因与来源、次数、时长、可取得的实际消耗和计量缺口 |

事实和模型推断分开，不能把模型转述当作正式测试或运行恢复证据。
审计保留原始来源、修订与失效原因，不覆盖旧失败、批准或历史结论。
存储方式见 §6；保留期限、敏感信息处理与可发送给模型的材料范围仍待明确，不能为了“完整审计”保存凭据明文。
具体质量阈值及证据方法需与业务需求对应，不用单一测试数量、覆盖率或模型投票替代业务验收。

各阶段采用**结构化结果清单＋可读报告**，在 DSH 工作台展示，关联原始日志、产物和必要截图。
清单至少关联需求／执行身份、输入／基线版本、候选摘要、测试库与数据版本、实际环境和模型路由、
逐项结果、未完成事项、复验依据及证据位置；具体 schema 在实施方案确定，不另建多套报告系统。
主控核对身份、来源、版本和实际证据后推进，不能只凭报告中的“通过”字样。
模拟、真实执行、模型推断与事实分别标注；无法取得的费用或轨迹标为未知／缺失。

# DogFood 业务交接约定（T01 草案，待所有者逐字段核对）

状态：**已定稿**（所有者 2026-10-13 逐项确认，见第 10 节）。依据 [DogFood 执行任务计划](dogfood-execution-plan.md) T01。
本文件定义三条业务线（需求规划 A、研发交付 B、版本交付 C）之间的身份、状态与批准传播规则。所有新命令均为**拟实现**，不得据本文假设接口已存在。

**适用边界（所有者 2026-10-15 澄清）**：本约定约束经过 ForgeLoop 执行的任务及业务交接。自我迭代要求 ForgeLoop 能修改自身项目并交付可验收代码；允许所有者、DSH 和其他工具按项目约定共同开发。已撤销服务端排他写入、来源签名准入及“只有 ForgeLoop 才能提交”的要求，原 C04 取消、原 G04 改写。

## 1. 身份与唯一性

| 身份 | 命名 | 归属与唯一性 |
| --- | --- | --- |
| 需求 `requirement_id` | `req-<project>-<seq>` | 由需求入口分配；同一项目内唯一；跨项目不得复用 |
| 需求文本版本 | `requirement_revision` | 每次补充原始材料递增；旧版本保留原文与时间 |
| 任务包 `task_plan_id` / `plan_version` | `plan-<requirement_id>-<seq>` / 整数 | 一条需求可有多个任务包版本；批准绑定 `requirement_id` + `plan_version` |
| 任务 `task_id` | 现有 `submit` 任务身份 | 一个任务只属于一个任务包版本、一个执行者 |
| 候选 `candidate_id` | 候选分支名 + 提交号（40 位） | 候选必须可定位到确定提交；不得用"分支最新"代替 |
| 产物 `artifact_id` | wheel 文件名 + `sha256` | 由候选提交构建一次；发布与部署复用同一 `sha256` |
| 发布 `release_receipt_id` | 标签 + 回执记录 | 一个标签对应一次发布；重复发布幂等、换标签拒绝 |

## 2. 需求记录字段（A01 实现）

`requirement_id`、`project`、`title`、`original_text`、`revisions[]`（`revision`、`text`、`source`、`recorded_at`）、`status`、`created_at`、`updated_at`。
补充材料只能追加版本，不覆盖原始文本；查询任何版本都必须回到原文。

## 3. 任务包字段（A03 实现）

`task_plan_id`、`requirement_id`、`plan_version`、`tasks[]`、`approval`、`status`。
每个任务：`task_id`、`goal`、`files[]`（准许修改清单）、`acceptance`、`test_command`、`depends_on[]`、`limits`（工时/失败轮次）、`authorization_source`（哪次批准授权本任务）。
校验：依赖必须存在且无环、同一任务包内 `task_id` 唯一、必须给出可执行测试命令、跨项目引用拒绝。

## 4. 状态词（三条线共用）

**先采用精简集合**（所有者 2026-10-13 决定）；完整集合列入待观察方案，只有精简集合解决不好问题时再扩展，不预先把完整状态机写进实现。

需求（精简）：`draft`（已收原文）→ `awaiting_clarification`（等待回答）→ `plan_proposed`（有任务包待批准）→ `approved`（任务包已批准）→ `executing` → `accepted`；异常 `rejected`、`blocked`。
任务：沿用现有实现的状态词（`awaiting_plan_approval`、`implementing`、`reviewing`、`testing`、`awaiting_acceptance`、`delivered`、`merged`、`interrupted`、`stop_requested`、`stopped`、`time_exhausted`、`awaiting_grant`），不新增。
候选/产物（精简）：`built` → `verified` → `accepted` → `merged` → `released` → `deployed`；异常 `rolled_back`。

待观察方案（暂不实现）：需求 `analyzing`／`analyzed`／`awaiting_plan_approval`／`awaiting_requirement_acceptance`，候选 `candidate_built`／`candidate_verified` 等更细粒度状态，以及按阶段拆分的子状态。

每项同时登记两个维度：**实现/独立验证** 与 **集成/真实验证**；接口通过不等于联合场景通过。

## 5. 批准传播

1. 需求级批准只授权"分析并生成任务包"，不授权任何文件改动。
2. 任务包批准授权其列出的任务、文件清单、测试命令与限额；**未列出的文件不得修改**。
3. 批准绑定需求身份与任务包版本；需求文本或任务包变更（范围、文件、验收、测试）即失效，需重新取得批准。
4. 任务级授权来源写入任务记录（`authorization_source`）；新增文件清单必须回到所有者的方案评审。
   呈现粒度（所有者 2026-10-13 决定）：**涉及架构、模块边界或接口契约的变化必须呈现给所有者**；模块内部实现细节变化不单独呈现，但必须写入交付记录。
5. 总体建设意图不构成任意文件或发布的批准；发布/部署仍需单项授权。
6. 候选提交入库采用**按任务包一次授权**（所有者 2026-10-13 决定）：该任务包内的候选提交在授权范围内可执行，仍须落在合法提交窗口；超出清单或改变契约需重新授权。

## 6. 依赖产物传递

- 上游任务完成后，把**已确认产物**（候选 diff 身份、正式测试证据、审查结论、验收结论）作为显式输入交给下游；下游记录该输入身份。
- 依赖产物**落库**（所有者 2026-10-13 决定）：写入权威记录（任务/需求记录），不只放在提示词或临时文件里；下游读取以记录为准。
- 上游失败或未验收时下游不得启动；等待追加授权或所有者决定不消耗执行工时。
- 基线漂移：下游必须基于新基线重新核对并重新绑定有效批准，不得拼接旧 diff 沿用旧验收。
- 同一文件的不同函数可在独立副本并行开发，但重叠范围必须登记，并由单独的集成任务合成与验证。

## 7. 候选、验收、提交与发布的先后顺序

1. 开发在独立副本产生候选（`candidate_id`），正式测试在副本内运行。
2. 用户验收绑定：任务包版本、候选身份（提交/diff）、正式测试证据、独立审查结论；后续材料变化使验收失效。
3. 候选提交入库需**所有者授权**并落在合法提交窗口；不得使用 `--no-verify`、禁用 hooks 或伪造时间。
4. 归并只接受已验收且必需检查状态明确的候选；未知检查状态不放行；main 漂移需重新核对。
5. 发布复用候选构建的同一 `sha256` 产物，不在标签工作流重新构建；部署只接受该产物，保留上一版本与可核对回滚入口。

## 8. 记录与证据

每次交接至少留存：任务 ID、需求身份、方案版本、初始失败证据（若有）、独立审查、实际命令与日志、候选身份、未验证项、发现但不碰。
"通过"只来自实际执行结果；模拟、替身与样例不作为真实场景验收依据。

记录实际执行工具及授权来源，外部工具完成的开发与 ForgeLoop 执行成果分别统计。外部协作不自动视为救援或违规；不补挂 ForgeLoop 任务 ID，不把可回查证据关联扩展为来源签名准入条件。

## 9. 逐任务文件范围（拟批准，待所有者确认）

范围沿用执行计划各任务的"拟修改范围"；每任务额外包含 `docs/architecture.md` 与 `contracts/architecture.json` 的必要同步（模块增删/接缝变化时），改变 CLI 契约的任务另含 `scripts/export_cli_contract.py` 与 `contracts/cli-contract.json`。

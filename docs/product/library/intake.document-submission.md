# 设计文档提交即发起研发

## 业务目标
减少从文档到需求的人工转抄，并保留需求与文档版本的可追溯关系

## 用户与角色
- 需求提交人
- 需求分析人员
- 研发与验证角色

## 触发与前提
需求提交人在业务会话中选择项目内 Markdown 文档或粘贴文档正文

## 预期行为
系统将文档正文作为需求原文受理，同时记录文档快照；重复内容返回原需求，修订内容在原需求下形成新版本。

## 业务规则
- 文档正文即需求原文，同时保存文档类型、项目内路径、内容指纹、字节数与标题快照，并与版本记录一并保存。
- 相同内容重复投递返回原需求，不新建需求、不重复分析。
- 内容修订在原需求下追加版本，旧快照、旧分析与既有证据保留。
- 原需求已终态时，修订按新需求受理并重新绑定该文档路径。
- 内联粘贴的正文同样登记快照。
- 需求详情展示文档快照历史。

## 例外与边界
- 文件缺失或超过大小上限由程序拒绝，受理层不静默降级。
- 原需求已终态后的修订按新需求处理，不覆盖终态需求。

## 可观察验收
- 提交文档后生成需求，详情中可查看该文档快照。
- 重复提交同一内容不会产生新需求，也不会重复分析。
- 修改文档后原需求下出现新版本，旧版本仍可查。

## 适用范围与版本
业务会话中的设计文档提交；内联粘贴正文同样适用

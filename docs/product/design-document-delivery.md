# 从功能设计文档到可安装交付

> 产品设计稿（2026-11-16，Asia/Shanghai）。项目通用规则见[产品与首版方案](product.md)，实施进展见[状态记录](../verification/status.md)。

**用户在已绑定的项目中提交一份功能设计文档，ForgeLoop 自动转发研发，最终交付经过验证的安装包。**
研发可以根据实际情况调整任务顺序和协作方式。用户只在现有资料无法回答关键业务问题，或事项需要其决定时介入。

## 1. 提交即发起研发

用户在 ForgeLoop 业务会话粘贴文档正文，或引用当前项目内的一份文档。**提交就是发起动作。**
系统保存文档快照，生成需求编号，并自动转发给当前项目的研发会话。执行资源正忙时，需求显示「已排队」，轮到后自动开始。

同一次提交的重复投递返回原需求。用户修订文档时，在原需求下生成新版本，系统核对哪些工作和证据仍然适用。
需求编号和首次受理时间持续保留。

## 2. 研发编排使用软约束

研发接到文档后，可以先阅读项目上下文、复现风险、拆分任务，也可以直接实现已经明确的部分。
**任务拆分、分工、顺序和验证时机是可调整的建议。** 查证、实现、测试和修复可以交错进行。
范围或规则尚待确认时，先停住依赖该决定的动作，其余已明确的工作继续。

| 关注点 | 研发需要做到什么 |
| --- | --- |
| **功能完整** | 每条必需业务规则都有可观察的结果。正常场景说明用户能完成什么。异常场景说明触发条件、用户提示、数据结果及后续动作。 |
| **执行安全** | 涉及权限、项目范围、敏感数据或不可逆写入时，按生效授权和项目保护规则校验。范围内的技术选择由研发自行处理。 |
| **结果可靠** | 关键行为有实际测试证据。需要恢复的场景实际验证恢复结果。代码、验收记录和安装包能追溯到同一次交付。 |

工作台上的「查证中」「实现中」「验证中」反映当前活动。研发可以根据新证据回查和调整。
项目已有的权限、范围和质量规则仍在相应动作及交付判定时生效。

**可安装交付**要求通过验收的代码提交、与提交对应的安装包、安装说明，以及实际测试和试装记录同时可用。
功能验证覆盖正常行为和适用异常。试装在隔离测试环境执行，交付包与试装包的摘要一致。

## 3. 工作台优先查证，集中处理必要决定

系统先查阅功能文档、项目业务说明、已有决定、代码和测试记录。需要补充公共事实时，自动搜索适用版本的官方文档、
公开标准或依赖说明。对外查询使用可公开的关键词，结论记录来源及适用条件。

- **能查证的事实直接采用。** 工作台展示补全了什么、依据在哪里。项目文档已明确某类数据的处理规则时，研发直接沿用该规则。
- **低风险且可逆的实现选择自动处理。** 沿用项目惯例，可在需求详情中查看采用的假设及影响。
- **只有关键缺口才向用户提问。** 已查证材料仍有冲突或缺失，并且会改变业务范围、验收、数据结果或授权时，在「需要处理」中集中列出。
  每个问题说明查过什么、为什么需要决定、可行选项及各自影响。已经获得有效答复的问题直接复用。

工作台首屏显示**当前在做什么、已确认的业务结果、是否需要用户动作**。最后一项在没有待决定事项时显示「系统处理中」。
用户可以展开查看证据，也可以停止或取消工作。停止状态以执行实际停稳为准。

### 异常怎样自动收口

| 研发遇到的情况 | 系统处理 |
| --- | --- |
| **实际行为不符合验收** | 带着预期、实际结果和复现证据定向修复，重新验证受影响的行为。 |
| **测试工具、模型或环境临时失败** | 记录故障原因，在恢复条件明确时按生效策略重试。适用时沿用同一候选及已有有效证据。 |
| **重复请求、取消或宿主中断** | 先核对已有结果和写入状态。已完成的动作直接收口。确认未生效且动作仍允许安全重试时继续。 |
| **授权不足、业务冲突或副作用未知** | 保留现场，暂停受影响动作，在工作台给出待决定事项和可选处置。 |

## 4. 三项度量指标

按**项目和受理时间**归组，每组明确统计截止时点。以独立需求编号计数，文档修订、重复投递和重试沿用原编号。
交付结果按截止时生效的需求版本和对应制品判定。

| 指标 | 统计口径 | 工作台展示 |
| --- | --- | --- |
| **可安装交付率** | 截止时已完成可安装交付的需求数 ÷ 同组全部已受理需求数。失败、阻塞、取消和未完成均留在分母。 | 达成数／受理数、百分比和未达成需求的当前状态。 |
| **每条需求的人工介入耗时** | 累加该需求中人工澄清、业务决定和人工补救的实际处理时长。同一人的重叠时段合并。原始提交、日常查看进度和等待回复的时间不计入。 | 单条需求显示分钟数和介入原因。界面内时长按可观测的活跃处理区间估算。已知发生了人工介入但缺少时长时，显示「时长未知」。 |
| **从受理到可用结果的用时** | 安装包、安装说明和验证证据均已可访问的时间减去首次受理时间。包含排队、查证、研发、修复和等待。 | 单条需求显示总用时。汇总显示已交付需求的中位数、P90 和样本数。未完成需求显示已等待时长，单独列示。 |

三项指标均可追溯到原始事件。**受理记录**确定什么时候开始，**人工处理记录**说明谁在哪个事项上花了时间，
**可安装交付记录**证明用户从什么时候起可以取得哪份已验证的安装包。

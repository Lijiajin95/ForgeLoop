# 需求阶段交付标准

> 2026-11-20（Asia/Shanghai）。适用于 ForgeLoop 的功能需求与缺陷问题，遵循[产品与首版方案](product.md)的准入、授权和验证规则。本文固化交付标准，并以「需求阶段归档与自动移交」给出详细需求说明。运行时扩展与真实场景验收待实施。

**当前版本的必需产物归档、校验并通过系统准入后，协调器自动移交研发。**
天工提供按需查看的需求详情，读取进度、依据、样例或历史属于只读操作。业务取舍、承诺冲突、授权变化等事项沿用[客户决定规则](product.md#32-必须请求客户决定的例外)。

## 1. 交付物

需求阶段交付一份绑定需求版本的说明。研发与测试使用同一版业务要点（BP）和验收项（AC），天工按该版本展示说明、材料和进展。
系统归档所有实际形成的需求阶段产物，包括失败尝试、已被取代的分析以及可以取得的原始执行记录。

| 产物 | 最低内容 | 适用范围 |
| --- | --- | --- |
| 输入与身份 | 原始文本、项目与需求身份、版本、提交来源。引用项目文档时保留正文快照、路径及内容摘要 | 全部 |
| 需求说明 | 目标、范围、非目标、业务要点、规则、异常边界及验收项。记录假设和适用条件 | 功能需求 |
| 问题说明 | 现象、影响、已有复现线索、修复判据及观察位置 | 缺陷问题 |
| 查证与决定 | 关键结论的生效依据、适用版本、摘录或观测、对应要点。发生澄清时保留逐题问答、取舍及解决依据 | 全部，按实际内容留存 |
| 功能地图与界面设计 | 本次影响的入口、操作路径、可见反馈、适用状态及关联的 BP 和 AC。已有或明确要求的原型、截图随适用版本引用 | 涉及界面或用户路径变化的需求 |
| 验收样例 | 关键 AC 的固定数据、前置条件、操作、独立预期和观察位置。适用时包含一个能暴露错误行为的反例 | 按需求风险与影响选择 |
| 进展与结果 | 可取得的分析轨迹、查证与规格校验结果、失败和重试、已有演练证据、准入及研发排队记录 | 全部，按实际发生的动作留存 |

需求说明可用 Markdown 提交，并通过版本化的结构化记录交接。BP 描述角色在什么条件下触发什么业务行为，
包含适用的规则和边界。AC 用「给定／当／则」写可观察结果并引用对应的 BP。研发通过 `covers` 回指业务要点，
测试场景通过 `point_ids` 和 `acceptance_ids` 回指要点和验收项。交接时随附样例数据或可核对的固定引用。

需求版本、分析版本和尝试各有身份。文档、原型和实际运行证据保存可核对的版本或内容摘要。
天工从记录生成当前说明及历史视图。已经归档的材料按版本追加，修订时记录受影响的要点、验收项和证据。

## 2. 查证与前置验证

1. **固定输入并分诊。** 保存受理时的原文，识别功能需求或缺陷问题。从可观察的场景拆出角色、操作、成功条件、权限和数据边界。
2. **先查项目。** 查阅当前原文、逐题回答、已确认的需求库条目和有关承诺。必要时由具备相应工具的环节取得同版本的产品行为、测试或实现记录。分别记录现有行为、已确认规则、可逆假设和待决定事项。涉及旧规则时，查清其是否仍然生效。
3. **按需查外部事实。** 宿主接口、依赖版本、公开标准或外部系统数据语义确实影响本次范围、兼容性或验收时，查适用版本的一手资料。记录来源、版本或日期、摘录及影响的 BP 和 AC。搜索结果提供分析依据，授权与业务取舍以项目的当前决定为准。
4. **核对结论并收敛问题。** 程序核验来源身份、版本、条目状态、摘录和 BP 与 AC 的关联。产品分析核对依据是否支持所述行为。影响范围、验收、数据或权限的关键缺口仍未解决时，保留已查依据、选项与影响，按既有入口逐题澄清。
5. **先写预期，再观察结果。** 用当前生效规则写出固定样例及预期。已有可运行对象时，实际载入样例并操作，记录预期、观察结果和证据。缺陷可在适用的现有版本保留复现记录，供固定候选复验。

| 检查层次 | 何时记录结果 | 可证明的事实 |
| --- | --- | --- |
| 规格校验 | 程序实际检查版本、依据、引用和覆盖之后 | 说明满足已编码的结构与一致性检查 |
| 原型演练 | 在明确版本的原型上实际执行固定样例之后 | 原型在这些样例下的可见行为及与预期的差异 |
| 候选验证 | 在固定候选上经公开入口实际执行并核对证据之后 | 对应候选在本次测试中的业务结果 |

只有说明或静态设计图时，可以记录规格走查。未执行的演练标为「待演练」，不适用时记录理由。
测试 Agent 依据当前需求说明独立完善验证场景，并在固定候选上补齐实际检查与证据。原型和候选结果分别展示。

## 3. 归档、进展与自动移交

1. 先登记当前需求、分析及必需材料的身份，再记录规格校验与系统准入结果。协调器按适用项目和版本领取可研发需求。研发资源忙时保留排队状态。
2. 普通需求按已生效策略自动推进，页面浏览和材料展开是独立的只读路径。缺陷沿用简版说明和相同准入链路。原型演练按本次需求范围进行，对未要求演练的需求用实际适用状态展示。
3. 仍待决定或校验失败时，记录具体原因和已有材料，沿用澄清、停止、冲突及有限重试规则。材料保存失败时，当前版本保持未移交状态。
4. 重复投递或中断恢复时先核对已有归档、准入和队列记录。同一需求版本只产生一次有效研发交接。修订、取消或停止后，迟到产物只进入审计；历史记录保留原身份。
5. 天工根据真实记录展示受理、分析、规格校验、待澄清、失败或重试、准入和排队。查证进展以已有工具或证据记录为依据。每项结果可回查适用版本、时间、原因和证据位置。

引用资料的读取与进展展示沿用项目隔离和访问权限。硬性条件在实际写入、准入或领取入口校验，
并用正常和拒绝两侧的行为用例验证。当前实现与待实施内容见[第 5 节](#5-实现与验收状态)。

## 4. 需求说明示例 · 归档与自动移交

### 4.1 目标与范围

需求提交者即使离开会话，系统也能完成当前版本的需求交接。项目成员有需要时在天工自行查看依据、样例和进展。
研发与测试据同一版本执行，能够识别修订前的材料。范围为需求受理后的产品分析、归档、现有准入与排队，以及需求详情的只读呈现。
研发编排、正式候选验证、发布和生产配置分别遵循各自的现有方案。

### 4.2 功能地图与界面设计

| 入口 | 用户行为或系统动作 | 完成信号 |
| --- | --- | --- |
| 业务会话 | 发送需求正文或引用项目内设计文档 | 显示需求身份与当前版本，记录实际受理时间 |
| 产品分析 | 系统查证、形成说明、归档并判定准入 | 详情显示当前进展，已有结论的版本和依据可查 |
| 研发队列 | 协调器领取已准入的当前版本 | 显示实际排队或领取记录，并能追到同版说明 |
| 天工 → 需求详情 | 按需打开进展、材料、样例和历史 | 当前结论与历史结果区分明确，来源和证据可展开 |

需求详情顶部展示「需求版本 · 分析版本」「当前阶段」和最近一次能核对的进展。
展开后按「说明与依据」「样例与证据」「澄清与历史」阅读。缺记录时显示对应缺项，读取失败时显示失败原因。
修订后的旧结果可以在历史中查看。初始版复用现有需求详情的结构和样式，界面示意如下。

```text
需求 v2 · 分析 v3                      研发排队
进展  已归档 → 系统准入通过 → 等待研发位
材料  说明与依据  |  样例与证据  |  澄清与历史
证据  规格校验通过  ·  原型待演练  ·  候选待验证
```

### 4.3 业务要点和验收

| BP | 角色与触发 | 预期业务行为 |
| --- | --- | --- |
| BP-1 | 产品分析形成结果，或一次尝试失败 | 以版本和尝试身份归档实际产物与记录。重试、修订、停止和取消后仍可回查历史 |
| BP-2 | 产品分析引用原文、项目约定或决定 | 当前交接可回查有效依据。被取代的依据保留在历史中，阻塞性缺口按现有流程收口 |
| BP-3 | 关键验收项形成，或存在可演练的对象 | 固定样例与独立预期随版本交接。每次实际演练带对象身份、观察结果和证据 |
| BP-4 | 当前说明和必需产物已归档且通过准入 | 协调器自动移交研发。并发、重复投递或中断恢复只产生一次有效交接 |
| BP-5 | 用户在天工查看需求详情 | 看到实际阶段、对应版本、阻塞原因和证据。浏览动作保持只读 |

以下是拟实施的验收用例。样例需求、版本和结果均为固定输入及独立预期，运行记录待实际执行后补齐。

| AC | 覆盖 | 给定与操作 | 可观察的独立预期 |
| --- | --- | --- | --- |
| AC-1 | BP-1、BP-4 | 提交一条范围明确的功能需求。产品分析成功，提交者退出客户端，研发位可用 | 一份当前版本的说明和必需材料归档。准入通过并出现一次有效研发交接 |
| AC-2 | BP-1、BP-4 | 当前版本归档失败，随后恢复并重复提交同一次结果 | 首次只出现失败与原因，当前版本保持未移交。恢复后材料完整，队列只产生一次有效交接 |
| AC-3 | BP-1、BP-4 | 材料已归档，入队前宿主中断。重启后重复处理 | 恢复时依据已有分析和队列记录收口。现有结果复用，当前版本最终只交接一次 |
| AC-4 | BP-1、BP-2 | v1 规则明确被 v2 取代。提交分别引用 v1 旧规则、v2 生效规则的 v2 分析结果 | 旧规则引用给出版本失效原因。有效引用通过该项校验，v1 分析仍在历史可查 |
| AC-5 | BP-2、BP-4 | 关键业务问题尚待答复，或存在已登记的未解除承诺冲突。尝试移交 | 需求显示具体待处理事项，研发仍待准入。有效解决后按当前版本重新判定 |
| AC-6 | BP-1、BP-4 | 分析进行中修订需求，随后旧结果到达。另对停止或取消的需求回传迟到结果 | 可查到迟到审计，当前版本、状态和交接依据由有效记录决定 |
| AC-7 | BP-3、BP-5 | 归档一条仅有规格检查的需求，再归档一条附原型演练记录的需求并查看详情 | 第一条显示演练待执行或不适用。第二条能核对原型版本、样例、观察结果和证据，两条候选验证各按实际状态展示 |
| AC-8 | BP-4、BP-5 | 一条无界面改动的缺陷已具备现象、复现线索和修复判据。用户先离线，之后打开详情 | 系统按策略自动交接。详情读取已存在的记录，研发队列的有效交接数仍为一次 |
| AC-9 | BP-1、BP-5 | v1 已归档并有演练结果，提交 v2 后打开需求详情 | 详情标明当前是 v2。旧演练带 v1 身份留在历史，当前证据按 v2 的实际执行呈现 |
| AC-10 | BP-3、BP-5 | 归档下表五组 W2 样例。在具备可运行原型时逐组操作候选验证栏 | 每组可回查对应的预期。运行后记录逐组观察和证据，阶段标为原型演练 |

### 4.4 固定样例 W2

复用[天工设计稿的 W2](tiangong-workspace.md#测试先行的验收样例)。入口为「工作台 → 按需求 → 候选验证」。
以下输入默认当前候选为 B，A 为历史候选。每轮独立设置数据，再打开验证栏，观察状态和异常提示。

| 输入 | 独立预期 |
| --- | --- |
| 无报告 | 尚无结论 |
| B 有通过报告 | 验证通过 |
| B 有失败报告 | 验证未通过 |
| 只有 A 的通过报告 | 需重新验证，A 的报告可从历史查看 |
| 测试方案生成失败且无报告 | 尚无结论，同时显示方案生成失败原因 |

[现有 HTML 设计稿](tiangong-workspace.html)包含一组固定示例。五组样例的完整原型演练与候选复验均待执行。

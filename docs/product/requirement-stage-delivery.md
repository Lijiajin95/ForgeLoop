# 需求阶段交付标准

> 2026-11-20（Asia/Shanghai）。适用于 ForgeLoop 的功能需求与缺陷问题，遵循[产品与首版方案](product.md)的准入、授权和验证规则。本文规定通用交付口径，具体需求和验收详见[归档与自动移交说明](requirement-stage-handoff.md)。

**当前版本的必需产物归档、校验并通过系统准入后，协调器自动移交研发。**
天工提供按需查看的需求详情，读取进度、依据、样例或历史属于只读操作。业务取舍、承诺冲突、授权变化等事项沿用[客户决定规则](product.md#32-必须请求客户决定的例外)。

## 1. 交付物

需求阶段交付一份绑定需求版本的说明。研发与测试使用同一版业务要点（BP）和验收项（AC），天工按该版本展示说明、材料和进展。
系统归档所有实际形成的需求阶段产物，包括失败尝试、已被取代的分析以及可以取得的原始执行记录。

| 产物 | 最低内容 | 适用范围 |
| --- | --- | --- |
| 输入与身份 | 原始文本、项目与需求身份、版本、提交来源。引用项目文档时保留正文快照、路径及内容摘要 | 全部 |
| 需求说明 | 目标、范围、非目标、业务要点、规则、异常边界及验收项。记录假设和适用条件 | 功能需求 |
| 问题说明 | 现象、影响、已有复现线索、修复判据及观察位置 | 缺陷问题 |
| 查证与决定 | 关键结论的生效依据、适用版本、摘录或观测、对应要点。发生澄清时保留逐题问答、取舍及解决依据 | 全部，按实际内容留存 |
| 功能地图与界面设计 | 本次影响的入口、操作路径、可见反馈、适用状态及关联的 BP 和 AC。已有或明确要求的原型、截图随适用版本引用 | 涉及界面或用户路径变化的需求 |
| 验收样例 | 关键 AC 的固定数据、前置条件、操作、独立预期和观察位置。适用时包含一个能暴露错误行为的反例 | 按需求风险与影响选择 |
| 质量属性 | 非功能约束的种类、指标、含数值与单位的目标、测量方式与位置，关联 BP／AC。没有非功能约束时留空 | 涉及性能、安全、可用性、兼容性或合规的功能需求 |
| 数据要求 | 实体、字段名／类型／约束、保留期与处置、是否个人信息，关联 BP／AC | 涉及数据结构、导出或个人信息的变更 |
| 进展与结果 | 可取得的分析轨迹、查证与规格校验结果、失败和重试、已有演练证据、准入及研发排队记录 | 全部，按实际发生的动作留存 |

需求说明可用 Markdown 提交，并通过版本化的结构化记录交接。BP 描述角色在什么条件下触发什么业务行为，
包含适用的规则和边界。AC 用「给定／当／则」写可观察结果并引用对应的 BP。研发通过 `covers` 回指业务要点，
测试场景通过 `point_ids` 和 `acceptance_ids` 回指要点和验收项。交接时随附样例数据或可核对的固定引用。

需求版本、分析版本和尝试各有身份。文档、原型和实际运行证据保存可核对的版本或内容摘要。
天工从记录生成当前说明及历史视图。已经归档的材料按版本追加，修订时记录受影响的要点、验收项和证据。

## 2. 查证与前置验证

1. **固定输入并分诊。** 保存受理时的原文，识别功能需求或缺陷问题。从可观察的场景拆出角色、操作、成功条件、权限和数据边界。
2. **先查项目。** 查阅当前原文、逐题回答、已确认的需求库条目和有关承诺。必要时由具备相应工具的环节取得同版本的产品行为、测试或实现记录。分别记录现有行为、已确认规则、可逆假设和待决定事项。涉及旧规则时，查清其是否仍然生效。
3. **按需查外部事实。** 宿主接口、依赖版本、公开标准或外部系统数据语义确实影响本次范围、兼容性或验收时，查适用版本的一手资料。记录来源、版本或日期、摘录及影响的 BP 和 AC。搜索结果提供分析依据，授权与业务取舍以项目的当前决定为准。
4. **核对结论并收敛问题。** 程序核验来源身份、版本、条目状态、摘录和 BP 与 AC 的关联。产品分析核对依据是否支持所述行为。影响范围、验收、数据或权限的关键缺口仍未解决时，保留已查依据、选项与影响，按既有入口逐题澄清。
5. **先写预期，再观察结果。** 用当前生效规则写出固定样例及预期。已有可运行对象时，实际载入样例并操作，记录预期、观察结果和证据。缺陷可在适用的现有版本保留复现记录，供固定候选复验。

| 检查层次 | 何时记录结果 | 可证明的事实 |
| --- | --- | --- |
| 规格校验 | 程序实际检查版本、依据、引用和覆盖之后 | 说明满足已编码的结构与一致性检查 |
| 原型演练 | 在明确版本的原型上实际执行固定样例之后 | 原型在这些样例下的可见行为及与预期的差异 |
| 候选验证 | 在固定候选上经公开入口实际执行并核对证据之后 | 对应候选在本次测试中的业务结果 |

只有说明或静态设计图时，可以记录规格走查。未执行的演练标为「待演练」，不适用时记录理由。
测试 Agent 依据当前需求说明独立完善验证场景，并在固定候选上补齐实际检查与证据。原型和候选结果分别展示。

## 3. 归档、进展与自动移交

1. 先登记当前需求、分析及必需材料的身份，再记录规格校验与系统准入结果。协调器按适用项目和版本领取可研发需求。研发资源忙时保留排队状态。
2. 普通需求按已生效策略自动推进，页面浏览和材料展开是独立的只读路径。缺陷沿用简版说明和相同准入链路。原型演练按本次需求范围进行，对未要求演练的需求用实际适用状态展示。
3. 仍待决定或校验失败时，记录具体原因和已有材料，沿用澄清、停止、冲突及有限重试规则。材料保存失败时，当前版本保持未移交状态。
4. 重复投递或中断恢复时先核对已有归档、准入和队列记录。同一需求版本只产生一次有效研发交接。修订、取消或停止后，迟到产物只进入审计；历史记录保留原身份。
5. 天工根据真实记录展示受理、分析、规格校验、待澄清、失败或重试、准入和排队。查证进展以已有工具或证据记录为依据。每项结果可回查适用版本、时间、原因和证据位置。

引用资料的读取与进展展示沿用项目隔离和访问权限。硬性条件在实际写入、准入或领取入口校验，
并用正常和拒绝两侧的行为用例验证。当前实现与待实施内容见[第 5 节](#5-实现与验收状态)。

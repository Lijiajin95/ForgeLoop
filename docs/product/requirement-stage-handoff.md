# 需求阶段产物归档、进展与自动移交研发

> 说明版本 v1 · 2026-11-20（Asia/Shanghai）· 待实施。本文依据[需求阶段交付标准](requirement-stage-delivery.md)编制。
> 受理时由 ForgeLoop 分配需求身份和需求版本，本文的说明版本用于追踪文档修订。

## 1. 目标、用户与范围

当前需求版本的说明和必需验收材料落库后，系统按现有准入规则自动移交研发。需求提交者即使离开会话，
协调器也能完成已经具备条件的交接。用户有需要时可在天工查看材料、进展与历史。查看、核对或确认页面属于按需操作，研发队列独立推进。
业务取舍、承诺冲突和授权变化继续走[现有客户决定流程](product.md#32-必须请求客户决定的例外)。

| 角色 | 要完成的事 | 可观察的结果 |
| --- | --- | --- |
| 需求提交者 | 提交正文或引用项目设计文档，必要时回答具体澄清问题 | 可查到已受理版本及待回答事项，普通需求在产物齐备后自动进入研发 |
| 产品 Agent 与系统 | 查证范围和规则，形成需求说明与验收样例，归档、校验并判定准入 | 当前版本的结论、材料、尝试和具体失败原因可按身份回查 |
| 研发与测试 Agent | 使用同版本需求及样例完成实现与验证 | 研发任务关联 BP，验证场景关联 BP 和 AC，并能追到固定候选的实际结果 |
| 项目成员 | 在天工按需查阅说明、进展和证据 | 能区分当前与历史、待执行与已执行，查看动作保持只读 |

本需求覆盖需求受理后的查证、分析、产物归档、现有准入与排队、研发和测试交接，以及天工需求详情的呈现。
功能需求采用结构化说明。缺陷沿用现象、影响、已有复现线索和修复判据的快通道。
非目标包括完整天工改版、通用原型生成平台、新的人工评审流程、外部 API 改造、正式候选验收流程替换及发布部署。

## 3. 业务要点

### BP-1 按版本归档需求产物

产品分析形成结果或结束一次尝试时，系统按项目、需求 ID、需求版本和分析版本关联有效说明及其材料。
尚未形成分析版本的失败或迟到结果按需求版本与尝试身份保留。归档包括原文与快照、查证依据、澄清和决定、BP、AC、样例、
实际形成的功能地图、UI 设计、原型引用及演练证据。正文和轨迹优先复用已存记录，附件或证据引用带可核对的版本或内容摘要。

普通需求的必需材料为符合当前规格校验的结构化说明和验收项，以及本次范围明确要求的材料。
缺陷的必需材料是问题说明与可检查的修复判据。按需产生的界面附件和演练状态随版本展示。
归档失败时记录失败点与可继续处理的原因。修订、失败、停止、取消和重试的已取得记录可按历史回查。

### BP-2 让关键业务结论能追到生效依据

产品分析从当前原文、已确认的项目约定、有效需求库条目和明确决定中提取规则。
关键 BP 保存来源位置、适用版本和支持结论的摘录。项目约定应能定位到正文，明确延续的历史决定可按其当前有效范围复用。
程序核对引用身份、适用版本、条目状态和摘录，以生效依据交接当前需求。已被取代的内容归入历史。
产品分析分别记录现有行为、已确认规则和推断。程序检查可确定的关联，业务含义由有依据的分析说明。

缺少会改变范围、兼容性或验收结果的外部事实时，采用现有联网工具查适用版本的一手资料，留下来源和摘录。
生效规则存在冲突，或关键后果仍无法确定时，记录已查依据、选项及影响，按现有澄清或决定流程处理。
搜索受限时记录实际缺口，根据其业务影响适用同一判断。

### BP-3 交接固定样例并区分三类证据

每条关键 AC 写清固定数据、前置条件、操作、可观察结果和检查位置。适用时记录反例以区分错误实现。
界面需求的本次受影响入口、操作路径和状态关联对应 BP 与 AC。原型按本次范围选用。
先根据生效规则写出独立预期，再观察实际执行结果。已有可运行对象且执行了演练时，保存对象身份、样例、观察结果及截图或日志。

规格校验、原型演练和候选验证分别保存和展示。演练缺项按实际情况为「待演练」或「不适用」。
研发和测试使用同版说明与样例。测试 Agent 独立补充检查，沿用现有流程在固定候选上通过公开入口执行并留证。

### BP-4 完成归档后按现有准入自动交接

运行时核对当前版本与必需材料的归档结果，再沿用系统准入和协调器队列。符合现行策略的普通需求自动排队，
研发位暂不可用时保持排队。校验或归档失败，以及等待澄清、业务冲突或授权不足时，保留实际原因并沿用现有处理路径。

重复投递和中断恢复先核对已有材料、准入和队列。已具备条件的当前版本复用完成的分析和材料，同版本只产生一次有效研发交接。
领取时核对当前版本和停止、取消等现有条件。过期结果视为审计记录，当前交接以有效版本为准。

### BP-5 天工按需展示可核对的进展

通过现有需求详情显示当前需求版本、当前分析版本、实际进展、阻塞原因和研发排队或领取状态。
用户可展开查阅依据、BP、AC、原型、样例、澄清与历史。每项执行记录能回查所属版本、样例、实际结果和证据位置。
活动和状态来自实际记录。尚未产生的结果、预期证据缺失和读取失败分别呈现。修订后可查旧版，当前视图依据新版本有效记录。

## 4. 功能地图与呈现

| 入口 | 操作或触发 | 完成信号 |
| --- | --- | --- |
| 业务会话 | 发送正文或引用项目内 Markdown | 返回需求身份与版本，已有原文可回查 |
| 产品分析 | 查证、形成说明、校验并归档 | 详情生成对应版本说明，失败与待澄清时显示原因 |
| 协调器 | 处理已归档并满足准入的需求 | 生成可以查询的排队或领取记录，关联同版说明 |
| 天工 → 需求详情 | 打开当前说明，展开或切到历史 | 分开看到当前进展、说明与依据、验证样例与执行证据、澄清和旧版 |

复用现有需求详情的布局和样式。顶部显示「需求版本 · 分析版本」「当前阶段」及最近一次能核对的进展。
正文依次为「说明与依据」「样例与证据」「澄清与历史」。有阻塞原因时在顶部说明，排队时展示真实排队记录。
证据分别显示规格、原型与候选的状态。示意如下。

```text
需求 v2 · 分析 v3                          研发排队
进展  已归档 → 系统准入通过 → 等待研发位
说明与依据    样例与证据    澄清与历史
规格校验通过  ·  原型待演练  ·  候选待验证
```

受理、分析、规格核对、等待、失败或重试、准入、研发排队和领取进展按实际动作登记。
天工的材料和证据读取遵循项目现有的工作区隔离和访问权限。

## 5. 验收项与固定输入

表中的需求、版本及候选名均为样例身份。各项的最后一列为实施前固定的独立预期。
所有样例均通过正常业务入口观察结果，必要时在隔离环境控制归档故障或宿主中断。

| AC | 覆盖 | 给定与操作 | 可观察的独立预期 |
| --- | --- | --- | --- |
| AC-1 | BP-1、BP-4 | 策略允许自动推进且研发位可用。分别从普通文本和 Markdown 受理两条范围明确的需求，取到受理身份后关闭客户端并等待后台推进，全程无需打开天工 | 两条需求分别保留同版原文与结构化说明，文档来源另有路径及摘要。各自准入通过并产生一次研发交接 |
| AC-2 | BP-1、BP-4 | 当前版本保存必需材料时失败。故障解除后重复提交同一次分析结果两次 | 失败时详情可查原因，当前版本保持未移交。恢复后材料齐备，有效研发交接数为一，失败尝试仍可查 |
| AC-3 | BP-1、BP-4 | 当前材料已归档，在记录研发排队前中断宿主，重启后重复触发协调器 | 依据已有归档和准入恢复，分析结果复用。当前版本最终只有一次有效研发交接 |
| AC-4 | BP-1、BP-2 | v1 写明「旧候选的通过报告也显示通过」，v2 改为「只有当前候选的通过报告才显示通过」。分别给 v2 分析引用旧句和当前句 | 旧句交接被拒且原因可查，当前句通过该项核对。v1 及其分析仍留在历史 |
| AC-5 | BP-2、BP-4 | 关键业务问题仍待回答，或已登记承诺冲突未解除。随后提供有依据的回答或决定 | 待处理时看到具体问题或冲突，研发保持待准入。解决后针对当前版本重新判定 |
| AC-6 | BP-1、BP-4 | v1 分析途中修订至 v2，再让 v1 返回。另在停止或取消后让当时的分析返回 | 能查到迟到尝试及原因，当前说明和状态保持由有效记录决定，迟到结果的研发交接数为零 |
| AC-7 | BP-3、BP-5 | 一条需求只有规格核对，一条另有绑定原型版本的实际演练。分别打开详情 | 前者按实际条件显示待演练或不适用。后者可查样例、观测和证据。两条候选状态各按真实记录展示 |
| AC-8 | BP-4、BP-5 | 受理一条无需原型的缺陷，已有复现线索与修复判据。提交者离线后再打开详情 | 用简版说明完成一次自动研发交接。打开详情可查到已有记录，交接数保持一次 |
| AC-9 | BP-1、BP-5 | v1 已归档且有演练结果。提交 v2，分别在 v2 分析前后打开详情 | 当前身份始终为 v2。等待新分析时明确显示当前进展，v1 证据可从历史回查。v2 成果归档后显示同版结论 |
| AC-10 | BP-3、BP-5 | 归档 W2 五组固定数据，若交付范围包含可运行原型，则逐组载入并打开验证栏 | 五组预期可追到同一验收项。实际演练逐组登记原型版本、实测及证据，当前和旧候选的通过结果可区分 |
| AC-11 | BP-2 | 用同一项目文档，分别给出存在的生效摘录、仅存在路径且摘录不存在、已被取代的库条目 | 生效摘录可核对。后两种返回具体依据问题并保持未移交，历史材料仍可查 |
| AC-12 | BP-3、BP-4 | 研发领取一条附固定样例的功能需求。随后测试 Agent 读取交接材料 | 研发和测试使用同版 BP、AC 与样例引用。测试结论带实际候选身份及证据 |

### W2 固定样例

入口为「天工 → 工作台 → 按需求 → 候选验证」。各组独立加载，当前候选均为 B，历史候选为 A。
观察状态文字、异常原因和历史入口。

| 样例 | 报告 | 测试方案 | 独立预期 |
| --- | --- | --- | --- |
| W2-1 | 空 | 可用 | 尚无结论 |
| W2-2 | B 通过 | 可用 | 验证通过 |
| W2-3 | B 失败 | 可用 | 验证未通过 |
| W2-4 | A 通过 | 可用 | 需重新验证，A 的报告可从历史打开 |
| W2-5 | 空 | 生成失败，原因「缺少必过场景」 | 尚无结论，同时显示方案生成失败原因 |

[现有 HTML 设计稿](tiangong-workspace.html)包含一组固定示例。五组完整演练及候选复验待执行。
适用对象缺失时仍保存样例和预期，记录对应的未演练状态。

## 6. 实施及证据要求

1. **归档、版本绑定、自动移交。** 复用现有域模型、记录和队列，先验证 AC-1 至 AC-3、AC-5、AC-6 和 AC-8。
2. **依据和样例。** 核对生效摘录与样例覆盖，接入同版研发和测试交接，验证 AC-4、AC-11 和 AC-12。
3. **详情与演练。** 显示进展、样例、证据与历史，验证 AC-7、AC-9 和 AC-10。界面试点范围为 W2 及关联材料。

每批实现前依据 [AGENTS.md](../../AGENTS.md)列出准许修改的文件及目的，在独立 worktree 先保留目标行为的失败证据，
再以最小改动使行为测试通过。外部接口及历史数据沿用兼容读法。关键条件在实际入口由确定性代码强制执行。
按影响更新架构、契约及[状态记录](../verification/status.md)，执行 `make check` 与提交覆盖率门禁后分批本地提交。
后续代码推送、发布、部署、生效配置和版本变更按所有者的明确授权处理。

真实 DSH 验收记录需求与分析版本、实际宿主与模型、运行轨迹、准入和队列状态，重点验证客户端离开后的交接和宿主中断恢复。
代码测试、原型演练和真实 DSH 验收分别汇报。本文保存需求及预期，运行时实现、演练与真实验收结果记入状态记录。

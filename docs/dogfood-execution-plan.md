# ForgeLoop DogFood 执行计划（TypeScript／DSH 版）

日期：2026-10-22。旧的 Python DogFood 计划与 G01/G02 记录保留在 Git 与
`legacy/`，按当时事实不追溯改写。本文只描述本轮的自我验证方式与已执行的链路。

## 1. 目标

用 ForgeLoop 修改 ForgeLoop 自身，验证：

1. 从 DSH 插件入口提交真实改进需求，而不是外部终端直接改代码；
2. 需求、分析、任务包、批准、实现、独立审查、正式测试与交付身份一致；
3. 产出可安装的候选包，并在新版本中验证改进、回查历史、保留恢复入口。

## 2. 本轮版本角色

| 角色 | 内容 | 证据 |
| --- | --- | --- |
| 参考基线 | 旧 Python 实现与 2026-10-22 在途工作树快照 | `.cache/forgeloop/dsh-migration/baseline/`、Git 历史 |
| V0 | 首个可运行纯 TypeScript 插件；含失败轮次可见性 | V0 构建的 tarball（版本名以 git tag 为准），SHA-256 `789965d6…`；需求 `req-20261022151546-b52121` |
| V1 | 由 V0 推进的“需求修订影响摘要”候选 | 需求 `req-20261022154141-b8907b`；摘要与安装证据见状态记录 |

V0/V1 是角色名，不是包版本；版本只由 git tag 决定，内容摘要以 tarball 与 `artifact.json` 为准。

## 3. 实际执行方式

1. 外部执行 Agent（DSH）在隔离 `DSH_HOME` 中安装 V0 tarball，绑定本项目记录根与执行现场。
2. 通过 V0 的 `/fl` 命令提交需求、排队分析与规划；审批人与执行者均为外部执行 Agent
   **代所有者在命令入口执行**，记录为 `local-owner`，不冒充模型自证或所有者本人操作。
3. 分析/规划/审查由无工具 Agent 完成；实现由有工具 Agent 在快照副本中完成；正式测试由程序
   运行。模型自评不构成通过条件。
4. 候选包由插件内 `/fl candidate` 从已交付 diff 构建；安装通过
   `dsh plugin add <tarball>`，必要时重启宿主。
5. 人工介入、外部补救、失败与未验证事项逐条记录在[状态记录](status.md)。

## 4. 验收条件

- **真实入口**：需求来自 DSH 命令，不是外部直接写记录；批准与验收有对象、版本与材料摘要。
- **真实执行**：实现/审查/测试由程序与真实 Agent 完成，保留轨迹、退出码、日志与摘要。
- **真实产物**：安装包包含构建后的 JavaScript 与必要资源，不携带 Python；安装形态为安装目录。
- **真实新版本**：V1 的新行为在安装后的 V1 中可用，旧需求与证据仍可读。
- **可恢复**：保留 V0 tarball 与记录副本；恢复步骤见[部署说明](deployment.md)。
- **如实区分**：实现已具备、检查已执行、真实场景已验收、后续方案分别陈述。

## 5. 不在本轮

- 不追求全自动发布、部署、回滚或长期无人值守；
- 不新增邮件/IM、Web 控制台、多租户或远程访问；
- 不为凑“自迭代”而故意制造缺陷，或让 V0 缺少必要授权/持久化保护；
- 不把外部执行 Agent 完成的开发计为 ForgeLoop 独立成果。

## 6. 历史关系

旧 G01/G02 的真实模型闭环、邮件入口与热升级记录仍是历史事实，但 **不再作为当前产品入口的
验收依据**；当前入口的验收以本文件与状态记录中的 V0/V1 证据为准。

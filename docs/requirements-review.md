# ForgeLoop 五步工作法需求审查

日期：2026-10-12，Asia/Shanghai。依据：用户要求快速启动，非必要需求首版不做，进入待实现列表。

**审查结论：首版交付一个可用的 CLI 研发闭环。邮件、管理页面、附件平台、自动上线和自动自升级后置。原先“只读状态页优先”和“完整平台全部建完才能算首版”的计划被替代。**

保留 LangGraph、PI、容器、main 主干、原始记录和人工决策等基础方向。完整目标保存在 [历史快照](history/full-product-scope-2026-10-12.md)，当前实施范围以 [首版需求](product-requirements.md) 为准，待实现项以 [需求列表](pending-requirements.md) 为准。

## 1. 质疑需求

按用户指定的五步顺序审查：质疑需求、删除非必要部分、简化、缩短周期、最后自动化。出处为 Musk 与 Everyday Astronaut 的原始访谈，步骤以转写辅助核对；这里的项目取舍是本次工程判断。[原始访谈](https://www.youtube.com/watch?v=t705r8ICkRw)、[转写核对](https://rosetta.to/u/everydayastronaut/starbase-tour-with-elon-musk-part-1-summer-2021?t=2393)

需求提出者是项目所有者；以下范围取舍由本次审查提出，实施前在最小技术方案中确认。每项先问：

- 首次完成一个真实小任务，没有它是否就无法交付？
- 可以用已有工具、CLI 或短暂人工步骤完成吗？
- 是当前已出现的问题，还是预计规模增大后才可能需要？
- 原生 PI／LangGraph 已有能力是否足够，是否在重复建设？

核心价值应由真实代码改动、真实测试、独立审查和用户验收证明。状态页展示、双入口覆盖和自主上线不是首个价值验证的替代物。

## 3. 简化实现

首版使用一个 CLI、一个 LangGraph 图、一个 PI RPC Adapter、一个本地持久化存储与文件记录、一个受限执行环境。先用现成能力，不先抽公共平台。

一次处理一个小任务。用户批准范围、方案和测试命令后，PI 实现并自验证；独立 PI 会话审查；程序运行正式测试；失败返回修复，达到本次三个失败轮次后等待追加授权。用户最终验收 diff、测试证据和报告，人工同步 main。审查或自验证失败不误计为正式测试失败。

范围与方案逻辑上仍分别记录，但可以在同一次本地批准完成。不建设邮箱审批签名、Web 身份、分布式授权或审批运营后台。

## 4. 缩短周期

首次看到真实 PI 事件是第一个工程检查点；首次产生可验证 diff 是第二个。节点环境、协议问题应在最小调用中暴露，不等展示层和完整平台做好后才接模型。

首个可运行结果完成即停止扩张。详细步骤见 [快速启动验收计划](first-validation-plan.md)。（2026-10-12 所有者撤销 30 小时上限与人工时间测量：交叉实践已证 Agent 开发效率优势。）

初始工程搭建和由 ForgeLoop 自动完成的任务分开记账。原先状态页任务后置；首个候选真实任务可以是给 ForgeLoop 已有 CLI 增加一个小而可验收的功能，具体目标在运行前确认。

## 5. 最后自动化

先手工验证一次 PI 调用、实际测试与审查，再由 LangGraph 串起这条已能工作的路径。首版自动化集中在编码、自验证、审查、测试与有界修复，不同时自动化邮件、资源采购、部署、运维和自升级。

完成若干真实任务后，按实际使用痛点选择下一项，经过范围确认再做，不要求把整个列表实现后才允许使用。（不再比较人工时间基线——所有者决定以交付质量与使用体验为价值判断依据。）
